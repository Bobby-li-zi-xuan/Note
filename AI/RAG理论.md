## RAG（检索增强生成）
>一种结合信息检索和文本生成的技术

工作流程：
1. 文档处理：将文档分块，生成 Embedding 向量
2. 将向量存储到向量数据库（PostgreSQL pgvector）
3. 将用户查询转换为向量，进行相似度搜索（余弦相似度）
4. 将检索到的相关文档作为上下文注入到 LLM
5. LLM 基于上下文生成回答

与微调的区别：
1. 微调在预训练模型基础上，使用特定数据对AI进行训练
2. 在**模型权重层面**修改大模型本身，让模型**永久内化**领域知识
3. 微调对算力和训练成本要求高

核心痛点及优化方案：
1. **召回精度低** → 向量化模型微调、多路召回（向量+关键词混合检索）、标题+正文联合 embedding
2. **上下文丢失** → 合理切片分块，增加块间关联，chunk 带标题前缀
3. **幻觉严重** → 严格要求LLM只基于检索原文回答
4. **时效性差** → 定时更新向量库、对接实时知识库
5. **上下文窗口有限** → 摘要压缩、过滤无用文档、Token预算控制
6. **重复内容浪费** → RagSearchFilter 距离过滤 + 两段式 Jaccard 去重
7. **检索结果无结构** → RagContextAssembler 编号化输出（【1】...【2】...）

## 常见的reranker模型
#### 一、两类主流 Reranker 架构
1. **Cross-Encoder（交叉编码器，工业 90% 在用）**
    输入 `[query][sep][doc]` 成对做交叉注意力，精细打分，精度高；一次只能打分一对，只适合召回 Top10~Top50 后重排。
2. **LLM-based Reranker（解码器大模型打分）**
    用 Qwen/Mistral/Gemma 等大模型判断相关性，超长文本、复杂推理更强，但速度慢、显存占用高。

#### 二、中文本地开源（国内 RAG 标配）
##### 1. BGE-Reranker 系列（最通用、中文首选）
都是Cross-Encoder
- bge-reranker-v2-m3（主流均衡款）
    - 参数：568M | 上下文 8192token | Apache2.0 商用免费
    - 优势：完美搭配 bge-m3 embedding，中文领域 SOTA，支持超长段落，量化后可 CPU 跑，延迟可控；无需复杂 prompt
    - 短板：超大文档批量重排 GPU 压力大
- bge-reranker-large/base（v1 旧版）
    - base 轻量、large 精度更高，仅支持 512token，短文本场景够用
- bge-reranker-v2-gemma（LLM 型高精度）
    - 基于 Gemma 2B，复杂问答、专业文档精度更强，推理速度慢一倍

##### 2. Qwen3-Reranker（阿里通义）
- 代表：Qwen3-Reranker-4B / 8B
- 特点：LLM 式 reranker，支持**32k 超长上下文**，中英均衡；适合合同、书籍长文档重排
- 缺点：参数量大，单条打分延迟高，低配机器不可行

##### 3. BCE-Reranker（网易有道）
bce-reranker-base_v1，轻量双语模型，中英日韩跨语言强；适合中英混合知识库，体积小、推理快

##### 4. mxbai-rerank（海外多语言，中文可用）
mxbai-rerank-large-v2，2B 参数，100 + 语言通用，海外多语种项目首选，中文弱于 BGE

## 常见的向量库
#### 一、基础信息总表

|对比维度|PGVector|Qdrant|Milvus|
|---|---|---|---|
|**产品定位**|PostgreSQL 向量插件，关系 + 向量一体化|Rust 独立高性能向量库，单机 / 轻集群专用向量引擎|云原生分布式企业级向量数据库，海量数据首选|
|**底层架构**|复用 PG 存储、事务、SQL 引擎，向量检索扩展|独立单进程 Rust 服务，分段存储、内存映射优化|存算分离：元数据 etcd、对象存储 MinIO、计算节点分离|
|**开源协议**|PostgreSQL License（宽松商用）|Apache 2.0|Apache 2.0|
|**部署复杂度**|极低，已有 PG 直接装插件|低，单二进制 / 容器一键启动；集群简单|高，依赖 etcd、对象存储、消息队列，K8s 重度依赖|
|**推荐数据规模**|≤1000 万向量，超千万性能断崖下滑|千万～1 亿向量均衡最优|1 亿～十亿 / 万亿级海量向量|
|**API**|标准 SQL（JDBC/ORM 全兼容）|gRPC+REST，专用检索 DSL|gRPC+REST，完整向量专用 SDK|
|**事务 ACID**|原生完整支持|仅单 segment 有限事务，无跨分片事务|无强事务，追求高吞吐检索|
|**GPU 加速**|不支持|有限量化加速，无 GPU 建索引|原生深度 GPU 索引（CAGRA/FAISS），百亿级建索引提速数倍|

### 二、性能与检索能力
#### 检索 QPS & 延迟（同等硬件 8 核 32G，768 维向量）
1. **PGVector**：5k~15k QPS；百万内稳定，千万级全库检索延迟暴涨；HNSW 构建极慢
    - 优势：**带 SQL 精准过滤**时，PG B 树先过滤缩小范围再检索，多租户隔离场景表现好
    - 短板：全量无过滤检索性能远低于专用向量库
2. **Qdrant**：30k~80k QPS；CPU 性能天花板，内存占用低；原生支持**多向量、ColBERT 细粒度检索**
    - 优势：过滤 + 向量联合检索优化极强，支持磁盘存储向量、仅缓存索引图，内存节省 3~5 倍
3. **Milvus**：单机 QPS 略低于 Qdrant；分布式集群横向扩展无上限；GPU 场景延迟碾压另外两者
    - 优势：海量分片、分区、冷热数据分离，高并发线上 RAG、推荐系统首选

#### 2. 索引支持
- PGVector：仅 IVFFlat、HNSW 两种，参数调优空间少
- Qdrant：HNSW、IVF-PQ、二进制索引，原生多向量共存
- Milvus：HNSW、IVF、DISKANN、SCANN、GPU-CAGRA、多种量化方案，工业最全索引体系

#### 3. 混合检索（向量 + 关键词）
- PGVector：需要自行搭配 PG 全文索引 tsvector，代码拼接实现，无原生融合打分
- Qdrant：原生支持稀疏向量 + 稠密向量混合检索，内置权重融合
- Milvus：无内置 BM25，需对接 Elasticsearch / 自建稀疏检索做多路召回融合

### 三、元数据、存储
1. **PGVector**
    - 元数据：完整 SQL WHERE、JOIN、分组、聚合，业务结构化数据与向量同表
    - 运维：复用现有 PG 备份、主从、监控、权限，无需新增中间件
    - 缺陷：向量与行数据耦合，单表超千万行后扩容困难；无法冷热分离
    
2. **Qdrant**
    - 元数据：强类型 payload 索引，范围、模糊、多条件过滤速度优秀
    - 运维：单实例无依赖，容器启动秒级；集群分片简单，但多租户、RBAC 能力弱
    - 优势：向量磁盘落地，低内存服务器可跑大规模数据
    
3. **Milvus**
    - 元数据：字段过滤、分区、多租户 RBAC 完整；支持海量分区隔离业务
    - 运维：组件多（etcd/minio/pulsar），运维成本高；提供托管 Zilliz Cloud 降低运维
    - 优势：存算分离，弹性扩缩计算 / 存储，冷热数据分层存储

### 四、核心优缺点拆解
#### PGVector
- **优点**
1. 已有 PostgreSQL 业务零新增中间件，架构最简
2. 完整 SQL、事务、联表查询，适合业务数据和向量强关联场景（用户、订单、文档元数据）
3. 学习成本极低，后端开发无需学习新 SDK，ORM 直接操作
    
- **缺点**
1. 千万级以上向量性能严重衰减，不适合海量知识库
2. 不支持 GPU 加速，高维 / 超大索引构建极慢
3. 无向量专属高级能力（多向量、混合稀疏检索、冷热分层）

#### Qdrant
**优点**
1. Rust 底层，CPU 性能、内存控制三者最优，低配机器友好
2. 原生多向量、ColBERT 细粒度检索，现代 RAG 标配
3. 部署极简，无复杂依赖，中小规模私有化首选
4. 过滤检索优化极强，带条件筛选的问答召回延迟极低
    
- **缺点**
1. 分布式能力弱于 Milvus，十亿级数据场景吃力
2. 无强事务，不适合要求数据强一致性的业务

#### Milvus
- **优点**
1. 唯一面向十亿 / 万亿向量原生分布式架构，线性扩容
2. 完善 GPU 索引加速，海量知识库、图像检索必备
3. 分区、多租户、冷热分离、高吞吐写入适配线上大流量
    
- **缺点**
1. 部署依赖多组件，单机小项目过度复杂，资源开销大
2. 无 ACID 事务，写入仅保证最终一致性
3. 冷启动加载分段索引延迟高于 Qdrant

## 向量索引算法
#### IVF-PQ 向量索引算法
1. **两大核心组件**
- IVF（倒排文件 / 聚类粗筛）
先对全量向量做 **K-Means 聚类**，把向量分成 `nlist` 个簇（聚类中心），每个簇对应一个倒排列表。
- 检索时：先只和**簇中心**算距离，选出最近的 `nprobe` 个簇，**直接过滤 90%+ 无关向量**，大幅缩小检索范围。
- 作用：**粗粒度过滤，减少计算量**。

- PQ（Product Quantization 乘积量化）
对向量做**有损压缩**：把一个高维向量切分成 **m 段子向量**，每段子向量单独聚类、用一个短编码替代完整向量。
- 例：768 维原始向量（3072 Byte）→ 压缩为 **32 Byte 编码**，内存压缩比可达 **50 倍 +**。
- 作用：**极致压缩内存、加速距离计算**。

2. **完整工作流程**
- 离线索引构建
1. 全量向量执行 **K-Means 聚类**，生成 `nlist` 个簇中心，建立倒排表。
2. 对每个簇内所有向量做 **PQ 乘积量化**，向量转为紧凑编码，不再存储原始浮点向量。
3. 最终只保存：**簇中心 + PQ 压缩编码**。

- 在线查询（两步检索）
2. **粗搜（IVF）**：查询向量对比所有簇中心，选出最近 `nprobe` 个簇，只在这些簇内检索。
3. **精搜（PQ）**：利用预计算查找表（LUT），快速计算查询向量与 PQ 压缩向量的近似距离，返回 Top-N 结果。
#### HNSW
1. 核心结构原理
HNSW 是**多层有向图 + 小世界网络**结合体，整体类似**跳表 + 地图分层**：
- **多层架构**：由多层图组成，**Layer 0（底层）** 包含**全量向量**，层数越高，节点越少、连接越稀疏。
- **分层作用**：
    - **高层**：长距离跳转，做**全局粗定位**（类似高速路）。
    - **低层**：密集连接，做**局部精细搜索**（类似街道）。
- **小世界特性**：每个节点同时拥有**近邻短连接**和**跨区长连接**，保证任意两点间跳转步数极少，检索复杂度接近 **O(logN)**。
2. 建索引流程（逐层插入）
- 新向量通过**随机概率**确定所属最大层数（层数越高概率越低）。
- 从**顶层入口节点**开始，逐层向下贪婪搜索，找到每层最近邻节点。
- 在对应层建立**双向边连接**，限制每个节点最大连接数 `M`，剔除冗余远邻。
- 更新全局入口节点，完成单向量插入。

3. 检索流程
- **顶层粗搜**：从全局入口开始，在高层图执行**贪婪搜索**，不断跳转到离查询向量最近邻居，快速缩小范围。
- **逐层下降**：当前层无法更近时，下沉到下一层，重复贪婪导航。
- **底层精搜**：到达 **Layer 0**（全量数据层），扩大候选范围，精确计算距离，返回 Top-K 结果。

## 评估指标
### 召回层指标（向量库 / Embedding）
作用：从海量文档捞出相关候选，决定上限
1. **Recall@k 召回率**
    真实相关文档是否出现在前 k 条（k 一般取 10/20/50）
    公式：相关且被召回文档数 / 全部真实相关文档
    痛点：召回低 = 漏关键材料，LLM 必然幻觉
2. **Precision@k 精确率**
    前 k 条里真正相关文档占比
    痛点：precision 低 = 一堆无关文档进入 rerank，干扰排序、增加计算开销
3. **MRR 平均倒数排名**
    衡量第一个相关文档排第几，适合问答场景；值越高，相关文档越靠前
4. **NDCG@k**
    衡量排序质量，**不只看有没有召回相关文档，还看重相关文档排得靠前还是靠后**。区分排序优劣
### Reranker 重排层指标
输入是召回 top-k 文档，重新打分排序
- Precision@k、NDCG@k、MAP（平均精度）
    核心目标：提升 top3/top5 精准度，过滤无关噪声文档

### 生成层（LLM 答案质量指标）
#### 自动化指标
1. **上下文相关性（Context Relevance）**
    问题和检索文档是否匹配，无关文档不应作为依据
2. **答案忠实性 / 事实一致性（Faithfulness）**
    答案内容是否全部来自检索片段，无编造、幻觉；RAG 核心指标
3. **答案有用性（Answer Relevance）**
    答案是否准确回答用户问题，不答非所问
4. 传统文本指标：BLEU、ROUGE、BERTScore（和人工标准答案对比相似度）

### 人工评估（生产必做）
- 幻觉等级：无幻觉 / 轻微编造 / 严重编造
- 完整性：是否覆盖全部提问要点
- 简洁流畅度、专业准确性

### 综合业务指标（线上落地）
- 用户重试率、客服转人工率、问题一次性解决率
- 平均检索耗时、token 消耗成本

### 召回 Recall@k 低（漏文档）
- **原因**
1. Embedding 语义匹配弱，同义词、行业术语识别差
2. 文档切分 Chunk 不合理：过长混杂多主题、过短丢失上下文
3. 单路稠密召回，缺少关键词兜底
4. 缺少难负样本，Embedding 泛化差（微调过拟合）
5. 向量库索引参数不合适（HNSW ef 太小，牺牲召回换速度）

- **优化**
1. 多路召回融合：稠密 Embedding (BGE-m3) + BM25 稀疏检索 + 稀疏向量（bge-m3 稀疏输出）加权融合
2. 优化 Chunk 策略：滑动窗口分块、带重叠切片、按语义分割（而非固定长度）
3. 换更强中文 Embedding：bge-m3 > bge-base > m3e-small
4. Embedding 微调：扩充 query 增强、构造难负样本、LoRA 微调防过拟合
5. 调大索引 ef_construction/ef_search，平衡召回与速度
6. 知识库补充同义术语、行业词典扩充语义覆盖

### （二）Precision@k 低（召回一堆无关文档）
- **原因**
1. Embedding 区分度不足，无关文本向量距离接近
2. 没有 Reranker 过滤，仅靠向量相似度排序
3. Chunk 混入大量无关杂内容
4. 向量融合权重不合理，BM25 权重过高引入关键词噪声

- **优化**
1. 接入 Reranker 做二次过滤（bge-reranker-v2-m3 工业标配），截断 top3~top5 送入 LLM
2. 多路召回加权调参，降低纯关键词匹配权重
3. 预处理清洗文档，剔除无效页眉页脚、重复文本
4. 微调 Embedding 增加难负样本，拉大相关 / 无关向量差距

### （三）NDCG/MRR 低（相关文档排在很靠后）
- **优化**
1. 优化 Reranker 精度；微调 Reranker 增加领域标注数据
2. 多路召回结果重排序融合，不直接拼接
3. Chunk 携带文档标题、章节前置，增加关键信息权重

### （四）生成层 Faithfulness 低（严重幻觉）
- **原因**
1. 召回混入大量无关片段，LLM 强行拼凑答案
2. 检索上下文过长，LLM 混淆信息、丢失细节
3. Prompt 没有约束忠实引用原文
4. 知识库存在矛盾、错误原始数据

- **优化**
1. Reranker 强过滤，只保留 top3-5 高相关片段，减少噪声输入
2. Prompt 增加强制约束：“仅使用提供文档内容回答，无依据则说明无法回答，禁止编造信息”
3. 文档预处理校验，剔除错误、冲突资料
4. 使用长上下文 LLM，降低超长文本信息遗忘
5. 增加引用溯源输出，强制模型标注答案来源段落

### （五）Answer Relevance 答案答非所问
- **优化**
1. Query 预处理改写：用户口语问句标准化、纠错、扩展子问题
2. 增加 Query 分类路由，匹配对应知识库分区
3. Prompt 清晰限定回答范围，区分多意图问题
4. 补充问答对微调 LLM，对齐业务提问方式
