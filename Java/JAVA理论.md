### equals()和 == 的区别
- equals()
	- 仅用于引用类型
	- 默认情况下等价于 ==
	- 可以重写，重写后自动覆盖Object.equals()，（所有类默认继承java.lang.Object)重写时必须同时 **重写HashCode**
		- 若不重写 `hashCode`，会使用 `Object` 类的默认实现 —— 生成一个伪随机值（JDK8+）。
		- 即使两个对象的业务属性完全相同（`equals` 返回 `true`），它们也是不同的对象实例 → `hashCode` 不同 → 哈希集合无法识别它们是同一个对象。
```Java
@Override 
public boolean equals(Object o) 
{ 
	// 1. 同一对象直接相等 
	if (this == o) return true; 
	// 2. 对象为空 直接不等 
	if (o == null) return false; 
	// 3. 类型不同 直接不等（拒绝父子类兼容） 
	if (getClass() != o.getClass()) return false; 
	// 4. 强转 
	User user = (User) o; 
	// 5. 比较基本类型+引用类型 
	// 基本类型直接==，引用类型用Objects.equals判空 
	return Objects.equals(id, user.id) && Objects.equals(username, user.username); 
} 
// 重写equals必须重写hashCode 
@Override 
public int hashCode() 
{ 
	return Objects.hash(id, username); 
}
```
- ==
	- 可用于基本类型和引用类型
	- 用于引用类型时判断的是**内存地址是否相等**
	- 不可重写
### Java反射机制
>指程序在运行时，能够获取自身或任意类的信息，并能够操作这些信息的能力
#### 核心原理
>JVM加载类后，会在内存中生成一个Class对象，反射就是通过操作这个Class对象间接操作目标类的成员
- 获取Class对象的方式
```java
//1. 类名.class
Class<User> clazz1 = User.class;

//2. 对象.getClass（）
User user = new User();
Class<? extends User> clazz2 = user.getClass();

//3. Class.forName("全类名")（动态加载）
Class<?> clazz3 = Class.forName("com.example.User");
```
- Class对象承载了类的所有元数据
#### 核心功能
1. 动态创建对象
``` java
// 获取有参构造器（参数类型为 String.class, int.class）
 Constructor<User> constructor = clazz1.getConstructor(String.class, int.class); 
// 创建对象 
User user = constructor.newInstance("张三", 20);
```
2. 动态调用方法
```java
// 获取方法（参数1：方法名；参数2：方法参数类型） 
Method method = clazz1.getMethod("setName", String.class); 
// 调用方法（参数1：对象实例；参数2：方法入参） 
method.invoke(user, "李四");
```
3. 动态访问属性
```java
// 获取属性（getDeclaredField 能获取私有属性，getField 只能获取公有属性） 
Field field = clazz1.getDeclaredField("name"); 
// 打破封装（访问私有属性必须设置，无法操作JDK内部的API，需要另外设置JVM启动参数） 
field.setAccessible(true); 
// 设置属性值 
field.set(user, "王五"); 
// 获取属性值 
String name = (String) field.get(user);
```
#### 核心特性
1. 反射是**运行时行为**，而非编译时，可动态加载编译期未知的类
2. 打破封装性：通过 `setAccessible（true）`可以访问私有成员
	- 原理：在 JVM 内部，每次调用方法或访问字段时，都会进行一个“访问控制检查”（Access Control Check）。这个检查的逻辑是：
		- JVM 会比对**当前调用者（Caller）**的类加载器和包名，与被访问的**目标成员（Field/Method）**的修饰符（`private`、`protected`、`public`）。
		- 如果是 `private` 且包名不同，JVM 就会抛出 `IllegalAccessException`
		当你执行 `method.setAccessible(true)` 时，**原理就是修改了该 `Method` 或 `Field` 对象内部的一个 `override` 标志位**。当这个标志位为 `true` 时，JVM 在执行该成员的访问逻辑时，会**直接跳过**上述的访问控制上下文校验步骤，不再检查调用者是否有权限。
3. 性能开销大
#### 适用场景
1. Spring的IOC容器、MyBatis的Mapper代理
2. JDK动态代理
3. Json序列号和反序列化
4. Spring注解处理
### String、StringBuffer和StringBuilder的区别
##### String
>**不可变**的字符序列。任何对String对象的操作都会生成一个新的String对象
- 特点
	- 不可变性
	- **线程安全**
	- 内存效率问题：String不可变，故它的字符串值可能会被多次复制，频繁操作时可能会造成内存浪费（连接）
- 使用场景
	- 字符串内容不需要频繁改变、字符串长度较小
##### StringBuffer
>**可以变更**的字符串且线程安全（所有方法都加了Synchronized锁）
- 性能：相对较低，在不涉及多线程的情况下可能比StringBuilder慢
- 使用场景：**多线程环境下**进行字符串修改
##### StringBuilder
>一个可以变更的字符序列，但**线程不安全**，适合单线程环境下使用
- **性能较高**，适合单线程环境中的高效字符操作

### 抽象类和接口的区别
1. **继承关系**
- 抽象类：**单继承**，一个类只能继承一个抽象类
- 接口：**多实现**，一个类可以 `implements` 多个接口
2. **构造方法**
- 抽象类：**有构造器**，供子类初始化调用
- 接口：**无构造器**，不能实例化
3. **成员变量**
- 抽象类：普通成员变量、常量、静态变量都可以
- 接口：**默认 public static final**，只能是常量
4. **方法权限 & 类型**
- 抽象类：
    抽象方法（无实现）、普通实例方法、静态方法；权限 `public/protected/default/private`
- 接口：
    抽象方法默认 `public abstract`；
    JDK8：`default`默认方法、`static`静态方法；
    JDK9：私有方法；
    不能有普通实例变量
5. **代码复用**
- 抽象类：**模板复用**，抽取子类公共代码，实现代码复用
- 接口：**行为约束**，只定义子类要实现哪些方法
6. **设计思想**
- 抽象类：**is-a** 是什么（动物→猫、狗）
- 接口：**has-a / can-do** 能做什么（会跑、会飞）
7. **修饰符**
- 抽象类：可以有 `final`、成员块、构造代码块
- 接口：不能用 `final`，无代码块
### 深拷贝和浅拷贝
##### 浅拷贝
>拷贝时创建一个新的对象，**只复制对象本身**，以及对象内部的**基本数据类型**；如果对象内部有**引用类型**（比如另一个对象的引用），**只复制引用地址**，不复制被引用的对象本身。
- 特点
	- 速度快，开销小
	- 修改新对象的引用类型成员，**会影响原对象**
	- String、Integer、Long 等不可变引用除外，这些对象**一旦创建，内部成员变量无法被修改**，没有任何`set`方法，所有修改操作都会**新建对象**，不会改动原对象。
- 实现方式
1. 重写clone()方法
```java
@Override
protected Object clone() throws CloneNotSupportedException{
	// 调用父类native克隆，默认浅拷贝 
	return super.clone();
}
```
2. 构造器拷贝（直接引用赋值）
```java
public User(User user){ 
	this.name = user.name; 
	this.age = user.age; 
	this.address = user.address; // 引用直接赋值 
}
```
3. BeanUtils工具拷贝
```java
//默认浅拷贝
User newUser = new User(); 
BeanUtils.copyProperties(oldUser, newUser);
```
##### 深拷贝
>拷贝时创建一个新对象，**完全复制整个对象图**。不仅复制对象本身和基本类型，还会**递归地复制所有引用类型所指向的对象**，最终得到两个完全独立的对象。
- 实现方式：
	- 重写`clone()`方法，对引用类型成员也调用`clone()`
	- 序列化/反序列化，对象写出为字节流，再反向读取生成新对象，彻底断引用
	- 手动new新对象，逐个赋值
```java
public User deepCopy(){ 
User user = new User(); 
user.setName(this.name); 
user.setAge(this.age); 
// 新建全新子对象 
Address addr = new Address(); 
addr.setCity(this.address.getCity()); 
user.setAddress(addr); 
return user; 
}
```
- 特点：
	- 新对象和原对象互不影响
	- 速度慢，开销大
## Java集合
#### Array
>Java中的基本数据结构，可以储存基本类型对象或数据引用
- 大小在创建时确定
- 通过索引访问，遍历效率较高
- 连续内存，缓存命中率高
#### ArrayList
>Java集合框架中的一个类，只能储存对象引用
- 基于**动态数组**实现，大小可根据需要自动扩容,每次扩容都需要 **拷贝数组**
- 提供了较快的随机访问和高效的内存应用
- 连续内存，缓存命中率高
#### LinkedList
>Java中的一个实现类
- 基于**双向链表**实现，没有固定容量限制
- 插入和删除效率高
- 每个节点除数据外，还要存前驱和后继指针，非连续内存。缓存命中率低

#### HashSet
>Java集合框架中实现了Set接口的类，用于储存不允许重复的元素
- 确保唯一性的机制
	- 基于哈希表实现：内部通过HashMap来储存元素
		- key是元素值，value是一个占位PRESENT，可用于判断元素是否删除成功
	- hashCode()方法：添加元素时，调用该方法来计算其哈希值，决定元素在哈希表中的储存位置
	- equals()方法：确定储存位置后，如果该位置已经存在一个具有相同哈希值的元素，会调用equals()方法判断两个元素是否相等，相等则添加操作失败
#### HashMap
>采用哈希表结构储存数据，储存的是键值对，底层用***一维数组+单向链表+红黑树***实现。
- **红黑树**出现的时机：当某个索引位置上的**链表长度达到8且数组的长度超过64**时，此时索引位置上的单向链表要改为红黑树，当元素个数小于6时退化为单向链表
- **扩容机制**：当储存的键值对数量超过设定的阈值时触发
	- 创建一个新数组，容量通常是原数组的两倍
	- 遍历旧数组中每一个键值对，重新计算他们在新数组中的位置，然后放入新数组的对应位置
- **put方法的流程**
	- 对传入的key(**可以为空**)计算其哈希值，确定其在底层数组中的储存位置
	- 判断位置是否为空，空则直接放入
	- 位置不为空，处理哈希冲突
		- 若key已存在：放弃添加元素，更新对应的value值
		- 若key不存在：在链表末尾添加新节点
		- 若链表长度达到阈值，将链表转为红黑树
	- 扩容检查：元素添加成功后，会检查当前的size是否超过了扩容阈值，超过则进行扩容操作
- **在JDK1.8中的优化**
	- 引入红黑树，**查询、插入、删除操作的时间复杂度更优**，且能保证数据有序性（红黑树是自平衡的二叉搜索树）
	- 用尾插法代替头插法：头插法可能导致链表反转，多线程下可能导致环形链表
	- 扩容机制优化：JDK1.7扩容需要重新计算所有元素的哈希值。JDK1.8利用高位运算
	- hash函数优化：引入扰动函数减少哈希冲突
> [!NOTE] 链表长度达到8会马上进化为红黑树吗
> 不会。key重复的本质是哈希碰撞，当链表长度达到8时HashMap会先尝试扩容数组减少哈希碰撞，若有链表长度仍然大于等于8会继续扩容，直到数组长度达到64，才将链表树化

#### ConcurrentHashMap
>**线程安全的键值对存储容器**，底层结构与HashMap一致，都是数组+链表+红黑树
##### 1. 数据结构
- Java1.7中的数据结构（分段锁）
![[image-20230505092654811.png]]
- 提供了一个segment数组，在初始化ConcurrentHashMap 的时候可以指定数组的长度，默认是16，一旦初始化之后中间**不可扩容**
- 在每个segment中都可以挂一个HashEntry数组，数组里面可以存储具体的元素，HashEntry数组是可以扩容的
- 在HashEntry存储的数组中存储的元素，如果发生冲突，则可以挂单向链表

- 储存流程
	- 先去计算key的hash值，然后确定segment数组下标 
	- 再通过hash值确定hashEntry数组中的下标存储数据  
	- 在进行操作数据的之前，会先判断当前segment对应下标位置是否有线程进行操作，为了线程安全使用的是**ReentrantLock进行加锁**，如果获取锁失败**会使用cas**自旋锁进行尝试

- Java1.8中的数据结构
![[Pasted image 20260504164928.png]]
- 采用 CAS + Synchronized来保证并发安全进行实现
- CAS控制数组节点的添加
- synchronized只锁定当前链表或红黑二叉树的首节点（桶级锁），只要hash不冲突，就不会产生并发的问题 , 效率得到提升

##### 2. 核心机制
- 初始化延迟
	- 数组**懒加载**，第一次 put 才初始化，节省内存。
- 并发扩容
	- 多线程可以**协助扩容**，分担迁移任务；
	- 扩容期间通过 `ForwardingNode` 标记旧桶正在扩容迁移，读写线程协助迁移，不阻塞全局。
- key/value 约束
	- **key、value 都不允许为 null** 
    - 区别于 HashMap：允许 key/value 为 null；
    - 设计目的：并发下避免 `null` 歧义，防止无法区分「不存在」和「值为 null」。
- 元素计数
	- 不用简单 `size` 变量；
	- 结合 **baseCount + CounterCell 数组** 分片计数，减少并发修改竞争，高效统计元素总数。
##### 3. 常用方法
- **put()**
	- 计算 hash 定位桶；
	- 桶为空：CAS 无锁写入；并发冲突时谁先完成写入就用谁的
	- 桶有数据：synchronized 锁住头节点，链表 / 红黑树插入；
	- 满足条件触发扩容 / 树化。
- **get()**
	- 完全**无锁**；
	- 通过 hash 定位，链表 / 树遍历查找；
	- 利用 `volatile` 保证节点可见性，读到最新数据。
- **clear/remove**
    - 同样采用**桶级锁**，局部加锁，并发高性能。
##### 4. 缺陷
- 不保证复合操作原子性（如 `if(map.containsKey) + put`），需手动加锁；
- 弱一致性：迭代器是**弱迭代**，遍历期间其他线程修改，不会抛并发修改异常。

## Java并发
#### 创建线程的几种方式
- 继承Thread类，重写run()方法
- 实现Runnable接口
- 实现Callable接口，使用FutureTask创建任务对象
- **使用Executor**框架：将任务提交给线程池，由线程池来管理线程的生命周期
- 最终通过new Thread().start()创建
#### 线程和进程的区别
- 线程：轻量级的进程，一个进程分为多个线程，线程是cpu调度的基本单位，线程共享进程的资源
	- 切换时的开销：只需保存CPU寄存器、PC计数器、栈指针
- 进程：资源分配的基本单位，相互之间无法通信，切换开销较大
	- 切换开销
		- 保存硬件上下文：CPU寄存器、PC计数器、栈指针等
		- 切换页表、刷新TLB缓存
		- 内核态栈切换
		- 刷新CPU缓存，原有的CPU缓存全部失效
		- 操作系统调度算法计算、更新进程状态、PCB 进程控制块信息保存与恢复
#### 协程
>协程（Coroutine）是一种运行在**用户态**、由应用程序自己调度的**轻量级执行单元**，可以在执行中主动暂停（Yield）、之后再恢复（Resume），切换完全不经过操作系统内核。
- **一句话定义**：**可暂停、可恢复的函数**，在单线程内实现多任务并发
- **关键动作**
    - **挂起（Yield）**：函数执行到一半主动让出 CPU，保存当前状态
    - **恢复（Resume）**：从挂起点继续执行
- **调度主体**：**用户态程序 / 运行时**（非操作系统内核）
#### 虚拟线程
- **身份**：`java.lang.Thread` 的实例，API 完全兼容传统线程。
- **归属**：由 **JVM 管理调度**（用户态），**不直接绑定 OS 内核线程**。
- **模型**：**M:N 调度**—— 大量虚拟线程（M）复用少量平台线程（N，称为载体线程 Carrier Thread）。
- **本质**：由**JVM管理的、轻量级的用户态线程实现**，它通过将大量的虚拟线程（M）映射到少量的操作系统线程（N）上运行，从而改变了传统Java线程一对一映射操作系统的模式
- **核心原理**
1. 载体线程池
    - JVM 用 `ForkJoinPool` 作为调度器，默认载体线程数 = CPU 核心数。
2. 挂载 / 卸载（Mount/Unmount）
    - 虚拟线程运行时 → 挂载到某个载体线程执行。
    - 遇到 **阻塞操作**（`sleep`、I/O 读 / 写、等待锁、JDBC 查询）：
        - JVM 保存当前执行快照（`Continuation`）。
        - 虚拟线程从载体线程**卸载**（挂起）。
        - 载体线程立即执行**另一个就绪虚拟线程**。
    - I/O 完成 → JVM 唤醒虚拟线程，重新挂载到空闲载体线程继续执行，全程没有等待操作。
	- **效果**：一个载体线程可同时 “服务” 成百上千虚拟线程，CPU 几乎无 空闲
- **为什么并发更快**
	1. 虚拟线程**创建开销极小、无栈内存抢占**
	2. 阻塞自动切换，**CPU 执行时间被极致压榨**
	3. 不再依赖调大线程池、不再卡线程数上限
- **缺点**
	1. **不适合 CPU 密集型**：长时间计算会霸占载体线程，导致其他虚拟线程饥饿。
	2. **慎用 `ThreadLocal`**：
		- 百万虚拟线程 → 百万份 `ThreadLocal`，**内存爆炸**。
		- 替代：`ScopedValue`（JDK 20+）。
	3. **`synchronized` 块问题（伪阻塞）**
		- 虚拟线程内持有 `synchronized` 锁时阻塞 → **不会释放载体线程**（称为 “pinning”）。
		- 替代：`ReentrantLock`。
	4. **不能池化虚拟线程**
	    - 虚拟线程**创建极便宜**，池化反而降低性能、增加复杂度。
	5. **本地方法（JNI）阻塞**
	    - JNI 内阻塞 → 同样无法卸载，会卡住载体线程。
- **构建器模式创建**
```java
// 创建但先不启动（unstarted），或者直接.start()
Thread thread = Thread.ofVirtual()
    .name("my-virtual-thread-1")          // 起个名字，便于调试
    .uncaughtExceptionHandler((t, e) -> { // 设置异常处理
        System.out.println("线程 " + t + " 挂了: " + e);
    })
    .start(() -> {
        // 执行任务
    });
```

> [!NOTE] ScopedValue 是什么
> >**ScopedValue（作用域值）** 是 Java 21（预览）→ Java 25（正式） 推出的、替代 / 补充 ThreadLocal 的轻量级、不可变、作用域绑定的线程内上下文传递机制，专为虚拟线程设计。
> 一句话：ThreadLocal 是 “线程长期变量”，ScopedValue 是 “代码块临时隐式参数”。
> 
> #### 二、核心设计目标
> >解决 ThreadLocal 在虚拟线程 + 高并发下的三大痛点：
> 
> 1. 内存泄漏：ThreadLocal 需手动 `remove()`，忘删易泄漏；
> 2. 可变不安全：任意代码可 `set()` 篡改值；
> 3. 虚拟线程性能差：每个虚拟线程都要复制 ThreadLocal 副本，开销爆炸。
> 
> 
> #### 三、核心特性（和 ThreadLocal 对比）
> 
> | 特性         | ScopedValue              | ThreadLocal                     |
> | ---------- | ------------------------ | ------------------------------- |
> | *可变性*    | *不可变*：绑定后只读，无 `set()`  | 可变：可随时 `set/get/remove`         |
> | *生命周期*   | *作用域绑定*：`run()` 结束自动销毁 | 线程绑定：线程不销毁就一直存在                 |
> | *内存泄漏*   | *无*：自动清理，无需手动 remove   | 有：复用线程极易泄漏                      |
> | *虚拟线程友好* | *极高*：栈帧存储，无哈希表开销       | 差：每个虚拟线程都要复制                    |
> | *父子线程传递* | *结构化并发自动继承*（不复制）       | 需手动 `InheritableThreadLocal` 复制 |
> | *访问速度*   | 约 *3ns / 次*            | 约 *15ns / 次*                  |
> #### 四、关键原理：怎么做到 “作用域自动清理”
> - 存储位置：不在线程哈希表，而在当前栈帧；
> - 绑定时机：`run()` 时压栈绑定；
> - 解绑时机：`run()` 返回时弹栈自动清理，JVM 强保障（哪怕 OOM / 栈溢出）；
> - 不可变：只有 `get()`，无 `set()`，绑定后只读。
> 
> #### 五、父子线程（虚拟线程）传递
> >配合 结构化并发（StructuredTaskScope）
> - 父线程绑定的 ScopedValue，子虚拟线程自动继承
> - 不复制，共享引用，零开销
> - 子线程不能修改，保证安全
> 
> #### 六、典型使用场景
> 1. 请求上下文传递（用户 ID、RequestID、租户 ID）
> 2. 虚拟线程环境：高并发、海量线程场景
> 3. 替代 ThreadLocal：日志链路追踪、权限上下文
> 4. 隐式参数传递：避免层层传参污染方法签名

#### start和run区别
- start：代表启用了一个新线程，将该线程由new状态变为runnable状态，最终会调用线程的run方法
- run：直接调用的话和普通方法一样，没有启用新线程
#### sleep和wait的区别
- 共同点 wait() ，wait(long) 和 sleep(long) 的效果都是让当前线程暂时放弃 CPU 的使⽤权，进⼊阻塞状态 
- 不同点 
	- ⽅法归属不同：sleep(long) 是 Thread 的静态⽅法，⽽ wait()，wait(long) 都是 Object 的成员⽅法，每个对象都有 
	- 醒来时机不同：执⾏ sleep(long) 和 wait(long) 的线程都会在等待相应毫秒后醒来 wait(long) 和 wait() 还可以被 notify 唤醒，wait() 如果不唤醒就⼀直等下去 
	- **锁特性不同：** 
		- wait ⽅法的调⽤必须先获取 wait 对象的锁，⽽ sleep 则⽆此限制
		- wait ⽅法执⾏后会释放对象锁，允许其它线程获得该对象锁（我放弃 cpu，但你们还可以⽤） 
		- ⽽ sleep 如果在 synchronized 代码块中执⾏，并不会释放对象原本持有的对象锁（我放弃 cpu， 你们也⽤不了）
#### 停止线程的方式
- 使用退出标志，使线程正常退出，也就是当run方法完成后线程终止
- 使用stop方法强行终止（不推荐，方法已作废） 
- 使用interrupt方法中断线程
	
#### synchronized工作机制
- 锁机制：当一个线程进入被synchronized修饰的方法或者代码块时，会获取到对象锁。当另外一个线程进入到同步区域时，该线程会被阻塞
- 互斥性：sychronized保证在同一时刻只有一个线程可以执行同步代码块
- 内存可见性：当一个线程修改了共享变量之后，其他线程能看到这个更新的值
- **修饰实例方法**
    锁对象：**当前 this 实例**，即当前实例方法所在的对象，不同实例互不阻塞。
- **修饰静态方法**
    锁对象：**类 Class 对象**，全局唯一，所有实例互斥。
- **修饰代码块**
    手动指定锁对象（任意 Object），粒度更细，性能更好。
#### volatile关键字
>轻量级同步关键字，只能修饰实例变量和类变量。
- 核心特性
	- **可见性**：当一个线程修改了volatile变量的值，其他线程能立刻看到这个修改
		- 底层实现：**内存屏障**，写volatile变量时，强制刷新本地缓存到主内存；读volatile变量时，直接从主内存重新加载
	- 禁止指令重排：JVM为了优化性能，可能会对指令执行顺序重排序（例如“先赋值后初始化”变成“先初始化后赋值”），volatile变量会禁止这种重排序
	- 不保证复合操作的原子性：多线程执行复合操作时仍然可能出现线程安全问题
		- 典型场景：`private volatile int count = 0`，当执行count++操作(包括读取-修改-写入散步)时，volatile关键词拦不住并发覆盖操作，可能导致结果小于预期
- 使用场景
	- 状态标记位：标记线程是否需要停止、任务是否完成等
	- 单例模式-双重检查锁：解决指令重排序导致的半初始化对象的问题
	- 多线程读写共享变量（非复合操作）

#### AQS
>Abstract Queued Synchronizer抽象队列同步器，是Java并发包的核心基础框架，是一个抽象类
- 核心思想：用一个int类型的state变量表示同步状态，通过内置的FIFO双向队列管理等待线程，为锁、信号量等同步组件提供统一的底层实现模板
- 核心组件
	- state变量：用`volatile int`修饰，储存同步状态
	- FIFO双向队列：管理等待获取同步状态的线程，队列节点是Node类型
	- 两种获取同步状态的模式
		- 独占模式：同一时刻只有一个线程能获取锁
		- 共享模式：同一时刻多个线程可获取锁
#### CAS
>Compare And Swap,是一种无锁并发编程机制，通过硬件级别的**原子指令**（不会被线程调度器中断），实现多线程环境下的变量更新
- 核心思想：CAS 操作包含 **3 个核心参数**：
	- **内存地址（V）**：要操作的变量在内存中的地址。
	- **预期值（A）**：线程认为变量当前应该有的值。
	- **新值（B）**：线程想要将变量更新成的新值。
- 执行逻辑：
	1. 线程读取内存地址 `V` 中的当前值，与自己持有的**预期值 A** 进行比较。
	2. 如果**相等**（说明变量未被其他线程修改），则将内存值更新为**新值 B**，操作成功。
	3. 如果**不相等**（说明变量已被其他线程修改），则**不做更新**，操作失败。
	4. 操作失败后，线程可以选择将预期值改为当前地址的真实值，再进行**自旋重试**（循环再次尝试 CAS）或放弃操作。
- 缺点：并发冲突时可能出现数据覆盖和并发错乱
    - 解决数据覆盖：加版本号控制，只要有线程开始修改并提交，就版本号加一，新来的CAS发现版本号不匹配，即时值匹配也不进行修改，防止数据覆盖
    - 解决并发错乱：增加一个状态标记位，线程开始执行则把标记位置为true，执行完成后在置回false。或者直接加分布式锁
#### ReentrantLock（可重入锁）
>主要利用CAS+AQS(主要）队列来实现，是**lock**的核心实现类。它支持公平锁和非公平锁,构造方法,接受一个可选的 公平参数（默认非公平锁），当设置为true时，表示公平锁，否则为非公平锁
- 工作流程 
	- 线程来抢锁后使用**CAS的方式修改state**状态，修改状态成功为1，则让 exclusiveOwnerThread属性指向当前线程，获取锁成功
	- 假如修改状态失败，则会**进入双向队列中等待**，head指向双向队列头部，tail指向双向 队列尾部 
	- 当exclusiveOwnerThread**为null**的时候，则会**唤醒**在双向队列中等待的线程
	- 公平锁则体现在按照先后顺序获取锁，非公平体现在不在排队的线程也可以抢锁

- **Lock和Synchronized的区别**

| 特性      | **ReentrantLock**                 | **synchronized**      |
| ------- | --------------------------------- | --------------------- |
| 实现      | JDK 层面，基于 **AQS** 实现              | JVM 层面，**内置关键字**      |
| 可重入     | ✅ 可重入                             | ✅ 可重入                 |
| 公平性     | 支持**公平 / 非公平**可选                  | 仅**非公平**              |
| 抢锁阻塞时中断 | 支持 `lockInterruptibly()`          | ❌ 不支持                 |
| 限时等待    | 支持 `tryLock(timeout)`             | ❌ 不支持                 |
| 条件队列    | 支持**多个 Condition**                | 仅一个 `wait/notify` 队列  |
| 锁释放     | **手动 unlock ()**（必须 finally），否则死锁 | **自动释放**（异常 / 结束自动释放） |
| 性能      | 高并发下更稳定                           | 低竞争不错，高竞争略差           |
| 使用复杂度   | 复杂，需手动加解锁                         | 简单，不易出错               |
#### 线程池 
##### 核心原理：为什么要用线程池？
1. **降低资源消耗**：线程是稀缺资源，重复利用已创建的线程，避免频繁 `new Thread()` 和销毁的开销（线程创建需要分配栈空间、内核态 / 用户态切换）。
2. **提高响应速度**：任务到达时，无需等待线程创建，直接使用池中的空闲线程。
3. **便于线程管理**：统一控制并发数（避免线程过多导致 CPU 上下文切换频繁）、设置任务超时、线程存活时间等。
4. **提供监控能力**：通过线程池的 API 可获取任务执行数、完成数、空闲线程数等状态。

##### 核心类：ThreadPoolExecutor 源码级参数
Java 线程池的核心实现是 `java.util.concurrent.ThreadPoolExecutor`，其构造方法的 7 个参数
```java
public ThreadPoolExecutor(
    int corePoolSize, // 核心线程数
    int maximumPoolSize, // 最大线程数
    long keepAliveTime, // 非核心线程空闲存活时间
    TimeUnit unit, // keepAliveTime 的时间单位
    BlockingQueue<Runnable> workQueue, // 任务阻塞队列
    ThreadFactory threadFactory, // 线程工厂（创建线程的方式，可自定义线程名、优先级）
    RejectedExecutionHandler handler // 拒绝策略
)
```

###### 各参数详解
1. **corePoolSize：核心线程数**
    - 线程池的**常驻线程数**，即使线程空闲也不会被销毁（除非设置 `allowCoreThreadTimeOut(true)`）
    - 任务数 ≤ 核心线程数时，直接创建核心线程执行任务。
    - 具体设置
	    - IO密集型：一般为CPU核心数的两倍，一半阻塞等 IO，一半运行，拉满CPU 利用率
	    - CPU密集型：一般为CPU数 + 1，线程满配 = CPU 核心数，刚好跑满 CPU，无上下文切换浪费
2. **maximumPoolSize：最大线程数**
    - 线程池允许创建的**最大线程总数** = 核心线程数 + 非核心线程数。
    - 当任务队列满了，且任务数 > 核心线程数时，才会创建非核心线程执行任务。
3. **keepAliveTime & unit：非核心线程空闲存活时间**
    - 非核心线程空闲超过该时间，会被销毁，释放资源。
    - 若调用 `allowCoreThreadTimeOut(true)`，核心线程空闲超时也会被销毁。
4. **workQueue：任务阻塞队列**
    - 用于存放**等待执行的任务**，核心线程都在忙时，新任务会进入队列。
    - 面试常考队列类型：
        - `ArrayBlockingQueue`：基于数组的有界队列，必须指定大小，公平 / 非公平策略。
        - `LinkedBlockingQueue`：基于链表的队列，默认大小 `Integer.MAX_VALUE`（无界），`newFixedThreadPool`/`newSingleThreadExecutor` 默认使用。
        - `SynchronousQueue`：**无缓冲队列**，不存储任务，直接一对一传递给线程，`newCachedThreadPool` 默认使用。
        - `PriorityBlockingQueue`：优先级队列，按任务优先级执行。
5. **threadFactory：线程工厂**
    - 用于创建线程，默认是 `Executors.defaultThreadFactory()`，创建的线程属于同一线程组、默认优先级。
    - 可自定义线程工厂，比如给线程命名（方便排查问题）：
```java
ThreadFactory namedThreadFactory = new ThreadFactoryBuilder()
    .setNameFormat("demo-pool-%d").build();
```
6. **handler：拒绝策略**
    - 当**任务队列满 + 线程数达到最大线程数**时，新任务的处理策略，JDK 提供 4 种默认策略

| 拒绝策略                  | 作用                                        | 适用场景            |
| --------------------- | ----------------------------------------- | --------------- |
| `AbortPolicy`（默认）     | 直接抛出 `RejectedExecutionException` 异常，拒绝任务 | 要求任务必须执行，不允许丢失  |
| `CallerRunsPolicy`    | 由**提交任务的线程**自己执行该任务                       | 并发高的场景，减缓任务提交速度 |
| `DiscardPolicy`       | 直接丢弃新任务，不抛异常                              | 允许任务丢失的场景，如日志收集 |
| `DiscardOldestPolicy` | 丢弃队列中**最老的任务**，将新任务加入队列                   | 任务执行顺序不敏感的场景    |

 ##### 线程池工作流程
**核心逻辑：判断核心线程 → 判断队列 → 判断非核心线程 → 执行拒绝策略**
1. 当一个任务提交到线程池：
    - 步骤 1：判断**当前线程数是否小于核心线程数**？
        - 是 → 创建核心线程执行任务。
        - 否 → 步骤 2。
    - 步骤 2：若核心线程已满、判断**任务队列是否已满**？
        - 否 → 将任务加入队列，等待核心线程空闲后执行。
        - 是 → 步骤 3。
    - 步骤 3：判断**当前线程数是否小于最大线程数**？
        - 是 → 创建非核心线程执行任务。
        - 否 → 步骤 4。
    - 步骤 4：执行**拒绝策略**。
2. 补充细节：
    - 非核心线程执行完任务后，空闲时间超过 `keepAliveTime` 会被销毁。
    - 任务队列是**有界队列**时，才能触发创建非核心线程；若使用无界队列（如 `LinkedBlockingQueue` 默认大小），则线程数永远不会超过核心线程数，`maximumPoolSize` 失效。
    

##### JDK 提供的 4 种常用线程池（Executors 工具类）
面试常考 **4 种线程池的特点、适用场景及弊端**，核心是它们都是基于 `ThreadPoolExecutor` 封装的：

| 线程池类型                       | 核心参数                                                                    | 特点                  | 适用场景                      | 弊端                        |
| --------------------------- | ----------------------------------------------------------------------- | ------------------- | ------------------------- | ------------------------- |
| `newFixedThreadPool(n)`     | 核心线程数 = 最大线程数 = n；队列是无界 `LinkedBlockingQueue`                           | 线程数固定，全部是核心线程，不会被销毁 | 任务量稳定、需要长期运行的场景（如服务器后台任务） | 无界队列可能导致任务堆积，OOM          |
| `newSingleThreadExecutor()` | 核心线程数 = 最大线程数 = 1；无界队列                                                  | 单线程串行执行任务，保证任务顺序    | 任务需要按顺序执行的场景（如日志写入）       | 无界队列易 OOM；线程池不可扩展         |
| `newCachedThreadPool()`     | 核心线程数 = 0；最大线程数 = `Integer.MAX_VALUE`；队列是 `SynchronousQueue`；空闲线程存活 60s | 按需创建线程，空闲线程自动销毁，灵活  | 短期、突发、轻量级任务（如临时批量处理）      | 最大线程数过大，高并发下创建大量线程，导致 OOM |
| `newScheduledThreadPool(n)` | 核心线程数 = n；最大线程数 = `Integer.MAX_VALUE`                                   | 支持延迟执行、周期性执行任务      | 定时任务、周期性任务（如心跳检测）         | 最大线程数过大，可能 OOM            |

> [!NOTE]
> 为什么不推荐用 Executors 创建线程池？
> - 阿里巴巴 Java 开发手册明确禁止：因为 `Executors` 提供的线程池**默认使用无界队列**或**最大线程数过大**，高并发下容易导致 **OOM（内存溢出）**。
> - 推荐方式：**手动创建 `ThreadPoolExecutor`**，指定核心参数（尤其是有界队列和合理的拒绝策略），避免资源耗尽。

##### JDK自带线程池的实现
1. 底层本质
JDK 线程池底层核心是**ThreadPoolExecutor**，通过**ctl 原子变量**同时维护**线程池运行状态**和**当前工作线程数量**，用**Worker 内部类**封装工作线程，配合**阻塞队列 + 拒绝策略**实现任务调度与线程复用。

 2. 核心变量 ctl 设计
ctl 是 AtomicInteger，**高 3 位存线程池状态，低 29 位存工作线程数**，通过 CAS 无锁更新，保证并发安全。
线程池有 5 种状态：
- RUNNING：正常运行，接收新任务、处理队列任务
- SHUTDOWN：不接收新任务，继续处理队列剩余任务
- STOP：不接收、不处理，中断正在执行的任务
- TIDYING：任务清空、线程数为 0，准备终止
- TERMINATED：线程池完全终止

3. 线程复用原理
线程池通过**Worker 内部类**封装线程，Worker 启动后会执行`runWorker()`方法，内部是**死循环**：
不断从阻塞队列`getTask()`获取任务执行，线程不会销毁，实现复用

4. Worker 内部类作用
- 继承 AQS 实现轻量锁，控制任务执行时的中断权限；
- 绑定真实线程和首个任务；
- 循环拉取队列任务，完成线程复用。

#### ThreadLocal
>Java 并发包中的核心工具类，核心作用是 **为每个线程创建独立的变量副本**，让线程操作自己的专属变量，避免多线程共享变量的线程安全问题，本质是**空间换时间**的设计思想
##### 底层结构
>每个Thread对象都维护了一个ThreadLocalMap对象
- - `ThreadLocalMap` 是 `ThreadLocal` 的静态内部类，类似一个**自定义 HashMap**，包含了一个Entry数组,Entry数组的**Key 是 `ThreadLocal` 对象的弱引用**，Value是与线程相关的业务数据。
- 当线程通过 `threadLocal.set(value)` 存值时，实际是往当前线程的 `ThreadLocalMap` 中存入 `(ThreadLocal对象, value)` 键值对；
- 当通过 `threadLocal.get()` 取值时，是从当前线程的 `ThreadLocalMap` 中根据 `ThreadLocal` 实例获取对应的 Value。

##### 核心特性
- **线程隔离性**
    - 每个线程只能访问自己的变量副本，不同线程的 `ThreadLocal` 变量互不干扰，天然线程安全。
- **可重入性**
    - 同一个线程在多层函数调用中，多次操作同一个 `ThreadLocal` 变量，访问的是同一个副本，支持线程内的可重入。
- **弱引用与内存泄漏问题**
    - **Key 的弱引用设计**：`ThreadLocalMap` 的 Key 是 `WeakReference<ThreadLocal>`，目的是当 ThreadLocal 对象不再使用时，GC 可以回收它，避免 ThreadLocal 本身的内存泄漏
    - **Value 的强引用风险**：Key 失效后，Value 仍然是强引用，若线程长期存活（如线程池核心线程），Value 无法被 GC 回收，会导致**内存泄漏**。
    - **解决方法**：使用完 `ThreadLocal` 后，必须调用 `remove()` 方法手动移除 Value，断开强引用。

> [!NOTE] ThreadLocal 的 Key 为什么是弱引用？     
> → 为了避免 `ThreadLocal` 实例本身的内存泄漏。如果 Key 是强引用，即使外部没有对 `ThreadLocal`实例 的强引用或者软引用，Map 也会持有 Key，导致 `ThreadLocal` 实例无法被回收，从而导致内存泄漏

> [!NOTE] Value为什么是强引用
> - 只要当前线程没有终止，`Thread` 实例就会存活，其持有的 `ThreadLocalMap` 也会存活，进而 对`Entry`  Value 的强引用就不会断开。保证线程在运行的时候不被GC回收。
> - 但当 `ThreadLocal` 对象本身被回收（Key 变为 null），这条强引用链依然存在，GC 无法回收 Value，这也是 `ThreadLocal` 内存泄漏的根源。

## JVM
>Java平台的核心组件之一，是Java编程语言和运行Java应用程序的底层操作系统直接的一个抽象层
- 作用
	- 字节码解释与执行：源代码(.java)通过编译器编译成字节码(.class)，JVM负责加载这些字节码，这是Java程序跨平台运行的关键
	- 跨平台兼容性：JVM可以将字节码转换为对应平台的机器码，使相同的java程序可以在不同操作系统中运行
	- 内存管理：JVM包含了一个自动的垃圾收集器，用于自动管理和回收不再使用的对象所占用的内存
	- 安全管理
	- 多线程支持
#### 主要组成部分
- **ClassLoader（类加载器）**
	- 类加载器种类（层次结构由上到下）
		1. 启动类加载器(BootStrap ClassLoader)：该类并不继承ClassLoader类，其是由C++编写实现。⽤于加载JAVA_HOME/jre/lib⽬录下的类库。
		2. 扩展类加载器(ExtClassLoader)：该类是ClassLoader的⼦类，主要加载JAVA_HOME/jre/lib/ext⽬录中的类库。
		3. 应⽤类加载器(AppClassLoader)：该类是ClassLoader的⼦类，主要⽤于加载classPath下的类，也就是加载开发者⾃⼰编写的Java类
		4. ⾃定义类加载器：开发者⾃定义类继承ClassLoader，实现⾃定义类加载规则。
	- **双亲委派模型**：如果⼀个类加载器在接到加载类的请求时，它⾸先不会⾃⼰尝试去加载这个类，⽽是把这个请求任务委托给⽗类加载器去完成，依次递归，如果⽗类加载器可以完成类加载任务，就返回成功；只有⽗类加载器⽆法完成此加载任务时，才由下⼀级去加载
	- **优点**
		（1）通过双亲委派机制可以避免某⼀个类被重复加载，当父类已经加载后则无需重复加载，保证唯一性。
		（2）为了安全，保证类库API不会被修改
- **Runtime Data Area（运行时数据区，内存分区）**
>组成部分：堆、方法区、栈、本地方法栈、程序计数器
- **Execution Engine（执行引擎）**
- **Native Method Library（本地库接口）**


> [!NOTE] 如何破坏类加载机制，植入自己重写的类逻辑？
> JVM 做了**硬性禁止**：例如自定义的String类
> **第一层锁**：系统向上委托到Bootstrap加载器后会直接把原生的String类加载出来并返回，不会去加载用户自定义的String类。
> **第二层锁**：用户自定义 `MyClassLoader`，重写 `loadClass()`方法，删除向上委托逻辑，打破双亲委派。但在调用`defineClass()`把字节码转化为Class对象时，JDK底层会做判断：如果类全名以java开头，而又不是Bootstrap加载器加载，直接抛出`SecurityException`异常，拒绝生成类
> 1. 绕过沙箱，使用 **BootStrap 类加载器加载自定义 String**
> 把你写的 `java.lang.String` 编译好，放到 **JVM 启动优先加载路径**，优先覆盖原生 String
启动 JVM 加参数：`-Xbootclasspath/p:你的class文件所在路径`
> 2.如果是自己的包（例如com.test.String，不是java.开头） 自定义 `MyClassLoader`，重写 `loadClass()`，**不执行双亲委派逻辑**，自己直接读取 class 字节码。局部生效，只有自定义类加载器加载出来的才是自己重写的类逻辑

#### 加载的顺序
- **类**
1. **父类 静态变量 / 静态代码块**（谁在前先执行谁）
2. **子类 静态变量 / 静态代码块**
3. **父类 成员变量 / 构造代码块**
4. **父类 构造方法**
5. **子类 成员变量 / 构造代码块**
6. **子类 构造方法**

- **接口**
1. **接口的静态内容不会因为实现类初始化而加载**，只有直接使用接口时才加载
2. **默认方法（default）属于对象，创建对象时才存在**

- **方法、成员变量**
1. 静态变量 / 静态块：类加载就执行
2. 成员变量 / 构造块：new 对象才执行
3. 构造方法：最后执行
4. 普通方法：调用才执行，不调用不执行

#### Java代码的执行过程
1. **将Java源码(.java)编译为字节码(.class)文件**
	- 检查代码语法，生成抽象语法树（AST）
	- 语义分析：检查代码逻辑合理性
	- 将AST转换为字节码指令，生成.class文件
2. **JVM通过类加载器加载字节码文件到内存**
	- 加载：读取.class文件，创建Class对象
	- 链接：检查字节码的合法性，为类变量分配内存并赋默认值，将符号引用转换为直接引用
	- 初始化（懒加载，只在首次使用类时触发）：执行类构造器，为类变量赋初始值，执行静态代码块
3. **字节码执行（两种方式）**
	- 解释执行：逐行解释字节码命令并执行，启动快但执行慢
	- **JIT（即时编译器）编译执行**：
		- JVM将“热点代码”编译为机器码直接交给CPU执行，缓存后复用，大幅提高性能
4. **内存管理**：在内存中划分不同的区域存储数据
5. **垃圾回收**：自动回收无用对象的内存空间
#### JVM的内存结构
1. 线程私有
	- **程序计数器**：当前线程所执行的字节码的指令地址，唯一不会抛出OOM（OutOfMemoryError，内存不足）的区域
	- **虚拟机栈**：管理 Java 方法调用的运行状态，每个方法调用对应一个栈帧
	- **本地方法栈**:为 Native 本地方法服务
2. 线程共享
	- **堆**：存储所有对象实例和数组，是 GC（垃圾回收）的核心区域
	- **元空间**：存储类信息（Class 对象）、静态变量、常量池、方法字节码等
#### 内存溢出（OOM)

| 特性       | 内存泄漏（Memory Leak）                      | 内存溢出（OutOfMemoryError）                                               |
| -------- | -------------------------------------- | -------------------------------------------------------------------- |
| **定义**   | 程序中**无用的对象**被持续引用，无法被 GC 回收，导致内存占用持续升高 | JVM 内存区域（堆、元空间等）被耗尽，无法为新对象分配内存                                       |
| **本质**   | 引用管理不当，对象可达但无用                         | 内存资源不足，无法满足对象分配需求                                                    |
| **表现**   | 程序运行时间越长，内存占用越高，FULL GC 频繁但老年代内存不下降    | 直接抛出 `OutOfMemoryError` 异常，程序崩溃，或FULL GC频繁且每次GC后内存又很快被填满（内存过小或大对象太多） |
| **因果关系** | 长期内存泄漏会**导致**内存溢出                      | 内存溢出可能由内存泄漏引起，也可能由大对象直接导致                                            |
| **示例**   | `static List` 存储大量无用对象、未关闭的 IO 连接 / 线程 | 一次性加载 1000 万条数据到内存、堆内存设置过小                                           |
都可能导致频繁FULL GC
##### 排查流程
1. 运行时监控：通过监控工具实时观察JVM内存状态
2. 生成堆转储文件（Heap Dump），精准定位问题
	- 配置JVM参数，自动生成堆转储文件
	- 使用工具（如JDK自带的VirtualVM）分析堆转储文件，找出占用内存最多的对象、对象的引用，判断是内存泄漏还是溢出
	- 通过日志辅助分析
3. 找到对应的代码，通过阅读上下文的情况，进行修复即可
##### 解决溢出
- **代码层面**
    - 避免静态集合存储大量对象：`static List/Map` 容易导致内存泄漏，尽量使用局部集合或带过期策略的缓存。
    - 及时释放无用对象：将无用对象的引用置为 `null`（尤其大对象），帮助 GC 回收。
    - 使用流式计算：Java 8 Stream 支持惰性求值，减少中间集合的内存占用。
- **JVM 参数层面**（JVM调优）
    - 优先调优新生代：
	    - 新生代设置合理大小（`-Xmn` 一般为堆内存的 1/3~1/2），减少对象进入老年代。
	    - 调整新生代晋升老年代的年龄阈值
    - 选择合适的 GC 收集器：Java 8 用 Parallel GC 提升吞吐量，Java 11+ 用 G1 GC 兼顾吞吐量和停顿时间；超大堆（>16G）可使用 ZGC/Shenandoah GC。
    - 合理扩容堆内存
- **架构层面**
    - 拆分大应用：将内存密集型业务拆分为独立服务，避免单个 JVM 内存压力过大。
    - 引入分布式缓存：将热点数据存入 Redis，减少 JVM 堆内存占用。
#### CPU飙高排查
1. 可以使用top命令查看占用cpu的情况
2. 通过top命令查看后，可以查看是哪⼀个进程占⽤cpu较⾼，记录这个进程id
3. 通过ps 查看当前进程中的线程信息，看看哪个线程的cpu占⽤较⾼
4. ⽤jstack命令打印线程的id，找到这个线程，就可以进⼀步定位问题代码的⾏号

## Java垃圾回收（GC）
>Garbage Collection,是JVM自动回收不再被引用的对象内存的机制，释放堆内存，避免OOM

- **GC Roots 常见对象**
1. 虚拟机栈中局部变量引用的对象
2. 本地方法栈 JNI 引用对象
3. 方法区 / 元空间静态变量、常量引用对象
4. 活跃线程、锁对象等

- **核心前提**：判断对象是否存活
	- 引用计数法：给对象加引用计数器，计数器=0则标记为垃圾（无法解决循环引用）
	- **可达性分析算法**：以“GC Roots”为起点，遍历对象引用链，若对象无任何引用链连接到GC Roots，则标记为垃圾

> [!NOTE] 标记为垃圾后，回收会马上进行吗？
> 并不会马上进⾏，对象中存在⼀个⽅法 finalize 。回收对象前，首先会判断这个对象是否执⾏了 finalize ⽅法，如果这个⽅法还没有被执⾏的话，那么就会先来执行这个⽅法，接着在这个⽅法执行中，可以设置当前这个对象与GC ROOTS产⽣关联，那么这个⽅法执行完成之后，GC会再次判断对象是否可达，如果仍然不可达，则会进行回收，如果可达了，则不会进行回收， finalize ⽅法只会被执行⼀次

#### 垃圾回收算法
1. 标记-清除
	- 逻辑
		- 标记：遍历标记所有可达对象
		- 清除：回收所有未标记对象的内存
	- 实现简单但效率低，且内存碎片化
2. 标记-复制
	- 逻辑：将内存分为两块，当一块用完了
		- 标记：标记可达对象，复制到空闲块
		- 清空原块
	- 无内存碎片且效率高，但是内存利用率低（只用了一半），适用新生代
3. 标记-整理
	- 逻辑
		- 标记可达对象
		- 将可达对象移动到内存的一端并划定边界
		- 清除边界外的内存
	- 无碎片且内存利用率为百分百，但移动对象成本高，适合老年代
4. 分代收集
	- 逻辑：结合上述算法，按对象存活周期将堆分为新生代和老年代
		- 新生代：用标记-复制（存活率低，复制成本低，效率高）
		- 老年代：用标记-清除/标记-整理（存活率高，整理可以避免内存碎片，节省空间）
	- 为JVM默认策略，兼顾效率和内存利用率
#### 垃圾回收器
1.新生代回收器

| 回收器                   | 核心特点                                          | 适用场景                |
| --------------------- | --------------------------------------------- | ------------------- |
| **Serial**            | 单线程回收，回收时暂停所有用户线程（STW），基于标记 - 复制算法。           | 客户端、单核 CPU、小内存      |
| **Parallel New**      | Serial 的多线程版本，其余逻辑一致，以**低延迟优先**，可与老年代 CMS 配合。 | 服务端、多核 CPU 新生代      |
| **Parallel Scavenge** | 多线程回收，目标是 “**高吞吐量**”（用户代码执行时间/ 总时间），支持自适应调节。  | 后台运算、高吞吐量场景（如大数据计算） |

> [!NOTE] STW
> (Stop-The-World）：暂停所有应用程序线程，等待垃圾回收的完成

2. 老年代回收器

| 回收器                            | 核心特点                                                                                                                                     | 适用场景                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| **Serial Old**                 | Serial 的老年代版本，单线程、标记 - 整理算法，STW 时间长。                                                                                                     | 客户端、低性能服务器                        |
| **Parallel Old**               | Parallel Scavenge 的老年代版本，多线程、标记 - 整理算法，追求高吞吐量。                                                                                           | 与 Parallel Scavenge 配合，**高吞吐量**场景 |
| **CMS（Concurrent Mark Sweep）** | 多线程、标记 - 清除算法，目标是 “**低延迟**”：<br><br>1. 初始标记（STW，短）；2. 并发标记（不 STW）；3. 重新标记（STW，短）；4. 并发清除（不 STW）。<br><br>缺陷：1. 内存碎片；2. 占用 CPU 资源；3. 浮动垃圾。 | 低延迟场景（如 Web 服务）                   |

3.全堆回收器

| 回收器                   | 核心特点                                                                                                                         | 适用场景                |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| **G1（Garbage First）** | JDK 9 默认回收器，分代收集 + 区域化堆布局：<br><br>1. 将堆分为多个 Region；2. 优先回收垃圾多的 Region；3. 标记 - 整理算法，无碎片；4. 可设置最大 STW 时间。<br><br>优点：兼顾吞吐量和低延迟。 | 大内存、低延迟场景（如服务器、云原生） |
| **ZGC/Shenandoah**    | JDK 11+ 引入，几乎无 STW（毫秒级），基于标记 - 复制，支持 TB 级内存。                                                                                 | 超高并发、超大内存场景（如分布式系统） |

> [!NOTE] G1的具体回收过程
> 1. **Young GC（新⽣代回收）**：标记 - 复制算法
> - 回收对象：只处理标记为 Eden 区和 Survivor 区的 Region。Survivor区分为From Survivor（存放上一次的存活对象）和To Survivor（初始为空）
> - 算法流程：
> 	- 标记：标记 Eden 区中存活的对象。
> 	- 复制：将存活对象复制到空的To Survivor 区 Region 中，年龄足够的直接晋升到⽼年代 Region 中。若To Survivor区已满，剩余对象直接进入老年代区域
> 	- 清理：直接清空原 Eden 区 的Region和部分From Survivor，当前的To Survivor区域变为下一次的From Survivor区域，已经部分清理的From Survivor区域变为To Survivor
> 特点：基于复制算法，⽆内存碎⽚，停顿时间可控。
> 2. **全局并发标记**
> 	- 初始标记：暂停所有线程（STW），标记 GC Roots 直接关联的对象。
> 	- 并发标记：恢复线程运⾏，遍历对象图，标记所有存活对象。
> 	- 最终标记：暂停所有线程（STW），处理并发标记阶段的漏标对象。
> 	- 筛选回收：计算每个⽼年代 Region 的垃圾⽐例，优先选择垃圾最多的 Region 进⾏回收。
> 3. **Mixed GC（混合回收）**：标记 - 压缩 + 标记 - 复制 结合
> 当⽼年代占⽤的堆空间⽐例达到阈值（默认 45%）时，触发 Mixed GC，同时回收新⽣代的所有Region 和部分⽼年代 Region。
> 4. **Humongous 区回收**：特殊处理
> Humongous 区存储⼤对象，其回收时机和⽼年代⼀致，在 Mixed GC 中处理。若⼤对象不再存活，直接清理对应的 Humongous Region；若存活，则通过压缩算法整理，避免碎⽚化
#### 引用
## 1. 强引用（StrongReference）
**最普通默认的引用**
```
Object obj = new Object();
```

- 特点：只要有强引用指向，**永远不会被 GC 回收**
- 场景：日常代码普通对象赋值
- 回收条件：**手动置为 null** 或引用脱离作用域

## 2. 软引用（SoftReference）
```
SoftReference<Object> sf = new SoftReference<>(new Object());
```

- 特点：内存充足不回收，**内存不够 OOM 前才被 GC 回收**
- 场景：做**缓存**（图片缓存、本地临时缓存）

## 3. 弱引用（WeakReference）
```
WeakReference<Object> wf = new WeakReference<>(new Object());
```

- 特点：**只要触发 GC，立刻被回收**，不管内存够不够
- 场景：`WeakHashMap`、避免内存泄漏（缓存、临时关联对象）

## 4. 虚引用（PhantomReference）
```
PhantomReference<Object> pf = new PhantomReference<>(new Object(), queue);
```

- 特点：**形同虚设**，不能通过引用获取对象，随时可被回收
- 必须配合**引用队列**使用
- 场景：**堆外内存回收、资源释放监控**，底层源码用得多

| 引用类型    | 类                     | GC 回收时机               | 特点                                                               | 典型应用                                   |
| ------- | --------------------- | --------------------- | ---------------------------------------------------------------- | -------------------------------------- |
| **强引用** | 无专门类（默认）              | 永不回收，除非引用断开           | 最普遍的引用，只要强引用存在，对象就不会被 GC 回收                                      | 普通对象赋值（如 `Object obj = new Object()`）  |
| **软引用** | `SoftReference<T>`    | 内存不足时回收（触发 OOM 前）     | 内存充足时不回收，不足时优先回收软引用对象；回收后会把引用加入 `ReferenceQueue`                 | 内存敏感的缓存（如图片缓存、数据缓存）                    |
| **弱引用** | `WeakReference<T>`    | 每次 GC 时都会回收（无论内存是否充足） | 生命周期比软引用更短，GC 扫描到就会回收；回收后加入 `ReferenceQueue`                     | 临时缓存、`ThreadLocal`、`WeakHashMap` 的 Key |
| **虚引用** | `PhantomReference<T>` | 任何时候都可能回收，仅作为回收标记     | 最弱的引用，无法通过虚引用获取对象实例；必须配合 `ReferenceQueue` 使用，唯一作用是跟踪对象被 GC 回收的状态 | 管理堆外内存（如 `DirectByteBuffer` 的内存释放）     |

## Java 内存模型（JMM）
>核心：happens-before原则
- **A 的结果对 B 完全可见**（B 一定能读到 A 写完的最新值）
- **A 在逻辑上一定先于 B 执行**（禁止非法重排序）
