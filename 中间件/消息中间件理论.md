## RabbitMQ
>基于AMQP协议，定位为智能消息代理，是灵活可靠的传统消息队列
#### 工作原理
![[IMG_216.png]]
1. 启动Broker，初始化核心组件
2. 生产者通过RabbitMQ客户端与Broker建立TCP(使用信道传输）连接,创建一个Channel
3. 生产者通过Channel将消息发送到Broker内的交换器，同时指定一个路由键
4. 交换器收到消息后，根据Routing Key匹配的绑定键，选择将消息发送到哪一个队列，如果匹配到多个队列，则复制消息并发送到所有队列
5. 队列储存消息，等待消费者处理
6. 消费者连接队列，获取消息并处理，处理完成后会向RabbitMQ发送确认消息，表示消息已经被成功处理
7. RabbitMQ收到确认消息后将已经处理的消息从队列中删除

> [!NOTE] Broker
> 运行中的RabbitMQ的服务实例，负责接受、储存、路由和转发消息
#### 如何保证消息不丢失？
- 生产者端确认：开启Publisher Confirm模式，等待Broker确认消息，失败时重发或者记录日志
- Broker端消息持久化：将交换机、队列和消息都标记为durable和persistent，防止重启丢失
- 消费者端确认：关闭自动ACK，改为手动确认，业务处理成功后才确认。消费失败时重新入队或者发送到死信队列统一处理

#### 处理消息积压
- 短期应急
	- 增加消费者实例：同一个队列有多个消费者，负载均衡，提升消费能力
	- 消费端限流：设置消费者每次最多预取的消息数，避免消费者一次性拉去过多消息导致OOM
- 长期优化：
	- 队列分片，将一个大队列拆分，每个小队列绑定到同一个交换机，生产者通过不同的Routing Key分流
	- 死信队列：积压且超时的消息自动进入死信队列，由专门的消费服务处理
	- 监控预警：监控队列中的Ready消息数，超过阈值时报警
- 直接用磁盘储存消息

#### 消息重复性问题处理
>重复消费的根本原因是网络延迟或者重试机制（如消费者ACK丢失、Broker重发）
- 核心幂等方案（消费端实现幂等性）
	1. 基于唯一ID + 分布式锁：
		- 消费者端收到消息，从消息头中提取 **业务唯一ID**作为锁的Key
		- 通过Redis尝试获取锁
			- **加锁成功**：说明当前没有其他实例处理这条消息，继续执行业务逻辑
			- **加锁失败**：说明其他实例正在处理/已经处理过，直接丢弃当前消息
		- 执行业务逻辑后，在Redis中**记录消费状态**，防止锁过期后消息被重复处理
		- 业务完成后释放锁
		- 可能的问题
			1. 锁超时,业务未处理完锁已经过期，导致消息仍然被重复消费
			2. 误删锁
			3. redis主从切换导致锁丢失
			4. 锁有性能瓶颈
	2. 消费消息时插入数据到数据库，通过**唯一索引**约束避免重复插入
	3. 基于状态机：业务数据设计状态字段，消费前检查状态，已经处理则跳过
#### 消息顺序问题处理
>RabbitMQ保证单队列内的消息是FIFO，但多个消费者并发消费会打乱顺序
- 核心方案：使用独立的单个队列，且只部署一个消费者实例，消费时按顺序处理
- 进阶方案
	- 生产者将同一业务ID的消息通过Routing Key哈希到同一个队列分片，每个队列分配对应一个消费者，保证同一业务的消费顺序
	- 消息端乱序接受消息后，缓存消息并按序列号排序后再处理
#### 实现高可用
- Broker集群：多节点部署
	- 部署多个RabbitMQ节点，分为磁盘节点和内存节点，多个节点负载均衡
- Queue高可用：镜像队列
	- 将Queue的消息同步到集群中的多个节点（镜像节点），当主节点宕机时，镜像节点自动切换为主节点
#### 延迟队列
>消息发送后不立即消费，等待预设延迟时间到期后才投递到消费者，解决需要超时失效，延时发送的实际业务

- 方案一：TTL + 死信队列
	1. 消息先进入**无消费者**的延迟队列，等待TTL过期
	2. 过期消息成为死信，自动转发到绑定的**死信交换机**
	3. 死信交换机将消息路由到消费队列，由消费者监听消费
- 方案二：使用延迟消息插件
	1. 生产者设置消息头指定延迟时间，将消息发送到 **延迟交换机**
	2. 交换机暂存消息并记录延迟时间
	3. 插件内部定时器到期，交换机将消息路由到目标队列
	4. 消费者消费信息
## Kafka
>高吞吐的分布式流处理平台平台，适用于海量数据持久化与流式处理
![[2502490c855caeceab093c8711fd3621 1.jpg]]
#### 工作原理
- 核心架构

| 角色                           | 功能                                                                                            |
| ---------------------------- | --------------------------------------------------------------------------------------------- |
| **Producer（生产者）**            | 向 Topic 发送消息，支持指定 Partition 策略（哈希 / 轮询 / 自定义）                                                 |
| **Broker（服务节点）**             | Kafka 集群的服务器节点，存储 Topic 分区数据，处理生产 / 消费请求                                                      |
| **Topic（主题）**                | 消息的逻辑分类容器，一个 Topic 可分为多个 Partition                                                            |
| **Partition（分区）**            | Topic 的物理分片，**分区内消息严格有序**，多分区实现并行处理；每个 Partition 有多个副本（Replica）                               |
| **Replica（副本）**              | 分为 Leader 副本和 Follower 副本：<br><br>- Leader：处理读写请求<br><br>- Follower：同步 Leader 数据，Leader 宕机后顶替 |
| **Consumer（消费者）**            | 从 Topic 拉取消息消费，多个消费者组成 **Consumer Group（消费组）**                                                |
| **Consumer Group（消费组）**      | 组内消费者负载均衡消费 Partition（一个 Partition 只能被组内一个消费者消费）；组间可重复消费同一 Topic                              |
| **ZooKeeper（旧版）/ KRaft（新版）** | 管理集群元数据（节点状态、Topic 配置、消费位移），选主 Leader 副本                                                      |
- 工作流程
	1. 生产者根据指定的Partition策略，决定消息发往Topic的哪一个Partition（默认积攒后批量发送，提高吞吐）
	2. Broker的Leader副本接收消息，写入本地日志文件，Follower副本同步数据
	3. 消费者组内选举一个Cooredinator（协调者），分配Partition给消费者（一个分区对应一个消费者）
	4. 消费者主动拉取Leader副本的消息（可批量拉取）
	5. 消费者消费完消息后，提交Offset（消费位移），记录当前消费位置
	6. Kafka按策略保留消息，消费后**不删除消息**，支持重复消费和回溯


> [!NOTE] 生产者发送消息的确认机制
> 通过 `acks` 参数控制消息可靠性：
> 
> - `acks=0`：发送即成功，不等待 Broker 确认（最快，可能丢数）
> 
> - `acks=1`：Leader 写入成功即返回确认（默认，Leader 宕机可能丢数）
> 
> - `acks=-1/all`：Leader 和所有 ISR（同步副本集）写入成功才返回（最可靠）。

> [!NOTE] ISR
> - 一个**动态维护的集合**，默认包含 Partition 的 Leader 副本 + 所有与 Leader 数据同步的 Follower 副本。
> - 若 Follower 副本同步延迟超过阈值，会被**踢出 ISR**；后续同步追上后，会被**重新加入 ISR**。

#### 如何保证消息不丢失
- 生产者端：设置acks=-1，确保Leader和ISR副本都写入成功；同时开启重试，处理网络抖动导致的发送失败
- Broker端：设置ISR最小副本数，确保至少有N个副本同步
- 消费者端：使用手动提交Offset，消费成功后再提交，避免消费速度过慢导致消息过期被清理

#### 如何保证消费顺序
>Kafka默认不保证消息顺序性
- 核心原则：**单Partiton + 单消费者**
	- 对需要保证顺序的业务，将相关消息发送到**同一个Partiton**
	- 消费组内**只部署一个消费者**消费该Partition，避免一个Partiton被多个消费者消费

#### Kafka为什么吞吐量大
1. 顺序写盘：消息追加写入日志末尾，磁盘IO效率高
2. 批量处理：生产者批量发送、消费者批量拉取
3. 零拷贝：降低CPU和内存开销
4. 分区并行：多Partiton同时读写，并行处理
5. 数据压缩：生产者支持压缩消息，减小网络传输和储存体积

#### 如何实现高可用
1. 副本机制：多副本备份数据，Leader宕机后Follower顶替
2. 集群部署：多Broker节点，避免单点故障
3. 元数据管理
4. 故障自动转移：Broker宕机后，Controller自动选举新的Partition Leader

#### 如何处理消息积压
1. 临时扩容，增加消费者数量（不能超过Partition数量）
2. 优化消费逻辑，避免阻塞
3. 调整拉取参数，提升批量拉取效率
4. 增加Partition数量

#### 如何处理重复消费
- **重复原因**：
    - 消费者自动提交 Offset 后，业务处理失败；
    - 消费者宕机后，Offset 未提交，重新消费时重复拉取；
    - 生产者重试导致消息重复写入。
- **解决方法**：消费端实现**幂等性**：
    - 基于业务唯一 ID（如订单 ID），通过 Redis `setIfAbsent` 或数据库唯一索引去重；
    - 分布式锁：保证同一消息只有一个线程处理。

## RocketMQ
>分布式发布-订阅消息系统
#### 核心架构

|组件|角色与职责|关键特点|
|:--|:--|:--|
|**NameServer**|路由注册中心：Broker 注册、心跳检测、Topic 路由查询|无状态、集群部署、节点间不同步，客户端从任意节点获取路由|
|**Broker**|消息存储与调度核心：接收 Producer 消息、存储、投递给 Consumer|主从架构（Master 读写，Slave 同步 / 读分担），支持多副本高可用|
|**Producer**|消息生产者：创建消息、选队列、发送|支持**同步 / 异步 / 单向 / 事务**发送，自动重试，负载均衡|
|**Consumer**|消息消费者：订阅 Topic、拉取 / 消费消息|支持**集群消费**（一条消息仅被一个消费者处理）/ 广播消费（全量处理）|
#### 工作流程
1. **Broker 注册**：Broker 启动后向所有 NameServer 注册，发送心跳保持存活。
2. **Producer 路由**：Producer 从 NameServer 获取 Topic 路由（对应 MessageQueue 列表）。
3. **消息发送**：Producer 按负载均衡 / 哈希选择 MessageQueue，发送到对应 Broker Master。
4. **Broker 存储**：Broker 写入**CommitLog**（顺序写磁盘），构建**ConsumeQueue**（索引）。
5. **Consumer 消费**：Consumer 获取路由后，从 Broker（Master/Slave）拉取消息，提交 Offset。

## 对比

| 对比维度     | RabbitMQ               | Kafka                        |
| -------- | ---------------------- | ---------------------------- |
| **吞吐量**  | 中等（单机 1 万–10 万 QPS）    | 极高（单机 10 万–百万 QPS）           |
| **延迟**   | 极低（微秒级，<1ms）           | 低（毫秒级，10–100ms）              |
| **消息顺序** | 单队列内有序，多消费者易乱序         | **分区内严格有序**，跨分区无序            |
| **路由能力** | 极强（多 Exchange 类型、灵活绑定） | 简单（按 Topic/Partition/Key 分发） |
| **可靠性**  | 强（事务、Confirm、死信队列、持久化） | 强（多副本、acks 机制、持久化日志）         |
| **消息留存** | 消费后删除，不适合长期存储          | 持久化留存，支持回溯重放                 |
| **扩展性**  | 集群扩展较复杂，依赖镜像队列         | 天然水平扩展，分区线性提升吞吐              |
| **适用场景** | 微服务通信、异步任务、复杂路由、RPC    | 日志收集、实时流处理、数据管道、事件溯源         |
