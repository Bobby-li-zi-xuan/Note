## 基础
- 主键
>唯一标识表中的每一行数据，每个表只能有一个主键
- 外键
>一个表中的字段，其值时另一个表的主键，用于建立两个表之间的关系，维护数据库表之间的数据一致性
	- 外键约束会增加数据库的管理和检查开销，降低性能
- 索引
>数据库表中一列或者多列的值排序后形成的数据结构

#### SQL语句的执行过程
1. 连接阶段：由服务器端的连接器组件负责，在客户端与MySQL服务器之间建立连接
2. 语法解析：数据库解析器检查SQL语法是否正确
3. 语义解析：检查表、字段是否存在，用户是否有权限访问
4. 优化器：基于统计信息选择执行方式（如索引选择、多表连接顺序等）
	- 决定使用哪一个索引的方式：基于索引的选择性、统计信息和查询条件
5. 执行器：按照选择的执行计划调用储存引擎接口读取并处理数据
6. 储存引擎：从磁盘或者缓存读取数据，返回给执行器
7. 将结果打包从网络返回客户端

#####  SQL的JOIN操作
>JOIN操作用于将来自两个或多个表的数据根据某些条件结合在一起
1. **INNER JOIN**：返回两个表中匹配的记录。
2. **LEFT JOIN（或LEFT OUTER JOIN）**：返回左表所有记录以及右表中匹配的记录，右表没有匹配的则用NULL填充。
3. **RIGHT JOIN（或RIGHT OUTER JOIN）**：返回右表所有记录以及左表中匹配的记录，左表没有匹配的则用NULL填充。
4. **FULL JOIN（或FULL OUTER JOIN）**：返回左表和右表中所有记录，匹配的部分显示实际数据，未匹配的部分显示NULL。
5. **CROSS JOIN**：返回两个表的笛卡尔积，即每一行与另一表的每一行进行组合。

#### 数据库的三大范式
##### 第一范式
>数据库表中的每个字段都只能包含***原子值***
##### 第二范式
>在满足1NF的前提下，所有非主属性***完全依赖于主键***（主键为复合值，不能只依赖于主键的一部分）
##### 第三范式
>在满足2NF的前提下，每个非主属性***直接依赖***于主键，而不通过其他非主属性间接依赖
#### 数据库的分片和分区
##### 分片
>分片是将数据水平切分到多个独立的数据库实例或者服务器上，每个分片存储数据库的一个子集
- 应用场景：适用于大规模分布式系统
- 特点：数据分布在不同的物理节点上，每个分片通常有独立的储存和计算资源
##### 分区
>分区是将单个数据库表中的数据按照某种规则分成多个部分，每个部分称为一个分区
- 应用场景：适用于管理和查询大表，提升查询性能和维护效率
- 特点：分区在同一个数据库实例内，相互之间可以共享数据库的资源
#### 数据库连接池
>一种管理数据库连接的技术，当需要建立数据库连接时，会从连接池中获取可用的连接，而不直接创建连接
- 优点：
	- 降低频繁创建和销毁数据库连接带来的开销
	- 通过设置最大连接数量来限制应用程序对数据库系统的并发访问，提高系统稳定性

#### 慢sql排查
1. 开启慢日志查询，定位慢 SQL
2. 用 EXPLAIN 命令分析定位到的慢SQL，判断**是否走索引、是否回表、是否文件排序**等瓶颈。
	- 通过key和key_len检查是否命中索引
	- 通过type字段查看sql是否有进一步优化空间
	- 通过extra判断建议，是否出现回表情况
3. 针对分析结果优化慢 SQL
#### 数据库表的优化（慢sql优化）
1. 数据量大时考虑使用数据库分表：将一张大表拆分为多个子表
2. 建立索引：在经常被查询的列上建立索引
3. 判断索引是否失效
4. 避免使用SELECT *，只查询所需字段
5. 避免定义大事务，大事务会锁表导致sql阻塞
6. 主从分库，读写分离
#### 深度分页优化方法
1. 利用主键分页，查询时 `select * from big_table where id > #{lastid} ordered by id asc limit 20`,用id > 上一页最后一条id代替大offset
2. 覆盖索引优化，将查询字段建立联合索引，避免回表
3. 延迟关联，结合覆盖索引和子查询，先通过覆盖索引只查主键，再根据查到的主键回表查完整数据
`select id from big_table where status = 1 ordered by id limit 10000,20`
- 前面的10000次无用查询走覆盖索引不需要回表，后面需要的20次查询再一个个回表查询
## 锁
#### 全局锁
>锁住整个数据库实例，让库进入只读状态，通常用于全库逻辑备份来保证数据的一致性
- `FLUSH TABLES WITH READ LOCK`(加锁)
- `UNLOCK TABLES`（解锁）
#### 表级锁
>开销小，加锁快，并发低
- 表锁：显示加锁，分读锁和写锁，阻塞整张表读写
- 元数据锁（MDL）：自动加锁，保证DDL（改表结构）和DML（增删改查）不冲突，自动触发
- 意向锁：InnoDB自动加，分为IS（意向共享）和IX（意向排他）用于快速判断表锁和行锁的兼容性
- 自增锁（AUTO-INC）：插入自增列时加，保证自增值唯一连续
#### 行级锁
>仅锁住指定行或间隙，开销大但并发高，InnoDB专属，通过在索引记录上加锁实现
- 记录锁：锁住具体索引行，读加共享锁、改 / 删加排他锁，针对 “已存在的行”
- 间隙锁：锁住索引记录之间的 “间隙”（无数据的区间），**可重复读**隔离级别下防**幻读**，阻塞插入
- 临界锁 (Next-Key)：记录锁 + 间隙锁的组合（InnoDB 默认行锁），锁住 “行 + 前面的间隙”，**彻底防幻读**
- 插入意向锁：插入数据时产生的特殊间隙锁，多个事务在同一间隙插入不冲突的记录时，可并行执行
#### 悲观锁
>假设并发操作会经常发生冲突，因此在数据读取时就上锁，防止其他事务修改或读取数据，直到事务完成
- 实现方式：MySQL `select ... for update` 行锁、排他锁，依赖数据库事务锁机制
- 使用场景
	- 高并发且冲突频繁的环境
	- 需要严格的数据一致性和完整性
- 优点：
	- 逻辑简单，保证数据一致性
	- 避免幻读、脏读、不可重复读等问题
- 缺点
	- 阻塞其他事务，降低并发效率
	- 可能导致死锁
#### 乐观锁
>假设并发冲突不常发生，只在数据更新时检查是否有其他事务修改过数据，如果有冲突则回滚或重试
- 实现方式：基于**版本号 / 时间戳**、CAS 机制
- 使用场景
	- 低并发或冲突少
	- 对性能要求高
- 优点：
	- 并发效率高
	- 无死锁风险
	- 实现简单，不用依赖数据库的锁机制
- 缺点
	- 无法解决幻读问题
	- 重试逻辑增加代码复杂度
## 日志
>事务日志是为了保证事务ACID属性，支持故障恢复，实现数据同步
#### undo log
>回滚日志，InnoDB引擎生成，保证事务的原子性
- 记录内容：记录了事务修改前的数据旧值
- 用途
	- 事务回滚：出错时还原到事务开始前状态
	- MVCC：配合ReadView实现多版本并发控制
#### redo log
>重做日志，InnoDB引擎生成，保证事务的持久性
- 记录内容：数据页的物理修改
- 用途
	- 故障恢复：事务提交后即使没有刷到磁盘，也可以通过该日志重做修改，避免数据丢失
#### bin log
>归档日志，归属于MySQL Server层，用于数据备份和主从控制
- 记录内容：数据库的逻辑操作，仅记录修改操作
- 用途
	- 数据备份恢复：基于日志恢复指定时间点数据
	- 主从同步：从库通过binlog同步主库的数据变更
#### 两阶段提交
>InnoDB引擎层日志和Server层日志协同工作的关键机制，确保事务的**持久性**和**主从数据**的一致性 
- 需要原因：事务提交后，redo log 和 binlog 都要持久化到磁盘，但是这两个是独立的逻辑，可能出现半成功的状态，造成两份日志之间的数据不一致
- 过程：分为prepare阶段和commit阶段。通过内部XA事务将binlog和redolog的提交封装成一个原子的“内部分布式事务”
	- **xa start**：事务执行 SQL 时，隐式启动内部 XA 事务，标记要协调的 “资源”（binlog 和 redo log）；
	- **xa prepare**：对应两阶段提交的「prepare 阶段」→ InnoDB 刷 redo log 到磁盘并标记为 prepare，同时通知 Server 层 “引擎资源已准备好”；
	- **xa commit**：对应两阶段提交的「commit 阶段」→ Server 层刷 binlog 到磁盘后，通知 InnoDB 提交 redo log，最终完成整个内部 XA 事务的提交；
	- **xa rollback**：若任意一步失败（比如 binlog 刷盘失败），内部 XA 事务触发回滚，InnoDB 用 undo log 回滚数据，binlog 放弃刷盘，二者均回到事务前状态。
## 索引

#### 聚簇索引
>**叶子节点直接存储完整的数据行**，索引与数据是**物理上绑定在一起**的，数据的物理存储顺序与索引的逻辑顺序完全一致。
- **一张表只能有 1 个聚集索引**：因为数据的物理存储顺序只能有一种。
- **默认主键就是聚集索引**：
    - 若表定义了 `PRIMARY KEY`，主键就是聚集索引；
    - 若无主键，会选择**唯一非空索引**作为聚集索引；
    - 若无唯一非空索引，InnoDB 会隐式创建一个 6 字节的 `row_id` 作为聚集索引。
- **叶子节点 = 数据页**
- **主键查询效率极高**：无需回表，通过聚集索引直接定位到数据行，3 层 B+ 树最多 3 次 IO。
- **范围查询快**：数据按索引顺序物理存储，范围查询可直接遍历相邻的数据页，利用磁盘顺序读写优势。

#### 非聚簇索引（二级索引）
>**叶子节点不存储完整数据，只存储「索引键 + 聚集索引键（主键）」**，索引与数据是**物理分离**的

- **一张表可以有多个非聚集索引**：如 `idx_name(name)`、`idx_age(age)` 都是非聚集索引。
- **叶子节点 = 索引键 + 主键值**：非聚集索引的 B+ 树叶子节点不存数据，只存索引字段的值和对应的主键值，这是实现**回表查询**的关键。
- **所有非聚集索引都依赖聚集索引**：查询时需要通过非聚集索引找到主键，再通过主键查聚集索引获取完整数据（这个过程叫**回表**）。
- **覆盖索引可避免回表**：若查询的字段都包含在非聚集索引中（如 `SELECT name FROM user WHERE name = '张三'`，索引 `idx_name(name)` 包含 `name`），则无需回表，直接从非聚集索引取数。

#### 索引优化方法
- 前缀索引优化法：使用某个字段中字符串的前几个字符建立索引，从而减小索引字段的大小
- 覆盖索引优化：创建的索引包含查询所需的**所有字段**，只需扫描索引就可以完成查询，无需**回表**
	- 回表：查询需要的列不在索引中，必须通过索引获取数据行的ID，再去查询聚簇索引获取完整数据
- 主键索引设置自增，实现顺序插入，B+树子节点连续，便于查找

#### MySQL使用B+树来作索引
- 磁盘储存压力更小，利用率高：只有非叶子节点储存指针，叶子结点全部储存数据，一页能存更多的索引，总页数更少，树层低
- 查询效率稳定：每个数据查找路径都差不多，一般为三层，查询一次三次IO
- 便于扫库和区间查询：B+树的叶子节点是一个双向链表，是**按索引键有序串联**的，InnoDB 会尽量将**逻辑上相邻的叶子节点**分配到**物理上连续的磁盘块**中。
	- **查询过程**：大幅降低IO成本
		- 找到范围的起始叶子节点（1 次随机 IO）；
		- 通过链表指针，直接读取**物理相邻的下一个磁盘块**（顺序 IO），无需再次寻道；
		- 直到读取完范围所有数据。
#### 索引失效场景
- 使用左或者左右模糊匹配，索引找不到前缀，只能全表扫描
- 违背最左匹配原则
	- 联合索引idx(a,b,c)必须从最左列开始连续匹配，查询时跳过a直接用b或c作为条件，或者中间跳过b直接用a，c都会导致索引失效
	- 解决方法：调整联合索引顺序，将高频过滤条件放在最左侧
- 数据分布不均匀
	- 查询结果集占比过高，优化器判断全表扫描成本更低，主动放弃索引
- 在索引列上使用函数、算术运算或者类型转换
- 隐式类型转换
## 引擎
- MySQL的几个执行引擎
	- **InnoDB**：MySQL默认的事务性存储引擎，支持ACID事务、行级锁定和外键，适用于高并发和需要数据一致性场景
	- MyISAM：非事务性存储引擎，读取速度快，支持表级锁定，适用于读多写少，不需要事务支持的应用
	- Memory：将数据存储在内存中，读写速度极快，但数据易丢失。通常用于创建临时表或者缓存
	- Archive：主要用于存储大量不经常访问归档数据，能对数据进行高度压缩节省储存空间，支持高速的数据插入，但查询性能差，适合大量不经常访问的归档数据
## 事务
#### 四大特性
1. **原子性**（Atomicity）
>**定义**：事务是最小执行单位，**要么全部执行成功，要么全部回滚失败**，不能只做一半。
- 典型场景：转账，A 扣钱、B 加钱。
- 如果 A 扣了钱，中途数据库宕机、程序报错，**必须全部回滚**，不能出现 A 钱少了、B 没到账的中间状态。
- 实现：**undo log 回滚日志**，失败时用 undo log 恢复数据。

2. **一致性**（Consistency）
**定义**：事务执行前后，**数据库完整性约束始终保持不变**，数据从一个合法状态变到另一个合法状态。
- 约束包含：主键唯一、外键、唯一索引、字段约束、业务规则。
- 例子：转账前后，两人账户总金额不变；不能出现负数余额、重复主键、违反外键关联。
- 区别：原子性是**操作不可分**，一致性是**数据合法不变**。

3. **隔离性**（Isolation）
**定义**：多个事务并发执行时，**事务之间互相隔离、互不干扰**，每个事务感觉自己在独占执行。
- 并发会产生三大问题：脏读、不可重复读、幻读。
- 通过**四种隔离级别**控制：读未提交、读已提交、可重复读、串行化。
- InnoDB 靠 **MVCC + 锁机制** 实现隔离性。

4. **持久性**（Durability）
**定义**：事务**一旦提交成功**，修改的数据永久生效，即使服务器断电、宕机、重启，数据也不会丢失。
- 实现：**redo log 重做日志**。
- 提交时先刷 redo log 到磁盘，就算内存数据没来得及落盘，重启后会通过 redo log 恢复数据。

#### 隔离级别
- **读未提交**：一个事务可以读到另外一个事务未提交的数据，可能出现脏读、不可重复读和幻读
	- 实现：直接读取最新的数据
- **读已提交**：一个事务只能读到已经提交的其他事务的数据，可能出现不可重复读和幻读
	- 实现：***MVCC***，每个事务在读取数据时可以看到已提交事务产生的一个Read View，未提交事务不会产生版本，不可见。
- **可重复读**：一个事务在其生命周期内多次执行相同的查询将始终看到相同的数据。MySQL InnoDB引擎默认的隔离级别，可能出现幻读
	- 实现：启动事务时生成一个Read View，整个事务期间都用这个Read View
- **可串行化**：对记录加上读写锁


#### MVCC
多版本并发控制，是 InnoDB 实现 **`READ COMMITTED`（读已提交）** 和 **`REPEATABLE READ`（可重复读，默认隔离级别）** 的关键。InnoDB 为每行数据保存**多个版本**，并通过 `undo log` 维护版本链。
- **读不阻塞写**：读操作读历史版本，不会被写操作的排他锁阻塞。
- **写不阻塞读**：写操作只锁当前版本，不影响读操作读取历史版本。

- **具体实现**：主要依赖于数据库记录中的隐藏字段、undolog和readview
1. **隐藏字段**
	- DB_TRX_ID：记录插入这条记录或最后一次修改该记录的事务ID
	- DB_ROLL_PTR：回滚指针，指向这条记录的上一个版本
	- DB_ROW_ID：隐藏主键，如果表结构没有指定主键，会生成该字段
2. **undo log**：将事务对于记录的修改生成一条记录版本链表，头部是最新的记录，尾部是最早的记录
3. **readview**：是快照读SQL执行时MVCC提取数据的依据，记录并维护当前活跃的事务（未提交的）id，根据**访问规则**来决定事务可以访问哪个版本
> [!NOTE] 当前读和快照读
> - 当前读
> 读取的是记录的**最新版本**，读取时还要保证其他并发事务不能修改当前记录，会对读取的记录加锁。增删改操作和加共享锁和面向更新的select操作都是当前读
> - 快照读
> **简单的select操作**就是快照读，读取的是记录数据的可见版本，有可能是历史数据，不加锁
> 	- **读已提交**：每次select都生成一个快照读，在每次执行快照读时生成readview
> 	- **可重复读**：开启事务后第一个select语句快照读，执行快照读时生成一个readview，后续复用该readView

#### 并行事务会出现的问题
- **脏读**：读到其他事务未提交的数据
- **不可重复读**：前后读取的数据不一致
- **幻读**：前后读取的记录数量不一样(被其他事务的 插入/删除影响)
	- 解决办法：
