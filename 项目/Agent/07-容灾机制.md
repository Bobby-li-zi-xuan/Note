# 容灾机制

本文档只讲各模块的**容灾视角**；机制本身的详细说明见对应模块文档。

---

## 一、runtime 模块容灾

### 1.1 三层终止条件（纵深防御）

| 终止条件 | 配置项 | 作用场景 |
|---------|-------|------------------|
| 最大步数限制 | `agent.runtime.maxSteps=8` | 防止 LLM"生成→报错→重试"死循环 |
| 最大工具调用次数 | `agent.runtime.maxToolCalls=4` | 约束工具链最大深度，防被恶意触发大量网络/IO 工具 |
| 总超时限制 | `agent.runtime.totalTimeoutMs=120000` | 最终兜底，防大文本上下文或挂起请求长期霸占线程 |

触发任一条件都优雅生成带阻断原因的终止摘要，让 LLM 做最终摘要后中断，对用户可见可控。

### 1.2 快照恢复（TurnSnapshot）

**触发与存储**：每轮 LLM 成功返回后 + 每次工具执行完成后，将整个交互状态序列化为 `TurnSnapshot` 原子保存到 Redis（Key `agent:snapshot:{sessionId}`，原地覆盖，TTL 30 分钟）。

**字段**：sessionId、requestId、step、messagesSoFar（序列化消息列表）、selectedModelId、expiresAt、planExecutionSnapshot（Plan 模式下非 null）。**terminationSummary 已从快照移除**——摘要与快照解耦，经 SSE 返回用户；快照只保留断点恢复必需状态。

**恢复流程**：新请求到达 → 检查同 sessionId 活跃快照 → 有则还原消息与步数，TurnLoop 从中断处无缝继续 → 正常完成后清除快照。LLM_FAILURE / CANCELLED 保留快照供断点续连。

**终止摘要策略**：

| 终止原因 | 快照 | 用户看到的回复 |
|---------|------|--------------|
| LLM_FAILURE | 保留 | 固定字符串"[系统提示：LLM 调用失败，已保存当前进度...]"（无法调 LLM），SSE 推送 |
| CANCELLED | 保留 | 无回复（连接已断开） |
| STEP_LIMIT / TOTAL_TIMEOUT | 清除 | 动态摘要（`HistoryTruncator.generateTerminationSummary()` 调 LLM 生成，≤200 字，SSE 推送） |
| COMPLETED（finish） | 清除 | LLM 自己的文本输出 |
| COMPLETED + content=null | 清除 | 动态兜底摘要 |

### 1.3 LLM 调用容灾（LlmInvoker）

| 失败阶段 | 容灾动作 |
|---------|----------|
| 首 token 前 | 可重试（网络/限流类）：`sink.error` 触发声明式 retryWhen 退避链（最多 2 次，200ms 起步，封顶 2s）；400 等参数错误不重试 |
| 首 token 后 | 绝不重试（已计费、重试会新旧内容杂糅），返回空结果由下一轮 step 兜底 |

**超时竞态裁决**：旧 CountDownLatch 在"超时先到/回调先到"存在竞态；新实现用 `Mono.delay`（独立调度器）+ AtomicBoolean CAS 精确裁决先到者置位，不阻塞调用线程。`stepTimeoutMs=30000` 防止 Socket 死锁导致虚拟线程泄漏。

**已交付增强**：声明式超时与重试、全链路取消穿透（SSE → TurnLoop → 工具 → 子任务）、Time Budget 动态分配（工具超时取 `min(policy.timeout, 剩余时间)`）。

**未来方向**：断路器（失败率超阈值熔断）、舱壁隔离（限制并发下游调用）、熔断后 Fallback 兜底回复。

## 二、llm 模块容灾

**模型状态机**：enabled（全量）/ disabled（下线）+ defaultModel 标记（未指定时的默认选择）；canary 灰度为未来方向。改 YAML 即可切换/回滚，无需改代码。

**模型选择容灾**：指定模型 ID → 必须 enabled（否则 null → MODEL_DISABLED）；未指定 → defaultModel。未来增强：模型降级链（首选连续失败自动切备用）。

**工具调用解析容灾**：onCompleteToolCall 实时收集 + onCompleteResponse 兜底检查，兼容不同厂商行为差异，避免工具调用丢失。

## 三、tools 模块容灾

### 3.1 装饰器链隔离

```text
PlanExecutor（顶层路由：显式 Plan / Interactive 恢复 / 隐式 Plan）
    ↓
RetryableToolExecutor（@Primary 注入点）← 容灾核心：重试 + 超时隔离 + 幂等检查
    ↓
DefaultToolExecutor ← 只聚焦参数校验与反射调用
    ↓
ToolInvoker ← 提供工具元数据并阻断无效目标
```

### 3.2 精确重试

三条件同时满足才重试：工具标记 `retryable` + 故障属可重试类型（TIMEOUT/RETRYABLE，参数错误立即中断）+ 未达 `maxAttempts`（默认 3）。退避为线性递增（`baseBackoffMs × attempt`，`backoffMs=200`），防多工具并发对下游雪崩。配置：`agent.tools.retry.maxAttempts=3`、`backoffMs=200`、`agent.tools.defaultTimeoutMs=8000`。

### 3.3 幂等缓存双重存储

| 存储层 | 介质 | 容灾防线 |
|-------|------|---------|
| 主存储 | Redis（TTL=120s） | 跨实例全局防重复 |
| 备用存储 | ConcurrentHashMap（本地内存） | Redis 宕机时提供等效防护（不跨进程共享、不自动过期） |

回退触发：捕获 Redis 连接异常/TimeoutException → warn + 写入本地 Map，定时剔除过期键。**"缓存组件崩溃不等于核心工具瘫痪"**。

### 3.4 细粒度超时隔离

`CompletableFuture.supplyAsync(...).get(timeoutMs)` 把工具执行框定在合理区间，超时抛 TimeoutException 并 `cancel(true)` 中断底层；`agent.tools.execution.defaultTimeoutMs=10000` 提供整链兜底。

**未来方向**：按工具粒度的断路器、不同工具不同线程池（舱壁）、gRPC RAG 工具的 HTTP Fallback。

## 四、memory 模块容灾

**检索降级链**：

```text
L0（静态规则）→ L1（Caffeine）→ L2（pgvector 语义检索，与 L3 同库）→ L3（PostgreSQL 全量存储）
   [语义检索异常] → 降级 findByImportance()（importance DESC, updated_at DESC）
   [最终兜底] → 返回空列表，Turn Loop 继续
```

- **写入容灾**：记忆写入 PostgreSQL 由 `@Transactional` 保障原子性；Ollama embedding 不可用时 `embed()` 返回 null，触发上层降级而非抛异常。
- **L1 一致性**：新记忆入库后立即 `invalidate(userId)` 驱逐缓存，下条对话走最新数据；Caffeine 有 maximumSize 红线 + TTL 防 OOM。
- **单用户故障舱壁**：`MemoryConsolidator` 每小时整理按用户 for 循环 + try-catch——单个用户脏数据异常不影响同批次其他用户。

**核心价值**：Agent 最多暂时"失忆"，绝不会因记忆系统故障让 Turn Loop 抛 500 崩溃。

## 五、subagent 模块容灾

**虚拟线程隔离**：`Executors.newVirtualThreadPerTaskExecutor()` 避免传统线程池海量任务时的栈内存压力（防 OOM）和全员 Waiting 的饥饿（防死锁）。

**全链路取消穿透**：SSE 断连 → Canceller → TurnLoop 每轮检查 break → PlanExecutor → StageScheduler → VirtualThreadSubagentRunner 的 daemon watchdog（50ms 轮询）→ 批量 `future.cancel(true)` 中断未完成子任务，杜绝无效 Token 消耗，取消延迟 ≤ 50ms。

**故障阻截**：AGGREGATE（默认）单任务失败仅记录，其余继续；DEPENDENT 任一失败即 cancelRemaining 短路。

**未来方向**：RateLimiter 防 429、部分结果返回、按依赖自动选执行模式。

---

## 六、api 模块容灾

**SSE 断连重连（"持久化 + 重放"）**：所有事件写入 Redis 流存储（带单调递增 ID）+ 实时推送 SseEmitter；客户端重连带 `Last-Event-Id` 时从该 ID 之后补发漏发事件；重放流已含 FINAL 则补发后主动清理连接，避免客户端无限挂起。

**心跳保活**：每 30s 推空注释（`:

`），绕过 Nginx/LB 的"沉默超时"断连。

**统一异常捕捉（@ControllerAdvice）**：`AgentException` 携错误码精确制导；未捕获异常统一 500。固定结构 `{"error":{"code":"...","message":"脱敏后的摘要"}}`。

**健康检查**：`/actuator/health` 对内放开，`management.endpoint.health.probes.enabled=true`——Redis 失联等关键依赖故障时 Readiness 置为下线，被 K8s 摘出负载池，恢复后自动回 Ready。

**未来方向**：后端服务断路器、请求限流、降级服务（核心不可用时返回简化可用响应）。

---

## 七、security 模块容灾

Filter 顺序（@Order）：TraceFilter(0) → DevModeFilter(1) → SanitizerFilter(2) → JwtAuthFilter（默认最低优先级）。JWT 密钥未配置时跳过所有请求（开发便利）；Token 无效/过期立即 401。DevModeFilter 通过 `X-Dev-UserId` 头指定身份。未来方向：认证失败限流防刷、认证事件审计。

---

## 八、modelregistry 模块容灾

配置示例：`agent.models` 下 modelId / defaultModel / provider / status。

**状态流转**：`disabled → enabled → disabled`。紧急回滚：enabled → disabled 立即生效、无需代码修改。canary 灰度发布尚未实现。

**未来方向**：模型降级链、健康检查集成（连续失败自动标记 disabled）、金丝雀/蓝绿发布策略。

---

## 九、skill 模块容灾

默认技能：code-review（代码审查）、knowledge-search（知识库搜索）。合并策略：会话级 + 请求级去重，请求级优先——部分技能不可用不影响其他技能。Skill（Prompt 片段 + 工具名列表）与 Tool（Java 方法）分离：工具不可用时 Prompt 仍有效，LLM 可选其他工具。未来方向：技能降级回退默认、技能健康检查。

---

## 十、observability 模块容灾

- **全链路追踪**：TraceFilter 生成/提取 trace ID 注入 MDC，日志可定位单请求全过程
- **指标**：`/actuator/prometheus`——LLM 调用耗时、工具重试/超时次数、幂等缓存命中率
- **审计日志**：PostgreSQL 持久化（JSONB details），对话/LLM/工具事件可回溯
- **健康检查**：Redis/PostgreSQL 经 Actuator 暴露

未来方向：指标采样、异步日志写入（失败进队列重试不阻塞主流程）、故障时降级监控频率。

## 面试题整理

1. **系统有哪些容灾机制？** runtime：四重终止保护（取消信号 + 步数/工具调用/总超时三层条件）+ 快照恢复 + Mono 声明式超时/重试 + 全链路取消穿透；llm：模型状态机（enabled/disabled + defaultModel）+ 双重工具调用解析；tools：重试装饰器链 + 幂等缓存双写；memory：pgvector 降级 importance 排序 + embedding 容错；subagent：虚拟线程隔离 + 取消穿透；api：SSE 重放 + 心跳 + 统一异常。
2. **pgvector 语义检索故障时如何保证可用性？** `semanticSearch()` 降级为 `findByImportance()`（importance DESC + updated_at DESC）；Ollama embedding 不可用时 `embed()` 返回 null 触发上层降级；最终返回空列表，Turn Loop 继续，Agent 最多暂时"失忆"。
3. **幂等缓存的 Redis + 本地双重存储如何实现？** 正常走 Redis（TTL 120s）；Redis 不可用时捕获异常自动回退进程内 ConcurrentHashMap；对调用方透明；恢复后新请求自动走回 Redis。
4. **工具执行的重试机制如何设计？** 装饰器模式：三条件（工具可重试 + 错误可重试 + 未达最大次数）同时满足才重试；线性退避；CompletableFuture 超时触发 TIMEOUT；幂等缓存避免重复执行。
5. **SSE 断连重连如何保证消息不丢失？** "持久化 + 重放"：事件同时写 Redis 和 SseEmitter；重连带 Last-Event-Id 从该 ID 后重放；重放流已含 FINAL 说明对话已结束。
6. **子任务并行时如何处理部分失败？** AGGREGATE 单任务失败不影响其他（继续收集）；DEPENDENT 任一失败立即取消其余任务。
7. **模型注册表如何做模型管理与切换？** enabled / disabled + defaultModel：改 YAML 即切换与回滚；canary 灰度为未来方向。
8. **LLM 调用连续失败时如何处理？** LlmInvoker 首 token 前后分策略（前重试后不重试）+ 声明式 retryWhen；TurnLoop 四重保护兜底；全链路 Canceller 穿透杜绝无效 Token 消耗。未来方向：断路器、模型降级链。
