# 总览篇

## 一、项目简介

BobAgent 是一个基于 Spring Boot 3.5 + Java 21 的 AI Agent 服务端：接收自然语言请求，通过多轮 LLM 交互自动决定调用哪些工具、管理上下文与长期记忆、必要时并行执行子任务，结果以 SSE 流式推送返回。采用**模块化单体**架构，按业务领域拆为 10 个模块，模块间通过 ports 接口隔离，保留未来拆微服务的能力。

**为什么模块化单体**：早期阶段业务内聚、一次编译部署、本地调试方便；Java 包物理隔离 + 接口契约让边界清晰；同进程免分布式事务。"单体优先，按需拆分"——每个模块已按端口接口组织，拆分成本低。

**核心技术栈**：Spring Boot 3.5、Java 21 虚拟线程、PostgreSQL + pgvector（会话/记忆/媒体库/角色/审计）、Redis（会话缓存/幂等/快照/播放状态/事件流）、Caffeine 本地缓存、Micrometer + Prometheus、gRPC（RAG 服务）、JWT、SSE、LangChain4j、TestContainers。

### 为什么选用 PostgreSQL

- **向量检索（核心驱动）**：pgvector 支持 vector(1024) + HNSW 索引 + cosine 距离 `<=>`，一套 DB 解决向量检索，替代独立向量数据库
- **JSONB**：替代 MongoDB 文档模型，媒体元数据、审计详情等半结构化数据照常存储
- **ACID 事务**：记忆/会话需要强一致性
- **成熟生态**：Spring Data JPA + Hibernate + Flyway 迁移
- **运维简化**：1 套 PostgreSQL 替代 MongoDB + 向量数据库

vs MongoDB 的代价：失去无模式写入、水平扩展分片、副本集自动故障转移——但本项目是单体、数据量单机可承受，水平扩展非刚需。vs MySQL：pgvector（MySQL 9.0+ 才有 VECTOR 且生态弱）、JSONB（支持 GIN 索引/表达式索引）、TEXT[] 原生数组、HNSW 索引 MySQL 不原生支持。一句话：**需要 pgvector 做语义记忆检索，JSONB 平滑承接原 MongoDB 文档存储，一份数据存所有**。

### 关于 langchain4j：作用与边界

项目深度使用 LangChain4j 的基础能力，业务完全自研。三个不可替代点：① **DDD 防腐层**：统一 `StreamingChatModel` + 消息规约，runtime 完全隔绝厂商差异，切换模型只改 YAML；② **SSE 流式 Chunk 组装**：大模型流式返回的 tool_calls 函数名和深层 JSON 参数按 token 碎片化切分，LangChain4j 的 `StreamingChatResponseHandler` 隐式完成所有 Chunk 累积与参数拼装，手写极易错位崩溃；③ **反射生成 Tool JSON Schema**：`@Tool`/`@P` + `ToolSpecifications.toolSpecificationFrom()` 自动把 Java 方法编译为 LLM 可识别的 JSON Schema，避免手工维护 Schema 的幻觉/非法参数问题。

**为什么不用 Spring AI**：现有 Spring 项目集成 AI 会选 Spring AI（注解配置、学习成本低）；但本项目从 0 搭建，需要精细控制 Agent 编排与记忆，且 LangChain4j 高级功能更丰富。**自研边界**：仅借用 ChatModel 抽象、ChatMessage 结构、@Tool 声明；刻意弃用 AiServices/Agent 链/Memory 等高级组件——多步条件路由、长短记忆过滤、并发容错套用框架链条会失去灵活性。

## 二、整体架构

四层：接入层（api / security / observability）→ 核心编排层（runtime）→ 能力层（llm / tools / subagent）→ 数据层（memory 及基础设施适配器）。

| 模块 | 核心职责 |
|------|---------|
| api | REST Controller、SSE 流式端点、请求响应 DTO、全局异常处理 |
| runtime | 核心编排：Turn Loop、Prompt 组装、工具路由、快照、SSE 事件桥接 |
| modelregistry | YAML 驱动的模型注册表，多模型与默认模型选择 |
| llm | LLM 流式调用适配层、请求构建、超时重试 |
| memory | 分层记忆：L0 静态规则 + L1 Caffeine + L2 PostgreSQL(pgvector 语义检索 + importance 加权) |
| tools | 工具注册、执行、重试与幂等、风险策略 |
| skill | 技能管理（Prompt 片段 + 工具集合） |
| subagent | 子任务规划、虚拟线程并行执行、结果聚合 |
| security | JWT 鉴权、OWASP 清洗、脱敏、开发模式 |
| observability | 全链路追踪、Prometheus 指标、审计日志、健康检查 |

**模块内部分层**：domain（纯 record 领域模型，零框架依赖）→ ports（接口，模块间唯一依赖通道）→ infra（具体实现：DB/Redis/gRPC）→ app（用例编排）→ api（对外接入）。依赖方向"内部依赖外部"，六边形架构风格。

**ID 前缀**：会话 `s_`、请求 `req_`、消息 `m_`、子任务 `st_`。**配置驱动**：核心参数都在 `application.yml` 的 `agent.*` 下，改配置不改代码。

## 三、关键设计亮点

### Turn Loop：同步主体 + 虚拟线程

Turn Loop 是核心循环：向 LLM 发消息列表 → 返回文本或工具调用 → 工具结果追加消息列表 → 下一轮。**刻意采用同步阻塞编码而非 WebFlux 响应式**：Agent 编排本质是有状态顺序决策，响应式链回调割裂、堆栈断裂、调试困难；Java 21 虚拟线程让同步阻塞代价趋近于零（阻塞等待时 JVM 自动卸载 carrier 线程，底层高吞吐、代码线性可读、异常堆栈完整）。

三个终止条件兜底防挂死：最大步数（默认 8，防无限循环）、最大工具调用（默认 4，防工具链无限延伸）、总超时（默认 120s，最终兜底）。

**虚拟线程防爆炸**：不限制虚拟线程创建数量（单个仅几百字节），但"防下游资源爆炸"：① 数据库连接池兜底（HikariCP maximum-pool-size 排队保护存储）；② 大模型 429/限流由工具重试层指数退避消化；③ 业务入口限流委派给外部网关（Nginx/Spring Cloud Gateway），Agent 节点"无状态、来多少接多少"。

### LLM 调用的异步化改造（历史背景）

旧版同步实现的四个问题（取消传播困难、超时控制粗糙、重试逻辑僵化、工具执行缺流水线）通过"同步主体 + 异步嵌入"解决：保持 TurnLoop 同步 while 循环，把 LlmInvoker 与工具调用两个阻塞点异步化。当前状态：`Mono.create()` 桥接流式回调 + `Mono.delay` 声明式超时 + AtomicBoolean CAS 裁决竞态 + `.retryWhen(Retry.backoff(2,200ms).maxBackoff(2s))` 声明式重试；`Canceller`（AtomicBoolean）全链路穿透（SSE 断连 → TurnLoop → 工具 → watchdog 批量 cancel）；工具超时取 `min(policy.timeoutMs(), 剩余 time budget)` 动态分配。

## 四、一次完整对话的流程

**阶段 1 接入（StreamController）**：创建/校验会话 → `SlashCommandParser` 解析 skillIds 并从消息中抹去指令标记 → 初始化 SSE 基础设施（StreamingResponseHandler、SseStageCallback、30s 心跳、Canceller 入 Map）→ `Thread.ofVirtual().start(chatStream)` → 立即返回 `requestId`（`req_` 前缀）。

**阶段 2 上下文准备（AgentService）**：会话校验 + skill 合并 → PromptAssembler 组装 System Prompt（同时触发三层记忆查询：L0 静态规则 → L1 Caffeine 命中即返 → L2 pgvector 语义检索 `(1-cosine) × importance` 加权、情绪匹配 ×1.1，结果回填 L1）→ 快照检测（按 sessionId，有则恢复步数与消息，无则加载 PostgreSQL 历史）→ 历史截断（token 精确估算 + 消息与固定开销合计占比 ≥70% 触发结构化摘要，自适应保留轮数，摘要注入 SystemPrompt）→ 添加用户消息。

**阶段 3 Turn Loop（TurnLoopCoordinator）**：取消/总超时检查 → `LlmInvoker.call().block()`（Mono 桥接 + 超时 + 重试）→ 返回 null 则 LLM_FAILURE（首步失败保存初始快照）→ step++ 保存快照 → 纯文本跨轮累积 → 工具调用检测（finish 优先 break；toolCallsCount++ 超限 → STEP_LIMIT；AiMessage 入历史 → PlanExecutor 执行 → 每 tool_call 注入专属结果 → 保存快照）→ 纯文本空响应触发一次自我修正 → 循环退出后 step 超限覆盖为 STEP_LIMIT（SELF_CORRECT_FALLBACK 不覆盖），COMPLETED 时过滤掉 finish 工具调用。

**阶段 4 收尾**：终止摘要（LLM_FAILURE 固定文案；STEP_LIMIT/TOTAL_TIMEOUT 调 `generateTerminationSummary` 动态生成；COMPLETED+null 兜底）→ assistant 回复加入消息 → persistTurn（用户消息 + 助手消息落库、会话 touch、快照清除——LLM_FAILURE/CANCELLED 保留）→ 工具结果归档（Redis `tool:results:<sessionId>`，TTL 72h、每会话 50 条，供 `recall_tool_result` 追问恢复）→ 记忆提取（P0/P1/P2 三级触发）→ 持久化成功后推送 FINAL 事件。

## 五、DDD
### 什么是 DDD

DDD（Domain-Driven Design，领域驱动设计）是以业务领域为核心建模的软件设计方法论，由 Eric Evans 在《领域驱动设计》中提出。它的核心观点是：**软件复杂性的根源在业务领域本身，因此架构应围绕领域建模，而不是围绕技术分层**。几个关键概念：

- **统一语言（Ubiquitous Language）**：业务人员与开发共用同一套术语，代码中的类名、方法名、注释与业务表述一致，避免"业务说会话、代码说 Session"之类的翻译损耗。
- **限界上下文（Bounded Context）**：每个领域模型只在一个明确边界内有效，按业务边界划分模块，防止一个模型被到处复用导致腐化。
- **领域模型封装业务逻辑**：业务规则放在领域对象 / 领域服务中，而不是散落在通用 Service 里。
- **领域层与技术层分离**：domain 是纯业务模型，不依赖任何框架；数据库、缓存、HTTP 等属于基础设施，通过端口接口（ports）由外部适配（infra）实现。

### 为什么不用传统 Spring MVC 三层，而选 DDD

传统三层是 **Controller（Web）→ Service（业务）→ DAO/Mapper（数据）** 的技术分层，适合 CRUD 型业务，但有两个本质问题：① 业务逻辑与技术代码都堆在 Service 里，容易变成"上帝类"，领域对象退化为只有 getter/setter 的贫血模型；② 分层维度是技术而不是领域，模块边界不清晰，项目变大后 Service 互相依赖，无法独立演进。

本项目业务复杂点在领域，而不是技术：

| 维度 | 传统三层 | 本项目（DDD 实践） |
| --- | --- | --- |
| 分层依据 | 按技术（Controller / Service / DAO） | 按领域边界（14 个模块） |
| 业务逻辑位置 | 散落在 Service 方法，贫血模型 | domain / ports 内聚，纯 record 零框架依赖 |
| 模块间关系 | Service 直接依赖 Service | 只依赖 ports 接口，实现藏在 infra |
| 存储 / 技术替换 | 换存储要改 Service | 只换 infra 适配器，领域层零改动 |
| 测试 | 依赖 Spring 上下文 | domain / ports 纯 Java 单测，infra 可 mock |

落到本项目就是两点核心实践：**限界上下文划分模块**（runtime / memory / tools / subagent 等 14 个模块各对应明确业务边界，模块间只依赖 ports 接口）+ **领域层与技术层分离**（domain 纯 record，infra 在外部实现，如 SnapshotStore → RedisSnapshotStore，替换存储方案领域层零改动）。ports 同时就是未来拆微服务的接口契约。

同时这是有取舍的 DDD：没有教条使用聚合根、领域事件等全部战术模式——对当前单体规模和维护成本，把握住"限界上下文 + 端口适配"这两条收益最大。

## 六、遇到了什么问题。如何解决的

1. **多工具依赖与执行顺序**：早期单工具同步、多工具并行，但大模型返回的多个工具调用间可能有依赖。解决：开发 `create_plan` 工具——LLM 需要时先规划（summary + stages），显式声明依赖，系统按依赖图按序执行。
2. **终止摘要丢失**：terminationSummary 原本存在 TurnSnapshot 里，但 STEP_LIMIT/TOTAL_TIMEOUT 是"正常终止"会清快照，摘要随之丢失，用户无法感知中断原因。解决：摘要与快照解耦——终止摘要作为本轮回复直接经 SSE 返回用户并持久化到 content；TurnSnapshot 移除 terminationSummary 字段并加 `@JsonIgnoreProperties(ignoreUnknown=true)` 兼容旧快照；明确 finish 工具定位（LLM 主动终止的元数据工具，content 只用于持久化不参与回复构建）；新增 COMPLETED+content=null 兜底分支。
3. **历史截断产生"孤儿工具"导致 LLM 报错**：截断时工具调用与工具结果被拆散。解决：① 持久化不存工具调用请求，而是压缩为 `[tool call: xxx]` 文本占位，天然无配对问题；② 快照恢复时对工具结果做哨兵化（内容不变，id/name 覆盖为 restored），让 LLM 当历史背景读取，不报"找不到工具请求"；③ 截断按轮次而非按消息条数，工具调用与执行同轮不拆散。
4. **记忆提取质量**：核心是提示词设计（提取时机、内容、去重、减少冗余）+ 系统摘要质量 + 同步提取触发条件设计，详见 memory 模块。

## 七、面试题整理

1. **Mono 是什么？它的价值是什么？在本项目中的作用是什么？**

   Mono 是 Reactor Core 中的响应式流类型（`Publisher`），表示"最多产生一个值（或错误/完成信号）"的异步任务，可类比为"单元素 Future + 声明式操作符"。与 Future/CompletableFuture 相比，Mono 的核心差别不是"异步"，而是**声明式**：异步任务的组合、错误处理、背压都表达为操作符链，而不是回调嵌套或手写状态机。

   **Mono 的价值**：

   - **声明式组合横切逻辑**：超时、重试、取消、错误恢复这类横切关注点用 `timeout`、`retryWhen`、`onErrorResume`、`doOnCancel` 等操作符直接组合，逻辑分层、可独立测试，不用手写线程、锁和循环。
   - **非阻塞 + 背压**：数据按需拉取，消费多少生产多少，天然防止下游堆积，少量线程即可扛高并发 I/O。
   - **统一的信号语义**：值、错误、完成都建模为流上的信号，错误恢复与链路终止的表达干净一致。
   - **可组合性**：`flatMap`、`zip` 等操作符让异步任务像函数一样组合，比回调嵌套可读，比手写线程池 + Future 更不易出错。
   - **适用边界**：不适合有状态的顺序决策逻辑——操作符链会割裂顺序、堆栈断裂、心智负担重，这也是本项目没有全响应式的原因。

   本项目没有采用 WebFlux 全响应式，而是"同步主体 + 异步嵌入"：Turn Loop 保持同步 while 循环，只在两个最容易失控的阻塞点用 Mono 异步化——LLM 流式调用（声明式超时信号 + 退避重试，只重试 IO 类 / 429 限流 / 首 token 前超时）和工具执行（`fromCallable + retryWhen + onErrorResume` 替代手写 for + Thread.sleep 的重试循环）。调用侧仍是同步的：虚拟线程上 `.block()`，阻塞时让出 carrier 线程，吞吐不损失，编排代码仍线性可读。

   一句话总结：**Mono 的价值是把异步横切逻辑（超时/重试/取消/错误恢复）声明式地表达出来并独立测试；在本项目里它只作为"异步嵌入件"，解决两个阻塞点的工程问题，Agent 编排本身刻意保持同步。**

2. **本项目为什么采用虚拟线程而不是响应式编程？各自有什么优缺点？**

   取舍的本质是“匹配问题形态”：Turn Loop 是**有状态的顺序决策循环**（发消息 → 判结果 → 调工具 → 结果回填 → 下一轮），天然适合同步线性表达；响应式编程则擅长高并发 I/O 流水线。本项目选择“同步主体 + 异步嵌入”——编排层用虚拟线程 + 同步阻塞，仅 LLM 调用和工具执行两个阻塞点用 Mono 做声明式超时/重试/取消。

   **虚拟线程方案**

   - 优点：① 代码线性可读、异常堆栈完整，调试和维护成本低；② 阻塞等待时 JVM 自动卸载 carrier 线程，少量平台线程即可支撑高并发；③ 虚拟线程占用仅几百字节，创建/销毁几乎零成本，天然适合 subagent 的子任务并行；④ 兼容现有同步库与事务边界，没有响应式改造的学习与迁移成本。
   - 代价：① 对 CPU 密集型任务无帮助，纯计算仍占 carrier 线程；② synchronized/原生栈帧可能钉住 carrier 线程（JDK 21 仍有 pinning 场景）；③ 没有内建背压，下游资源爆炸要靠连接池、重试退避、网关限流兜底；④ ThreadLocal 按虚拟线程分配，滥用会带来额外内存。

   **响应式编程（WebFlux/Reactor）方案**

   - 优点：① 极少量 OS 线程扛海量并发，全程无阻塞等待；② 背压内建，天然防止下游堆积；③ 超时/重试/取消等横切逻辑声明式组合、可独立测试；④ 适合无状态、高吞吐的 I/O 流水线。
   - 代价：① 回调链割裂顺序逻辑、堆栈断裂、异常定位困难；② 学习曲线陡峭，心智负担重；③ 事件循环线程上出现任何阻塞调用都会拖垮整个节点；④ ThreadLocal/MDC 上下文传递需要额外机制；⑤ 与 JPA、同步 HTTP 客户端等阻塞生态集成别扭。

   **项目结论**：Agent 编排的核心矛盾不是“并发量”，而是“多步状态决策的正确性与可维护性”；Java 21 虚拟线程把阻塞代价降到趋近于零，因此同步主体是更优解。同时不排斥响应式的长处——两个最容易失控的阻塞点（LLM 流式调用、工具执行重试）用 Mono 收编，超时/重试/取消获得声明式表达；防下游资源爆炸依赖三层兜底：数据库连接池排队、工具重试指数退避、业务入口限流交给网关。
