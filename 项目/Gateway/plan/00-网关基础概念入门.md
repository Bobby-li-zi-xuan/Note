# 网关基础概念入门

> 目的：用最少的技术术语，让你能读懂后面 6 个版本文档。遇到不懂的词，先来这里查。

---

## 1. 什么是 API 网关

**类比：公司前台。**

没有前台的公司：访客要自己找到对应部门，地址混乱，谁都能进，出了事没人记录。
有前台的公司：所有访客先到前台，前台负责登记（**鉴权**）、问清来意并转接（**路由**）、人多时限流（**限流**）、记录来访台账（**日志**）。

API 网关做的事完全一样，只不过接待的是程序请求：

- 统一入口：所有请求只进一个地址。
- 统一规则：鉴权、限流、路由、计费都集中在这里。
- 统一记录：每次请求都有日志和指标，出问题能查。

**一句话**：API 网关是所有请求的“总前台”，后端服务不需要自己处理这些杂事。

---

## 2. 什么是 AI 网关

AI 网关 = 前台 + 背后是一群“大模型供应商”（OpenAI、DeepSeek、通义、Claude……）。

普通网关把请求转给固定的后端；AI 网关要额外决定三件事：

1. **这次用哪家模型**（路由决策：便宜的？快的？质量好的？）
2. **怎么管钱**（Token 计量、成本、配额）
3. **怎么处理流式回复**（大模型是“边说边吐字”的，网关要边收边转给客户端）

### 统一接口是什么

每个供应商的 API 格式都不一样。如果没有网关，客户端要分别对接 OpenAI 格式、Claude 格式、Gemini 格式……

AI 网关的解决办法：**对外只暴露一种格式（OpenAI 兼容格式）**，内部由网关做翻译。

**一句话**：AI 网关是“懂大模型的前台”，客户端只学一种打电话的方式，由它转接给任何一家供应商。

## 3. 核心概念逐个讲

下面每个概念都按“类比 → 一句话原理 → 在哪里出现”来讲。

### 3.1 反向代理

- 类比：门卫把访客带到正确的办公室。
- 原理：客户端不知道后端真实地址，只认网关；网关代替后端接收请求并转发。
- 出现：版本 1 的整个网关就是反向代理。

### 3.2 路由

- 类比：总机按分机号转接电话。
- 原理：根据请求特征（模型名、参数、调用方身份），从多个后端中选一个。
- 出现：版本 1 加权路由 → 版本 2 升级为智能决策引擎。

### 3.3 负载均衡

- 类比：银行几个窗口，尽量让每个窗口工作量差不多。
- 原理：把流量分散到多个实例上，避免一个忙死、一个闲死。
- 加权随机：有些“窗口”效率高（权重高），就多分一些活——像转盘抽奖，权重大的扇区大、被抽中概率高。
- 出现：版本 1。

### 3.4 健康检查

- 类比：定期给餐厅打电话问“还营业吗”，挂“暂停营业”牌的不派单。
- 原理：定时探活，把不健康的实例从候选里剔除。
- 出现：版本 1。

### 3.5 重试（Retry）

- 类比：打电话没接通，挂断再拨一次。
- 原理：失败后按策略再试。
- ⚠️ 关键边界：**对方已经接起来、说了一半，就不能再“重打一次”**（会重复生成内容）。所以重试只在“还没收到第一个字”之前做。
- 出现：版本 3。

### 3.6 超时（Timeout）

- 类比：等太久就挂断。而且分几个阶段分别计时：拨号、等接听、通话总时长、等下一句话。
- 原理：每一层都设时限，任何一个超时就按预案处理。
- 出现：版本 3。

### 3.7 熔断（Circuit Breaker）

- 类比：保险丝/电路跳闸。家里线路频繁出问题，先跳闸保护，过一会儿再试着合闸。
- 原理：某个后端频繁失败时，网关直接快速失败（不再傻等），进入“打开”状态；一段时间后放少量请求试探（半开），成功则恢复。
- 出现：版本 3。

### 3.8 降级（Fallback）

- 类比：主餐厅突然关门，按备选清单换下一家。
- 原理：路由决策时预先生成一份“备胎清单”（降级链），主选失败就按顺序换。
- 出现：版本 3。

### 3.9 冷却（Cooldown）

- 类比：某家店连续差评 N 次 → 临时歇业 30 秒 → 开业后第一个客人是“试吃”，不行再歇。
- 原理：比熔断更轻量的临时禁用机制。
- 出现：版本 3。

### 3.10 限流（Rate Limit）与配额（Quota/Budget）

- 类比：
  - 限流 = 景区限流：**每秒**最多放 N 个人进门。
  - 配额 = 月票额度：**这个月总共**还能玩 N 次 / 花 N 元。
- 原理：一个管“速度”，一个管“总量”，两者分开设计。
- 出现：版本 4。

### 3.11 令牌（Token）与 API Key

- 类比：游乐园会员卡。卡号只在办卡时给你看一次，园方存的是卡号指纹（哈希），丢卡补办也不泄露原卡。
- 原理：令牌是调用方的凭证，可以限制能用哪些模型、花多少钱、哪些 IP 能用、什么时候过期。
- 出现：版本 4。

### 3.12 Token（大模型的“字数”）

- 类比：大模型按“字数”收费，这个“字数”就叫 token。中文大约 1 个字 ≈ 1 token，英文约 4 个字符 ≈ 1 token。
- 原理：网关要统计每次调用用了多少 token 来算钱。
- 流式场景：模型边生成边吐字，网关要**边收边累计**（增量计量），不是等全部结束才数。
- 出现：版本 4。

### 3.13 流式响应（SSE）

- 类比：短视频“边下边播”，而不是等整部下载完再看。
- 原理：大模型一个字一个字生成，网关通过 SSE 把内容分片实时转发给客户端。
- 出现：版本 1（基础透传）、版本 3（完整的流式治理）。

### 3.14 插件 / 流水线（Plugin / Pipeline）

- 类比：机场安检流水线。每个岗位一个职责（验票、查行李、查液体），按顺序执行；以后想加新检查（比如查违禁品）就加一个岗位，不用拆掉整个机场。
- 原理：网关把“鉴权、限流、护栏、缓存”等能力做成可插拔的插件，按顺序挂在请求流程上。
- 出现：版本 2。

### 3.15 控制面 / 数据面

- 类比：控制面是“管理层”（制定规章制度、人员档案），数据面是“一线员工”（按规章接待每一个客人）。
- 原理：管理操作（低频）与请求处理（高频）分离，互不拖累。
- 出现：贯穿所有版本。

### 3.16 配置热更新

- 类比：换规章制度手册不用关店。先把新手册全部印好、检查好，一次性替换；客人手里的旧手册用完即弃。
- 原理：新配置校验通过后原子替换引用，进行中的请求不受影响；校验失败就继续用旧配置。
- 出现：版本 5。

### 3.17 Copy-on-Write（写时复制）

- 类比：换菜单时，先把新菜单完整印好，再一次性换上。客人永远不会拿到“半张新菜单 + 半张旧菜单”。
- 原理：修改配置时先构建完整新对象，全部成功后一次性替换引用。
- 出现：版本 5。

### 3.18 原子操作（Atomic）

- 类比：收银时“查余额 → 扣款”必须一气呵成。如果先查余额、再慢慢扣款，两个客人可能同时花同一笔钱。
- 原理：预算扣减、限流计数用原子操作保证并发下不超扣。
- 出现：版本 4。

### 3.19 可观测性（Observability）

- 类比：监控摄像头 + 值班台账。出了事能回放、能定位。
- 原理：指标（数字）、日志（记录）、链路（一次请求的完整轨迹）三件套。
- 出现：贯穿所有版本，版本 6 完善。

## 4. 一次请求的完整旅程（简化版）

```
客户端
  │  ① 发请求（带令牌）
  ▼
网关：
  ② 验票（令牌鉴权）
  ③ 限流检查（现在放人吗）
  ④ 选模型（路由决策：过滤候选 → 打分 → 选主选）
  ⑤ 转发（执行：连接上游、超时/重试/熔断都在这里）
  ⑥ 计量（记 token、算成本、扣配额）
  │  ⑦ 返回响应（流式则边收边转）
  ▼
模型服务（返回结果）

整个过程中，网关一直在写日志和指标（可观测性）。
```

## 6. 新手学习路径建议

1. 先读本文档（00），再看总计划（01），了解项目分几个版本、每版学什么。
2. 每个版本文档按这个顺序读：**用大白话讲**（先有整体画面）→ **功能模块与实现逻辑**（细节）→ **借鉴的开源实现思路**（看看别人怎么做）→ **演示与验收**（知道做到什么程度算完成）。
3. 动手很重要：版本 1 先跑通，再往后读。只读不跑，概念记不住。
4. 研读开源项目时：先读文档和流程图，再看源码的关键函数，不需要逐行读懂。
5. 遇到不懂的术语，回到本文档第 5 节速查。
