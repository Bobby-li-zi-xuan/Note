# 实现总计划（学习路线版）

> 依据文档：《AI Gateway & Inference Scheduler - 完整项目设计文档 v3.0》
> 阅读顺序：先读《00-网关基础概念入门》，再读本文档，然后按版本 1 → 6 顺序阅读。
> 本文档只描述**实现目标与模块实现逻辑**，不包含具体代码实现。

---

## 1. 这份计划怎么读

这个项目一共分 6 个版本，每个版本是一个**可运行、可演示的里程碑**，也是一个学习主题：

| 版本 | 学习主题 | 你要学会的东西 | 依赖 |
|---|---|---|---|
| 版本 1 | 网关是什么 | 反向代理、路由、加权负载均衡、健康检查、流式透传 | 无 |
| 版本 2 | 怎么让网关可扩展、会“思考” | 插件架构、路由信号、多目标打分、可解释路由 | 版本 1 |
| 版本 3 | 怎么让网关可靠 | 重试、超时、降级、熔断、冷却、流式治理 | 版本 1 |
| 版本 4 | 怎么让网关可治理、可计费 | 持久化、令牌、限流、配额、Token 计量、成本 | 版本 1、3 |
| 版本 5 | 怎么让网关可运维 | 声明式配置、热更新、管理 API、审计 | 版本 2、4 |
| 版本 6 | 进阶玩法（可选） | 语义缓存、安全护栏、协议互转、金丝雀、可观测性 | 版本 3、4 |

依赖关系：

```
版本1 ──► 版本2 ──► 版本5
  │
  └──► 版本3 ──► 版本4 ──► 版本6（可选）
```

版本 6 里的几个能力相互独立，选 1~2 个做就行，不用全做。

## 2. 总体策略：怎么学、怎么做

### 2.1 自研为主，开源项目当“参考书”

我们不把 LiteLLM、New API 等项目的代码搬过来，而是：

1. 看它们**有什么功能**（功能层）；
2. 研究这些功能**是怎么实现的**（实现逻辑层，比如“失败计数 → 冷却 → 恢复”的状态转换）；
3. 把实现逻辑用自己的架构在 Java 里实现。

这样你学到的不是“别人代码长什么样”，而是“这类系统本质上是怎么做出来的”。

### 2.2 研读资料已内嵌，不需要自己翻文档

每个版本文档的**第 5 节“研读资料”**已经直接把需要研读的开源文档内容整理进去了（配置示例、实现机制、关键行为），并附原文链接。阅读方式：

1. 直接读内嵌内容，理解“它做了什么、怎么做的”；
2. 想深入时再点原文链接看完整文档；
3. 不需要先读完全部开源文档再开始动手。

### 2.3 先懂概念，再写代码

每个版本先读概念（00 文档 + 本版“用大白话讲”），再读实现逻辑，最后才动手写代码。计划文档里只有逻辑描述，代码是开发时的事。

### 2.4 每个版本结束都要“能跑、能演示”

版本之间不欠债：每个版本完成时，系统必须可运行，前一版本的功能不回退。

---

### 2.5 版本协作模式（从版本 1 开始执行）

每个版本的详细实施计划会标注【手敲清单】：核心算法与设计思维部分（如 H1~H5）需要你自己默写；其余脚手架代码（配置、DTO、Controller、错误处理、指标、mock 等）由 Codex 实现。手敲部分在代码中留 TODO Hx 标记与说明注释，提示该写哪一段；未完成前调用对应功能会直接报错。

### 2.6 成熟设计优先（重要原则）

设计和实现任何功能 / 代码前，先查以下高 star 项目的成熟做法，尽量复用其设计，不从头发明轮子：

- **LiteLLM**：统一接入、路由插件流水线、重试 / 冷却、预算
- **New API / One API**：渠道、令牌、额度、控制台
- **Portkey**：策略配置（条件路由 / 金丝雀 / 熔断）、护栏
- **Higress**：语义缓存、成本降级、插件热插拔
- **Kong / APISIX**：插件生命周期、管理面、配置热更新
- **Envoy AI Gateway**：限流与配额分离、Token 计量

执行方式：每个版本 / 模块设计前先完成对应“研读任务”（第 4 节与各版本文档第 5 节的内嵌资料），再写设计与代码；实现时保持“自研落地、设计对齐成熟方案”，并在文档中记录借鉴了什么、为什么。

## 3. 通用模块边界（每个模块是干什么的）

项目代码按模块组织，每个版本在这些模块里做增量开发：

| 模块 | 职责（大白话） | 主要版本 |
|---|---|---|
| `api` | 前台：对外接口、统一格式、统一错误 | V1 |
| `decision` | 调度员：选哪个模型，为什么选它 | V1、V2 |
| `execution` | 执行层：真去调用上游，处理失败 | V1、V3 |
| `governance` | 收银台与会员体系：令牌、限流、配额、成本 | V4 |
| `config` | 规章制度手册：配置加载、校验、热更新 | V1、V5 |
| `observability` | 监控与台账：指标、日志、审计 | 全版本 |
| `mock` | 模拟餐厅：模拟延迟、故障、流式的测试服务 | V1 |

## 4. 开源研读任务总览（内容在各版本文档第 5 节）

| 版本 | 研读对象 | 重点研究什么（实现逻辑） |
|---|---|---|
| V1 | LiteLLM 配置结构；One API 渠道模型 | 配置怎么变成“模型候选”；密钥怎么引用；加权随机怎么算 |
| V2 | LiteLLM Router Plugins；Kong 插件阶段；Portkey 策略 | 路由上下文怎么传递；插件怎么收窄候选；signals 怎么共享 |
| V3 | LiteLLM 重试/冷却；New API 渠道失败处理；Portkey 熔断 | 失败计数→禁用→恢复；重试触发条件；熔断状态机 |
| V4 | New API 令牌；Envoy AI Gateway 配额；LiteLLM 预算 | “预检→扣减→结算”；限流与配额分离；软/硬预算 |
| V5 | APISIX Admin API；LiteLLM 配置合并；Kong 管理面 | 独立管理端口与密钥；删除引用保护；配置分层 |
| V6 | Higress ai-cache；Kong 语义护栏；New API 协议互转；Portkey 金丝雀 | 语义缓存判定流程；allow/deny 规则；字段映射思路 |

## 5. 每版本通用验收标准

每个版本完成时，都要满足：

1. **可运行**：一条命令启动全部服务（网关 + mock）。
2. **可演示**：按版本文档里的演示场景操作，能看到预期效果。
3. **可测试**：核心逻辑有单元测试；场景用 mock 服务验证。
4. **可解释**：关键行为（路由选择、降级、熔断、限流）有日志，能说清“发生了什么、为什么”。
5. **可回归**：前一版本功能不回退。

## 6. 风险与对策（提前知道哪些坑）

| 风险 | 大白话 | 对策 |
|---|---|---|
| 流式重试难处理 | 对方已经说了半句话，不能重打 | V3 明确规则：首字节发出前才可重试 |
| 并发扣钱算错 | 两个人同时花同一笔钱 | V4 用原子操作，不用大锁 |
| 重启丢数据 | 关店一天，账本没了 | V4 引入嵌入式 H2 数据库 |
| 范围越做越大烂尾 | 想做的太多做不完 | V6 全部可选，每版本结束都能用 |
| 被质疑“抄开源” | 简历面试讲不清 | 每模块记录设计原因；README 写清借鉴了什么、自研了什么 |
