# 版本 1：统一接入与基础网关（学习版）

## 1. 学习目标

做完这个版本，你能：

- 用自己的话说清 **API 网关 / AI 网关是什么、解决什么问题**（面试第一问）。
- 理解反向代理、路由、加权负载均衡、健康检查、流式透传的原理。
- 亲手跑通“客户端 → 网关 → 多个模型服务”的完整链路。
- 会用 mock 服务模拟延迟、故障，做可重复的实验。

## 3. 用大白话讲：这个版本做了什么

想象你开了一家“AI 外卖平台”：

- 客户只打一个电话（OpenAI 兼容接口），说“我要一段 GPT 风格的回复”。
- 平台（网关）翻电话本（**模型注册中心**），找到几家能做这道菜的店（候选实例）。
- 按每家店的座位数（**权重**）随机选一家下单（加权随机路由）。
- 下单前先确认店还营业（**健康检查**），不营业就换一家（失败切换）。
- 有几家是“模拟餐厅”（mock 服务），可以随便设置上菜速度、翻车概率，方便练习。

版本 1 不做智能调度（版本 2）、不做完整容错体系（版本 3），只把**“能打电话、能转接、能换家”**跑通。

## 4. 功能模块与实现逻辑

### 4.1 对外 API 层（前台话术）

**解决什么问题**：每家供应商的请求/响应格式都不一样，客户端不想学 N 种格式。

**实现逻辑**：

1. 只暴露两个入口：聊天接口（支持 `stream=true` 开流式）与模型列表接口。
2. 请求进来先解析成内部统一结构 `ChatRequest`（与 HTTP 无关），后续模块只认它。
3. 响应统一为 OpenAI 格式；所有异常统一转成标准错误体（`error.type` + `error.message`）。
4. 每个请求分配 `requestId`，贯穿日志与指标（以后排查问题全靠它）。

**为什么这样设计**：内部统一结构意味着“换供应商 = 只改翻译（Connector）”，核心逻辑完全不动。

### 4.2 模型注册中心（电话本）

**解决什么问题**：客户端叫的模型名（别名）和实际供应商模型不是一回事。

**实现逻辑**：

1. 启动时读配置，构建“别名 → 候选实例列表”的映射。
2. 启动校验：重复别名、空候选、引用不存在的渠道、密钥引用缺失 → 直接启动失败并给出可读提示。
3. 提供查询接口：按别名返回候选列表（路由使用 + `/v1/models` 展示使用）。

**为什么这样设计**：把错误全部暴露在启动期，而不是运行到一半才炸。

### 4.3 渠道雏形（供应商档案）

**解决什么问题**：一个供应商账号（地址 + 密钥）要被多个模型复用。

**实现逻辑**：

- 渠道 = provider + baseUrl + 密钥引用 + 模型列表 + 权重 + 启停状态。
- 密钥只存引用（如 `env:OPENAI_API_KEY`），启动时从环境变量读入内存；不落盘、不落日志。
- 每个渠道复用同一个 HTTP 客户端（连接池），不每次请求新建。

**为什么这样设计**：密钥安全（简历可讲）+ 连接复用（性能基本盘）。

### 4.4 加权随机路由（转盘抽奖）

**解决什么问题**：多个实例都能接这个请求，选谁？让流量按权重分散。

**实现逻辑**：

1. 先过滤：健康检查不通过、渠道停用的实例剔除。
2. 把候选按权重在数轴上累加：A 权重 10 → 区间 `[0,10)`，B 权重 5 → 区间 `[10,15)`。
3. 生成 `[0, 总权重)` 的随机数，落在哪个区间就选谁。
4. 执行失败：从剩余候选中再选，最多尝试 N 次（默认 2）；全部失败返回 503。
5. 每次选择和切换都写路由日志（为版本 2 的“可解释路由”打基础）。

**为什么这样设计**：权重累加区间算法简单，改权重无需重建结构；失败切换让版本 1 就有基本可用性。

### 4.5 健康检查（探病号）

**解决什么问题**：别把请求发给已经挂掉的实例。

**实现逻辑**：

1. 定时（默认 5 秒）向每个实例发轻量探活请求。
2. 连续失败 3 次 → 标记不可用；探活成功 → 恢复可用。
3. 状态**异步更新**，路由读的是“状态快照”，而不是请求到来时现查。

**为什么这样设计**：在请求路径上做实时探测会拖慢每个请求；快照 + 异步 = 简单且不阻塞。

### 4.6 mock 模型服务（模拟餐厅）

**解决什么问题**：没有真实大模型也能开发、测试、演示。

**实现逻辑**：

- 每个 mock 实例一个档案：模型名、平均延迟、延迟抖动、故障概率、是否支持流式、限速。
- 提供行为控制接口：运行中可调故障率（演示故障切换）、调延迟（为版本 3 超时演示做准备）。
- `/health` 可按配置返回健康/不健康。
- 聊天接口支持非流式与 SSE 流式；流式逐 chunk 输出并带 `usage` 字段（为版本 4 计量预留）。

**为什么这样设计**：可重复的故障实验环境，简历演示全靠它。

### 4.7 基础日志与指标（台账）

**实现逻辑**：

- 结构化日志：requestId、模型别名、选中实例、耗时、结果（成功/失败/切换）。
- 内存计数器：请求总数、成功/失败数、按实例分组的请求数。

**为什么这样设计**：从第一天就养成“可观测”习惯，后面版本逐步增强。

### 5.1 LiteLLM 的配置结构（config.yaml）

**来源**：[LiteLLM 官方文档 - Overview / configs](https://docs.litellm.ai/docs/proxy/configs)

**文档要点（整理）**：

配置文件分四大区块：

| 区块 | 作用 |
|---|---|
| `model_list` | 支持的模型列表，每条是“对外模型名 → 上游参数” |
| `litellm_settings` | 模块级设置（重试次数、超时、fallback、冷却阈值） |
| `router_settings` | 路由设置（路由策略、超时、Redis 等） |
| `general_settings` | 服务端设置（如 `master_key` 主密钥） |

**核心心智模型（本项目最重要的借鉴）**：`model_name` 是**对外暴露给客户端的名字**，`litellm_params.model` 是**实际发给上游的模型字符串**——两者分离。同一个 `model_name` 可以配多条记录，LiteLLM 会自动对它们做负载均衡。

**原文配置示例（摘录）**：

```yaml
model_list:
  - model_name: gpt-4o          # 客户端传这个名字
    litellm_params:
      model: azure/gpt-4o-eu     # 实际发给上游的模型
      api_base: https://my-endpoint-europe.openai.azure.com/
      api_key: "os.environ/AZURE_API_KEY_EU"   # 从环境变量读密钥
      rpm: 6                     # 该部署每分钟请求上限（用于加权负载均衡）
  - model_name: gpt-4o           # 同名第二条 → 自动负载均衡
    litellm_params:
      model: azure/gpt-4o-ca
      api_base: https://my-endpoint-canada.openai.azure.com/
      api_key: "os.environ/AZURE_API_KEY_CA"
      rpm: 6
```

**密钥引用规则**：`api_key: "os.environ/<变量名>"` 表示运行时执行 `os.getenv("<变量名>")`，配置文件和日志里不出现密钥明文。

**负载均衡的加权思路**：给每个部署设置 `rpm` / `tpm`（每分钟请求数 / Token 数）后，LiteLLM 的 `simple-shuffle` 路由策略会**按 rpm/tpm 加权选择**。支持的策略：`simple-shuffle`、`least-busy`（最少忙碌）、`usage-based-routing`（按用量）、`latency-based-routing`（按延迟）。

**对本项目的启示**：

1. “别名与上游分离”直接对应本项目的 ModelAlias / ModelInstance 设计；
2. 密钥用 `env:` 引用对应本项目渠道的 credentialsRef；
3. “按 rpm 加权”说明权重不一定是拍脑袋的数字，可以用真实容量指标——本项目 V1 先用静态权重，V3 状态系统就绪后可以演进为动态权重。

### 5.2 One API / New API 的渠道模型

**来源**：[New API 特性说明](https://docs.newapi.pro/zh/docs/guide/wiki/basic-concepts/features-introduction)（One API 的 Go 重写版，渠道概念同源）

**文档要点（整理）**：

- 渠道（Channel）是上游供应商接入的单位：一个渠道 = 供应商类型 + 密钥 + BaseURL + 可用的模型 + 分组 + 权重 + 状态。
- 支持**渠道加权随机**：多个渠道服务同一个模型时，按权重分配流量。
- 支持**失败自动重试**：渠道调用失败后自动切换到其他渠道。
- 支持**模型映射**：对外模型名与实际渠道模型名可以不同。
- 令牌（Token）管理：过期时间、额度（超出自动失效）、模型限制、IP 白名单、分组。
- New API 默认用 SQLite 存储，开箱即用（本项目 V4 用 H2，思路相同：嵌入式数据库）。

**对本项目的启示**：

- 渠道实体字段设计直接参考：provider、密钥、BaseURL、模型、权重、状态；
- “加权随机 + 失败切其他渠道”就是本项目 V1 路由逻辑的原型；
- “模型映射”与 LiteLLM 的“别名与上游分离”是同一个思想的两面。

## 6. 演示场景与验收标准

### 演示场景 A：多实例加权路由

启动网关 + 2 个 mock 实例（权重 2:1）。连续调用 20 次，流量比例接近 2:1（允许 10% 以内波动）；`/v1/models` 正确列出模型。

### 演示场景 B：故障切换与健康检查

把实例 A 故障率调为 100%：请求自动切到实例 B（日志可见切换记录）；再把 A 的 `/health` 调为不健康，等一个检查周期后，A 不再出现在路由日志的候选列表。

### 验收标准

1. 一条命令启动网关 + mock。
2. 非流式与流式请求均返回正确 OpenAI 格式。
3. 加权路由比例符合配置。
4. 故障切换、健康检查剔除可稳定复现。
5. 核心逻辑有单元测试（加权随机边界、候选过滤、失败切换）。

## 7. 新手常见问题

**Q1：为什么要做 OpenAI 兼容？**
因为 OpenAI 格式生态最大、工具最多，客户端接入成本最低；格式统一后，加新供应商只写一个 Connector。

**Q2：权重是百分比吗？**
不是。权重是相对比例：A=10、B=5 时，A 拿 2/3 流量。总权重变了比例自动变。

**Q3：健康检查间隔设多少合适？**
学习项目 5 秒足够。太短会给上游增加负担，太长则不灵敏。

**Q4：失败切换和“重试”有什么区别？**
版本 1 的切换是“换一家店再试一次”；版本 3 的重试是完整策略（次数、退避、什么时候能重试的安全边界）。

## 8. 本版本不做什么

- 不做插件框架（版本 2）
- 不做重试退避、熔断、降级链（版本 3，本版本只有简单的“换下一个候选”）
- 不做令牌、限流、计量计费（版本 4）
- 不做配置热更新与管理 API（版本 5）
