# 版本 4：治理与计量（学习版）

## 1. 学习目标

做完这个版本，你能：

- 理解令牌、配额、限流三者分别管什么（凭证 / 总量 / 速度）。
- 理解“限流管速度、配额管总量”为什么分开设计。
- 学会 Token 计量的两种方式（非流式精确、流式增量近似）与误差处理。
- 理解并发下“预检 → 扣减 → 结算”的时序为什么重要（钱不能算错）。

## 3. 用大白话讲：这个版本做了什么

之前的网关像一家“不用记账、随便进”的店。版本 4 装上了**收银台和会员体系**：

- **会员卡（令牌）**：谁在用、能用哪些模型、能花多少、什么时候过期。
- **景区限流（限流）**：每秒最多放 N 个人进门，防止挤爆。
- **月票额度（配额/预算）**：这个月总共能花 N 元，花完就停（或自动换便宜餐厅）。
- **收银机（Token 计量与成本）**：每次消费按“字数（token）”算钱，流式就是边出字边计费。
- **账本（持久化）**：所有数据落盘（H2 数据库），重启不丢账。

版本 4 做完，你的网关就是“能收钱、能记账、能管人”的完整系统——这是简历上“企业级”三个字的底气。

## 4. 功能模块与实现逻辑

### 4.1 持久化基础（账本）

**解决什么问题**：之前配置和状态都在内存，重启全丢。

**实现逻辑**：

- 选型：嵌入式 H2（文件模式），零外部依赖；预留 SQL 方言隔离，以后可换 PostgreSQL。
- 表结构（最小集）：渠道表、令牌表、预算表、用量记录表、审计表（版本 5 用）。
- 启动迁移：建表脚本幂等执行；字段变更走版本化迁移。
- 访问模式：热数据（渠道权重、令牌哈希）缓存到内存；写操作走数据库；用量记录先写内存环形缓冲、定时批量落库，避免每次请求一次磁盘 IO。

**为什么这样设计**：学习项目不引外部数据库（装了就跑不动），但用“缓存 + 批量落库”这个思路本身就很值钱。

### 4.2 渠道管理（供应商档案升级）

**实现逻辑**：

- 渠道 CRUD：创建、修改（权重/优先级/启停）、删除（有历史用量则软删除）。
- 密钥管理：只存引用（`env:XXX`），值不落库、不出现在任何管理接口返回里。
- 渠道级配额：渠道可设 Token/成本上限；超限渠道进入“只降级不主选”状态（仍可作备胎）或完全停用（可配）。
- 变更生效：权重/状态变更通过内存缓存原子替换引用，在途请求不受影响。

### 4.3 令牌管理（会员卡）

**实现逻辑**：

- 创建：生成随机令牌，**明文只在创建响应里出现一次**；库里只存哈希；支持前缀显示（如 `agw_****`）。
- 属性：额度（Token 或成本）、模型范围、IP 白名单、过期时间、启用状态。
- 校验时序（每个请求）：取令牌 → 查缓存 → 校验存在/启用/未过期/IP/模型范围 → 预检额度余额。
- 吊销：删缓存 + 标记库记录失效；已有在途请求不追溯。

**为什么这样设计**：存哈希借鉴了密码存储的思路——数据库泄露也拿不到可用凭证。

### 4.4 双层治理：限流与配额

**实现逻辑**：

- **限流（管速度）**：QPS / RPM / Token 速率，滑动窗口（时间戳环形数组或固定窗口+重叠修正），计数用原子更新；维度：全局、令牌、模型、渠道。
- **配额（管总量）**：按周期（小时/天/月）统计 Token 或成本；作用域：令牌、租户、模型、渠道。
- Token 速率限流的小技巧：请求到达时用**预估输入 Token 占位**，响应结束按实际用量修正（解决流式请求“结束前不知道总量”的问题）。
- 超额行为：限流超了 → 429；预算超了 → 拒绝，或自动降级到低成本模型（预算插件写信号，版本 3 降级链消费）。
- 并发安全：原子操作（内存计数）+ 乐观锁（持久化对账）；禁止用大锁包住整个请求流程。

**为什么这样设计**：借鉴 Envoy AI Gateway——限流和配额是两个不同问题：一个问“现在放不放人”，一个问“这月还有没有钱”。混在一起会互相干扰。

### 4.5 Token 计量与成本（收银机）

**实现逻辑**：

- 非流式：优先取上游 `usage` 字段（prompt/completion/total），缺失时用近似算法。
- 流式：版本 3 的流式代理逐 chunk 触发计量回调，**增量累计** completion tokens；prompt tokens 在发出前按输入长度预估。
- 近似算法（**明确标注误差**）：按字符数与模型家族系数估算（中文约 1 token/字，英文约 4 字符/token）；系数做成配置表，可按模型覆盖。
- 单价表：每模型配置 `priceIn / priceOut`（每 1K tokens）；成本 = `tokenIn × priceIn + tokenOut × priceOut`。
- 用量记录：requestId、令牌、模型、渠道、tokenIn/Out、cost、耗时、结果；异步批量落库。

**为什么这样设计**：精确 tokenizer 在 Java 里要引入外部依赖，学习项目用“近似 + 误差标注”更务实，而且这个取舍本身面试能讲。

### 4.6 预算闭环（花完钱怎么办）

**实现逻辑**：

- 预算实体：作用域 + 限额类型（TOKEN/COST）+ 周期 + 上限 + 已用量 + 预警阈值。
- 扣减时序：请求前预检（余额 > 0）→ 请求结束按实际用量**原子扣减** → 周期切换时重置。
- 预警：用量到阈值（默认 70%/90%）记日志、发事件，不影响请求。
- 超额策略：拒绝（带明确原因）或降级（预算插件把超预算候选降权/剔除，并建议低成本候选）。

## 5. 研读资料（内容已内嵌，直接阅读；链接供深入）

### 5.1 New API 的令牌管理

**来源**：[New API 官方文档 - 令牌管理](https://docs.newapi.pro/zh/docs/guide/feature-guide/user/token)

**文档要点（原文整理）**：

令牌是调用 API 的凭证，每个令牌可独立配置权限范围和配额上限。创建令牌的配置项：

| 配置项 | 原文说明 | 本项目对应 |
|---|---|---|
| 过期时间 | 设置有效期，留空或 -1 表示永不过期 | `ApiToken.expiresAt` |
| 剩余配额 | 限制令牌可消耗的最大配额，**超出后自动失效** | `ApiToken.quota` |
| 无限配额 | 不受配额限制（仍受账户总配额约束） | 可选开关 |
| 模型限制 | 限定令牌只能调用指定模型，留空不限制 | `modelScope` |
| IP 白名单 | 限定允许使用的来源 IP，留空不限制 | `ipWhitelist` |
| 分组 | 指定令牌使用的渠道分组 | 版本 5 配置 |

**两个关键行为（原文明确）**：

1. **Key 只在创建时完整显示一次**：“关闭弹窗后无法再次查看完整 Key”；
2. **删除立即失效**：“确认后该令牌立即失效，无法恢复”。

**对本项目的启示**：令牌字段直接照抄这套最小集合即可；明文只显示一次 + 库中存哈希是我们 4.3 设计的依据。

### 5.2 LiteLLM 的预算（Budgets）

**来源**：[LiteLLM 官方文档 - Budgets, Rate Limits](https://docs.litellm.ai/docs/proxy/users)

**文档要点（原文整理）**：

**全局/密钥预算配置（摘录）**：

```yaml
litellm_settings:
  max_budget: 0        # 预算上限（美元）
  budget_duration: 30d # 重置周期：30s / 30m / 30h / 30d
```

**超出预算的行为（原文）**：请求失败，错误为 `ExceededBudget` / `budget_exceeded`。

**多预算窗口（原文摘录）**：同一个 Key 可以同时设多个周期的预算：

```json
{"budget_limits": [
  {"budget_duration": "24h", "max_budget": 10},
  {"budget_duration": "30d", "max_budget": 100}
]}
```

每个窗口独立统计、独立重置（1h 每小时、24h 每天、7d 每周日、30d 每月 1 号）。用途原文说得很清楚：**日预算挡突发，月预算挡总量**。

**按模型预算 + 预算降级（原文要点）**：可以给 `gpt-4o` 单独设预算（`model_max_budget`）；超出后默认返回 `budget_exceeded`，但 LiteLLM 提供 **Budget Fallbacks**——把请求重新路由到另一个模型而不是拒绝。**这就是本项目“成本降级链”的官方参考实现。**

**软预算（原文提及）**：`soft_budget` 用于预警（不阻断），硬预算 `max_budget` 用于拦截。

**对本项目的启示**：

1. 预算要有周期与自动重置（本项目 Budget.period）；
2. 软/硬两级预算（本项目 70%/90% 预警 + 超额动作）；
3. 预算超了既可以拒绝，也可以降级到低成本模型——两条路都做，用策略配置切换。

### 5.3 Envoy AI Gateway 的 QuotaPolicy（配额策略）

**来源**：[Envoy AI Gateway 官方文档 - Quota Policy](https://aigateway.envoyproxy.io/docs/next/capabilities/traffic/quota-policy/)

**文档要点（原文整理）**：

**QuotaPolicy 与限流的关系（原文）**：

> QuotaPolicy manages total consumption budgets (for example, 100,000 tokens per hour). This is distinct from usage-based rate limiting, which controls request velocity (for example, requests per second).

翻译：配额管“总消耗预算”（如每小时 10 万 token），限流管“请求速度”（如每秒请求数）——**两者分开，这正是本项目 4.4 双层治理的出处**。

**按模型配额配置（原文摘录）**：

```yaml
perModelQuotas:
  - modelName: gpt-4
    quota:
      defaultBucket:
        limit: 10000   # 窗口内最大 token 数
        duration: "1h" # 滑动窗口：1s / 1m / 1h / 1d
```

**成本表达式（原文摘录）**：默认按 `total_tokens` 计费，可用 CEL 表达式给不同 token 类型加权：

```
input_tokens + cached_input_tokens / 10u + output_tokens * 6u
```

含义：缓存输入只算 1/10，输出 token 算 6 倍——因为输出通常更贵。这就是“按实际价格计算配额消耗”的思路。

**按租户分桶（原文摘录）**：通过请求头（如 `x-tenant-id`）给不同租户单独配额；匹配方式支持 `Exact`（精确值）、`Distinct`（每个值独立一桶）、`RegularExpression`。

**Shadow 模式（原文）**：`shadowMode: true` 时只统计、不执行——先灰度验证规则合理，再正式启用。

**超额行为（原文）**：所有相关配额桶都用完 → 后续请求返回 **429 Too Many Requests**。

**对本项目的启示**：

1. 配额按模型维度配置（本项目 Budget 支持模型作用域）；
2. 成本表达式思想：配额可以按“加权成本”而不是裸 token 数计算（本项目单价表直接按价格算成本即可）；
3. 按租户分桶 = 本项目作用域（令牌/租户/模型/渠道）设计来源；
4. shadow 模式很值得做：预算规则上线前先只记录不拦截（可以列入 V4 可选项）。

## 6. 演示场景与验收标准

### 演示场景 A：令牌额度

创建额度 $0.10 的令牌：连续调用高成本模型直到超限——先成功，超限后返回明确错误（或自动降级到低成本模型），用量记录可查。

### 演示场景 B：限流

某令牌 QPS=5：第 6 个并发请求返回 429，错误体含限流原因；窗口结束后计数恢复。

### 演示场景 C：成本降级

配置“高成本模型预算触顶 → 降级到低成本模型”：预算用完后，同一请求自动改走低成本候选（日志显示预算信号与降级事件），调用方无感知。

### 验收标准

1. 重启后渠道、令牌、预算、用量记录不丢失。
2. 流式成本按增量累计，误差率有文档标注（误差 < 15% 达标）。
3. 预算扣减并发下不超扣（压测验证）。
4. 429 / 预算拒绝 / 降级三类行为有日志与指标。
5. 版本 3 功能回归通过。

## 7. 新手常见问题

**Q1：为什么用 H2 而不是 MySQL/PostgreSQL？**
学习项目要“一条命令跑起来”，H2 零安装；同时它的 SQL 与主流数据库兼容，以后换库成本低。简历上可以写“存储层做了 SQL 方言隔离，可平滑迁移到 PostgreSQL”。

**Q2：预检和扣减为什么要分开？**
因为请求开始前不知道实际用量（尤其流式）。只能“先看余额够不够”放行，结束时“按实际算账”。分开之后，中间还要处理“预检通过但请求失败”——失败就不扣钱。

**Q3：流式计量为什么不精确？**
没有官方 Java tokenizer，精确计数要么引第三方库要么自己实现 BPE 分词，复杂度高。近似算法（按字符/语言系数）误差可控，文档里写明误差范围，面试时如实说明就是加分项。

**Q4：并发扣款怎么保证不超扣？**
用原子操作（如内存计数器的 compare-and-set）或数据库乐观锁：扣减前比较当前值，若已被别人扣过就重试/拒绝。关键是不能“先读、再算、后写”三步分开。

## 8. 本版本不做什么
