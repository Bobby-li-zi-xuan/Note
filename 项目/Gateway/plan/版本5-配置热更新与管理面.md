# 版本 5：配置热更新与管理面（学习版）

## 1. 学习目标

做完这个版本，你能：

- 理解“配置即代码”的价值与声明式配置的写法。
- 理解热更新的核心难点：**怎么做到“改了配置但服务不中断、不出现中间状态”**。
- 学会 copy-on-write 思想（面试高频，不止网关用得上）。
- 理解管理面与数据面分离的意义，以及审计日志为什么重要。

---

## 2. 前置知识

- 先读《00-网关基础概念入门》第 3.15~3.17 节（控制面/数据面、配置热更新、Copy-on-Write）。
- 版本 2（插件与策略）与版本 4（渠道、令牌、预算）已完成——本版本管理的就是它们。

---

## 3. 用大白话讲：这个版本做了什么

之前的网关改配置要改文件、重启服务，像“改规章制度要关店一天”。版本 5 做三件事：

1. **规章制度手册（配置文件）**：模型、渠道、策略、插件、限额全部写进一份 `gateway.yaml`，一目了然；印出来之前先检查错别字（Schema 校验），有错就不让开店。
2. **不关店换手册（热更新）**：新手册先全部印好、检查好，然后**一次性替换**；正在用餐的客人（在途请求）继续用旧菜单，不受影响。旧手册留档，能一键回退。
3. **管理办公室（Admin API）+ 值班记录（审计）**：管理操作通过独立的管理接口完成，每个操作都有记录（谁、何时、改了什么）。

版本 5 做完，网关从“开发玩具”变成“可以运维的系统”。

## 4. 功能模块与实现逻辑

### 4.1 配置结构与 Schema（手册格式）

**实现逻辑**：

- 配置内容：模型别名与策略、渠道、令牌初始定义、插件及配置、限流与预算限额。
- Schema 校验：启动时完整校验（结构、类型、引用关系、权重和、字段枚举）；错误输出“文件 + 路径 + 原因”，可读性强。
- 引用校验：模型引用渠道、策略引用权重、插件引用配置项，启动时全部解析；环境变量引用只查“变量名存在”，取值运行时解析。
- 单文件/多文件：默认 `gateway.yaml`，支持 `include` 拆分（渠道、策略分文件），合并后统一校验。

**为什么这样设计**：配置错误在启动时暴露，比运行中爆炸好一万倍；可读的错误信息是运维体验的一部分。

### 4.2 配置服务（ConfigService：换手册流程）

**实现逻辑**：

- 不可变配置对象：加载后配置整体不可变；各模块持有一份“当前配置引用”。
- 热更新五步：解析新配置 → Schema 校验 → 预检（引用完整性、与现有运行对象兼容）→ **原子替换全局引用** → 通知相关模块刷新缓存。
- 原子性保证（copy-on-write）：先构建完整的新运行时对象图，全部成功才替换引用；在途请求继续用旧引用，天然不受影响。
- 版本化：每次生效配置有版本号与变更说明；保留最近 N 版，支持一键回滚（回滚也走完整校验）。
- 失败处理：校验/预检失败时，当前配置保持不变，管理接口返回可读错误。

**为什么这样设计**：热更新的核心不是“能改”，而是“改错了也不出事”。原子替换保证任何时刻系统看到的都是**一份完整的配置**。

### 4.3 热更新与运行对象联动（换手册后各部门怎么知道）

**实现逻辑**：

- 渠道权重/启停变更：重建渠道缓存并原子替换；**不重建 HTTP 连接池**（连接池按渠道 ID 复用，换权重不该断连接）。
- 策略/插件变更：策略管理器与插件注册表重建对应实例；插件实例不可变，替换引用生效。
- 限额变更：预算实体按“作用域+周期”更新上限；**已用量保留**，不因配置更新重置（重置是显式操作）。
- 一致性：通知按依赖顺序下发（渠道 → 策略 → 插件），任何一步失败则整体回滚到旧版本。

### 4.4 Admin API（管理办公室窗口）

**实现逻辑**：

- 接口分组：
  - 渠道：创建、修改、启停、删除（软删）、列表。
  - 令牌：创建（明文只返回一次）、吊销、额度调整、列表。
  - 策略/插件：查询、启停、配置更新（走热更新流程）。
  - 用量：按令牌/模型/渠道/时间聚合查询。
  - 决策日志：按 requestId 或时间范围查路由决策明细（版本 2 的可解释路由在这里变成可查询）。
- 鉴权：Admin API 用**独立管理令牌**（与调用方令牌体系分开），支持 IP 白名单；所有写操作进审计。
- 幂等与校验：写操作校验参数并返回明确错误；删除类操作要求显式确认（如渠道 ID + 名称）。

**为什么这样设计**：管理面与数据面分离——管理操作再频繁也不会影响请求性能；独立令牌防止“能调模型的人能改配置”。

### 4.5 审计日志（值班记录）

**实现逻辑**：

- 记录内容：操作者、操作类型、目标对象、变更前后摘要（新旧配置 diff）、结果、时间。
- 存储：独立审计表（版本 4 持久化扩展）。
- 查询：按操作者/对象/时间过滤。
- 与请求日志分离：请求日志面向调用链路，审计日志面向管理行为，互不混写。

## 5. 研读资料（内容已内嵌，直接阅读；链接供深入）

### 5.1 APISIX 的 Admin API（管理面的成熟范式）

**来源**：[Apache APISIX 官方文档 - Admin API](https://apisix.apache.org/docs/apisix/admin-api/)

**文档要点（原文整理）**：

**独立管理端口与鉴权（原文摘录）**：

```yaml
deployment:
  admin:
    admin_key:
      - name: admin
        key: ${{ADMIN_KEY}}   # 支持环境变量引用
        role: admin
    allow_admin:              # IP 白名单
      - 127.0.0.0/24
    admin_listen:
      ip: 0.0.0.0
      port: 9180              # 管理端口与数据面端口分离
```

调用管理接口时带 `X-API-KEY` 请求头；文档明确要求“修改默认 admin_key 并配置 allow_admin IP 白名单”。

**资源操作语义（原文整理）**：

| 方法 | 语义 | 本项目对应 |
|---|---|---|
| `PUT /apisix/admin/routes/{id}` | 创建/整体更新指定 ID 的资源 | 渠道/策略写操作 |
| `GET /apisix/admin/routes` | 列表（支持分页 `page`/`page_size`、按 `name`/`label`/`uri` 过滤） | 列表查询 |
| `PATCH /apisix/admin/routes/{id}` | 局部修改（数组整体替换；置 null 删除属性） | 局部更新 |
| `DELETE /apisix/admin/routes/{id}` | 删除 | 删除 |

**删除引用保护（原文示例，本项目必须学）**：删除仍被路由引用的 upstream 会被拒绝，返回：

```
can not delete this upstream, route [1] is still using it now
```

只有显式加 `?force=true` 才强制删除。**这就是本项目“删除渠道要先检查是否被模型引用”的参考。**

**热更新机制（原文说明）**：APISIX 的配置写入 etcd（或 standalone 模式下的 apisix.yaml），数据面监听变更后生效——管理操作不影响数据面运行。

**对本项目的启示**：

1. 管理端口/密钥/IP 白名单三者独立于数据面（本项目 Admin API 独立令牌 + IP 白名单）；
2. 删除引用保护 + 显式确认（本项目删除类操作要求确认）；
3. REST 资源风格（`/channels/{id}`、`/tokens/{id}`）。

### 5.2 LiteLLM 的配置加载与合并

**来源**：[LiteLLM 官方文档 - Overview / configs](https://docs.litellm.ai/docs/proxy/configs)

**文档要点（原文整理）**：

- config.yaml 是配置源，包含 `model_list` / `litellm_settings` / `router_settings` / `general_settings`。
- 启动命令：`litellm --config /path/to/config.yaml`；加载成功日志会打印 `Proxy initialized with Config, Set models:`。
- 密钥通过 `os.environ/XXX` 从环境变量解析，配置文件不含明文。
- **配置分层（store_model_in_db 开启时）**：启动先加载 YAML，再用数据库里保存的配置做 **deep merge 覆盖**（DB 值优先）；`model_list` 不做合并——UI/API 新增的模型与 YAML 模型**并列存在**，同名的变成额外部署一起负载均衡。

**对本项目的启示**：

1. 配置校验 + 快速失败（本项目启动校验）；
2. 配置有“来源优先级”（YAML 为基础，管理 API 写入为覆盖）——本项目 V5 可以先只做 YAML 权威，为“DB 覆盖”预留扩展点；
3. 新增模型不影响已有模型（追加而非替换）。

### 5.3 Kong 的声明式配置与管理资源

**来源**：[Kong 官方文档 - Declarative Configuration](https://developer.konghq.com/gateway/latest/production/deployment-topologies/db-less-and-declarative-config/)

**文档要点（整理）**：

- Kong 支持 **dbless（无数据库）模式**：用一份声明式 `kong.yml` 描述全部配置，文件带 `_format_version` 字段，启动时加载。
- 管理资源：`services`、`routes`、`plugins`、`consumers` 等，通过 Admin API 以 REST 风格增删改查。
- 资源通过引用关联（route 引用 service，plugin 挂到 service/route/global），变更即热生效。

**对本项目的启示**：声明式配置（`gateway.yaml`）+ 资源化管理（渠道/令牌/策略/插件都是资源）就是本项目 4.1 与 4.4 的设计蓝本。

## 6. 演示场景与验收标准

### 演示场景 A：热更新

运行中把渠道权重从 A:10 改成 A:1：无需重启，流量比例明显偏向 B；接口返回新版本号。

### 演示场景 B：非法配置防护

提交非法配置（权重和不为 1、引用不存在的渠道）：接口返回可读错误；当前配置继续生效；运行中的请求不受影响。

### 演示场景 C：审计追溯

依次执行“修改权重 → 吊销令牌 → 回滚权重”：审计接口能按时间列出三条操作及变更前后摘要。

### 验收标准

1. 启动时配置校验错误可读、快速失败。
2. 热更新原子生效，在途请求无感知；非法配置不生效。
3. 配置支持版本化与回滚。
4. Admin API 覆盖渠道/令牌/策略/插件/用量/决策日志查询。
5. 管理写操作全部有审计记录；版本 4 功能回归通过。

## 7. 新手常见问题

**Q1：热更新会不会出现“改了一半”的状态？**
不会。因为替换是原子的：先完整构建新配置对象，成功后才一次性换引用。任何时刻，每个模块看到的都是一份完整版本，不存在“渠道是新的、策略是旧的”这种混搭（除非通知失败，那会整体回滚）。

**Q2：校验失败为什么旧配置还能用？**
因为流程是“先校验，后替换”。校验失败 = 根本不进入替换步骤，旧配置引用从未被触碰。这是热更新安全性的根本。

**Q3：管理令牌和调用令牌为什么分开？**
调用令牌是“客人门票”，只能调模型；管理令牌是“经理钥匙”，能改配置、吊销门票。混在一起意味着任何一个普通调用方都能改网关配置——这是安全事故。

**Q4：为什么连接池不随配置重建？**
重建连接池会断开所有在途连接，代价很大。权重、启停这类变更只需要换“路由数据”，连接是物理资源，按渠道 ID 复用即可。

## 8. 本版本不做什么

- 不实现管理后台前端页面（版本 6 可选）
- 不实现语义缓存、安全护栏、协议互转（版本 6）
- 不做配置的分布式一致性（单节点场景，远期）
