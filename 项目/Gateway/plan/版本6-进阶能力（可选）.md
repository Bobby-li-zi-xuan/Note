# 版本 6：进阶能力（可选，学习版）

## 1. 学习目标

核心能力完成后，按兴趣挑选增强项。每个子能力都能单独写进简历：

- **语义缓存**：学会 embedding 与向量相似度的实际应用。
- **安全护栏**：学会规则引擎式的内容安全设计。
- **协议互转**：学会“协议适配层”的设计（字段映射、流式格式差异）。
- **金丝雀发布**：学会灰度发布的流量划分与对比观测。
- **可观测性完善**：把指标、日志、审计收敛成标准体系。

⚠️ 这些子能力相互独立，**选 1~2 个做就行**，不用全做。建议按文末的取舍排序挑选。

## 3. 用大白话讲：进阶能力是什么

核心版本做的是“把网关做对”，版本 6 做的是“把网关做酷”：

- **语义缓存**：客户常问“怎么退换货”和“退换货流程是什么”——意思一样，直接翻出上次的答案，不用再找大模型（省时省钱）。
- **安全护栏**：安检升级——拦 Prompt 注入（有人想骗模型泄露系统提示词）、识别敏感内容、给手机号打码。
- **协议互转**：配一个“翻译官”，让只会说 Claude 话的供应商用 OpenAI 话术服务客户。
- **金丝雀**：新餐厅先试营业，只放 10% 客人进来，口碑（指标）没问题再全面开放。
- **可观测性**：装监控大屏，哪个环节慢、哪家店翻车率高，一目了然。

## 4. 功能模块与实现逻辑

### 4.1 语义缓存（记住常问的问题）

**实现逻辑**：

- 两级缓存：
  - 精确缓存（先行）：请求哈希（模型 + 参数 + 规范化消息序列）完全一致才命中，零开销。
  - 语义缓存：请求文本向量化 → 与缓存条目算余弦相似度 → 超阈值（默认 0.95）视为命中。
- 向量化：调 embedding 服务（OpenAI 兼容或本地模型）；向量结果缓存复用，避免重复计算。
- 缓存键：模型别名 + 关键参数（temperature 等影响结果的参数）+ 向量；不同模型/参数不共享。
- 命中行为：跳过执行层直接返回缓存；仍记录用量（按“节省成本”口径），输出缓存命中指标。
- 失效与容量：TTL（默认 1 小时）；内存上限，超限按 LRU 淘汰；管理接口支持清空。
- 一致性：只缓存成功响应；流式响应需先聚合完整内容（默认关闭流式缓存，避免复杂度）。

**为什么这样设计**：精确缓存是“保底”，语义缓存是“惊喜”——先保证绝不误命中，再追求相似命中。

### 4.2 安全护栏（安检升级）

**实现逻辑**：

- 规则结构：护栏 = 规则集合（类型 + 模式 + 动作：拦截/脱敏/告警）。
- 三类规则：
  - Prompt 注入检测：关键词、正则、编码绕过检测（base64/Unicode 混淆）；命中默认拦截。
  - 敏感内容识别：涉政/暴力等关键词与正则（规则文件可配）。
  - PII 脱敏：手机号、邮箱、身份证等正则识别，请求/响应中替换为掩码。
- 执行位置：请求侧（进上游前）与响应侧（返回前）各一道护栏插件（挂在版本 2 插件框架上）。
- 记录：命中的规则、动作、脱敏前后摘要写日志与指标（`guardrail_hits{rule,action}`）。
- 定位声明：规则版不追求 100% 准确，文档写明局限；后续可换模型判定实现（同一 SPI）。

**为什么这样设计**：规则版能跑、能演示、能讲清局限；把“检测器”抽象成 SPI 后，升级为模型判定版不用改架构。

### 4.3 协议互转（翻译官）

**实现逻辑**：

- 请求映射：OpenAI 请求 → 上游协议请求（消息结构、system 提示、tools 结构、参数名差异映射表）。
- 响应映射：上游响应 → OpenAI 响应（内容、usage、finish_reason 字段映射）。
- 流式映射：上游流式事件 → OpenAI chunk 格式；注意消息边界与事件类型差异（如 Anthropic 的 message_start / content_block_delta）。
- 错误映射：上游错误码/错误体 → OpenAI 风格错误。
- 实现方式：新增 Connector 实现（版本 1 的 Connector SPI 扩展），映射表独立为配置/常量，便于新增协议。

**为什么这样设计**：协议适配是“翻译层”问题——映射表与核心逻辑分离，加协议 = 加映射 + 加 Connector，不动路由和治理。

### 4.4 金丝雀发布（新店试营业）

**实现逻辑**：

- 配置：金丝雀组 = 候选子集 + 流量比例（如 10%）；稳定组为其余流量。
- 分组判定：按令牌/租户/请求 ID 哈希取模（同一调用方始终同组，保证体验一致）或纯随机。
- 路由集成：金丝雀插件在 Filter 阶段写分组信号，Scheduler 按分组选候选集（版本 2 机制天然支持）。
- 对比观测：两组流量分别打指标标签（延迟/错误率/成本），满足条件后逐步调高比例至全量。
- 回滚：金丝雀组失败率超阈值自动降回稳定组（复用熔断/冷却状态）。

### 4.5 可观测性完善（监控大屏）

**实现逻辑**：

- Prometheus 指标端点：把版本 1~5 的内存计数器统一导出（请求量、延迟直方图、错误率、Token 用量、成本、熔断/降级/限流事件、缓存命中、决策策略分布）。
- 结构化日志规范：统一字段（时间、级别、requestId、module、event、明细 JSON）；成功请求默认采样率可配，错误全量。
- 可选 OpenTelemetry：链路追踪贯穿 入口 → 决策 → 执行 → 上游；先接 HTTP 层与执行层 span，再扩展插件 span。
- 状态闭环：指标既是决策的产出，也是决策的输入（`ModelState`），形成可观测闭环。

### 4.6 管理后台（可选加分项）

**实现逻辑**：

- 静态单页前端调用 Admin API：用量/成本趋势、模型路由分布、延迟与错误率、熔断/降级事件流、决策日志检索。
- 只读优先：展示类页面优先；管理操作（改权重/吊销令牌）做简单表单，复用 Admin API 与审计。
- 不引重型前端工程（学习项目不划算）。

### 5.1 Higress 的 ai-cache 插件（语义缓存的实现参考）

**来源**：[Higress 官方文档 - AI 缓存](https://higress.cn/en/docs/latest/user/plugins/ai/api-provider/ai-cache/) / [Higress 源码 README](https://github.com/higress-group/higress/tree/main/plugins/wasm-go/extensions/ai-cache)

**文档要点（原文整理）**：

插件定位（原文）：LLM 结果缓存插件，默认配置可直接用于 OpenAI 协议下的结果缓存，**同时支持流式与非流式响应缓存**。

**配置分三部分（原文）**：

1. 向量数据库（vector）：存储请求/响应的向量；
2. 文本 Embedding 服务（embedding）：把文本转成向量；
3. 缓存数据库（cache）：精确字符串缓存。

**两级缓存与优先级（原文）**：插件同时支持“基于向量数据库的语义缓存”和“基于字符串匹配的精确缓存”；**两者都配置时，优先查精确缓存，未命中再用向量库做语义检索。**

**相似度判定（原文整理）**：

- 度量方式：`Cosine`、`DotProduct`、`Euclidean`；
- `Cosine` 和 `DotProduct` **值越大越相似**，用 `gt`（大于阈值）判定命中；
- `Euclidean` **值越小越相似**，用 `lt`（小于阈值）判定命中。

**流程（原文描述 + 源码 README 整理）**：

```
请求 → ① 精确缓存查询（字符串匹配）
         ├─ 命中 → 直接返回缓存响应
         └─ 未命中 → ② 文本 embedding 向量化
                      → ③ 向量库相似度检索
                      ├─ 超过阈值 → 返回缓存响应
                      └─ 未命中 → ④ 转发上游
                                   → ⑤ 响应写入缓存（含向量）
```

**对本项目的启示**：本项目 4.1 的两级缓存（精确先行 + 语义兜底）与 Higress 完全一致；相似度阈值按度量方式区分 `gt`/`lt` 这个细节也要保留。

### 5.2 Kong 的 AI Semantic Prompt Guard（语义护栏的参考）

**来源**：[Kong 官方文档 - AI Semantic Prompt Guard](https://developer.konghq.com/plugins/ai-semantic-prompt-guard/)

**文档要点（原文整理）**：

插件作用（原文）：在 AI Prompt Guard（关键词规则版）之上增加**语义相似度匹配**，允许或阻止与列表“相似”的 prompt。

**匹配行为（原文逐条）**：

1. 配置了 deny 列表，请求命中 deny 列表 → 返回 **403**；
2. 配置了 allow 列表，但请求没命中任何 allow 项 → 也返回 **403**；
3. 同时配置 deny 和 allow 时，**deny 优先**：命中 deny 就 400/403，即使它也匹配 allow；只有不命中 deny 且命中 allow 才放行。

**向量库与 Embedding（原文整理）**：

- 向量库支持 Redis（Vector Similarity Search）、Valkey、pgvector；
- Embedding 服务支持 OpenAI、Azure、Bedrock、Gemini、Hugging Face、Mistral 等；
- 多语言支持取决于所选 embedding 模型（原文 FAQ：插件把原始 UTF-8 文本发给 embedding 服务）。

**对本项目的启示**：

1. allow/deny 规则 + 动作（拦截）的结构（本项目 4.2 的规则集合）；
2. **deny 优先于 allow** 的判定顺序要写进规则引擎；
3. 语义护栏依赖 embedding 服务——学习版先做规则版，SPI 留好即可。

### 5.3 New API 的格式互转（协议互转的参考）

**来源**：[New API 特性说明](https://docs.newapi.pro/zh/docs/guide/wiki/basic-concepts/features-introduction) / [New API 功能指南](https://docs.newapi.pro/zh/docs/guide/feature-guide)

**文档要点（原文整理）**：

- New API 的核心能力之一是把多种协议（OpenAI / Claude / Gemini 等）**统一成 OpenAI 兼容格式**对外提供；
- 支持跨格式转换：例如上游 Claude 模型可以通过网关以 OpenAI 格式被调用；
- 依赖“字段映射”处理请求/响应的差异（消息结构、参数名、usage、错误体）。

**对本项目的启示**：本项目 4.3 的实现路径（请求映射 → 响应映射 → 流式映射 → 错误映射）就是这类格式互转的标准拆分；先做非流式，再做流式（流式的消息边界差异最花时间）。

### 5.4 Portkey 的金丝雀测试（金丝雀的参考）

**来源**：[Portkey 官方文档 - AI Gateway](https://portkey.ai/docs/product/ai-gateway)

**文档要点（原文整理）**：

- Portkey 支持 **Canary Testing**：在**生产环境**对新模型做金丝雀测试；
- 与负载均衡的区别：金丝雀是“小比例试新 + 对比观测”，而不是均匀分散；
- 所有策略（含金丝雀）通过 Gateway Config 声明，与路由、熔断、重试等配置并列。

**对本项目的启示**：金丝雀 = 流量比例配置 + 稳定分组（哈希）+ 双组指标对比（本项目 4.4）；用版本 2 的插件写分组信号，是低成本且优雅的接入方式。

## 6. 演示场景与验收标准

### 语义缓存

同一问题用两种措辞连续请求：第二次命中语义缓存（延迟显著下降、指标显示命中）；不同参数不误命中。

### 安全护栏

提交注入样本（含编码绕过）被拦截并返回明确错误；含手机号的响应被脱敏；护栏命中记录可查。

### 协议互转

配置一个 Anthropic 上游渠道，客户端以 OpenAI 格式调用：请求/响应/流式均正常，错误体为 OpenAI 格式。

### 金丝雀

新渠道配置 10% 流量：调用 100 次，比例接近 10%；同一令牌重复调用始终同组；新渠道故障率超阈值自动回滚稳定组。

### 验收标准

1. 所选子能力均满足各自演示场景。
2. 新能力全部通过版本 2 插件框架接入，不修改核心路由代码。
3. Prometheus 指标端点就绪，关键事件可查询。
4. 版本 5 功能回归通过。

## 7. 新手常见问题

**Q1：语义缓存会不会答错？**
有可能——相似 ≠ 相同。缓解：阈值调高（0.95+）、只缓存低风险请求（如不含个性化参数的）、TTL 短一些。文档里要写清这些限制，面试官反而认可。

**Q2：规则版护栏靠谱吗？**
不追求 100%，但能拦常见攻击。关键是讲清“为什么用规则版”：学习项目不依赖外部模型判定服务，且 SPI 设计保证以后可以升级。

**Q3：协议互转最难的地方在哪？**
流式。各家流式事件模型不一样（Anthropic 分 message 和 content_block 多层事件，OpenAI 是扁平 chunk），映射时容易丢字段或顺序错乱。建议先做非流式，再做流式。

**Q4：金丝雀和加权随机有什么区别？**
加权随机是“每个请求独立随机”；金丝雀要求“同一调用方始终同组”（按 ID 哈希分组），否则用户会一会儿新版一会儿旧版，体验和观测都会乱。

## 8. 建议取舍（按简历价值 / 成本排序）

1. **协议互转**（高价值、成本中）——展示协议设计能力，面试好讲。
2. **安全护栏**（中高价值、成本低）——规则版实现快，能讲清局限与演进。
3. **金丝雀**（中价值、成本低）——与插件框架天然契合，演示直观。
4. **语义缓存**（高价值、成本高）——要接 embedding，做好较花时间，排后面。
5. **管理后台**（中价值、成本高）——纯工作量型，作为可选加分项。

## 9. 本版本不做什么

- 不做 MCP/A2A Agent 网关（远期方向）
- 不做 Redis 分布式缓存/限流（远期）
- 语义缓存不做流式响应缓存（默认关闭，避免聚合复杂度）
- 护栏不追求模型级检测精度（规则版定位明确）
