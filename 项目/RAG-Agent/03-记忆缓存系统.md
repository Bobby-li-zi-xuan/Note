# 03 · 记忆缓存系统

## 一、设计动机

绝大多数 LLM 对话系统只有一个"消息列表"，窗口满了就丢弃旧的。这种方式有几个问题：

1. **重启后丢失上下文**：浏览器刷新或服务重启，LLM 完全不记得之前聊了什么
2. **无法跨会话复用记忆**：每次新对话都从零开始
3. **重要信息和闲聊混在一起**：用户的偏好、之前确认的事实、设定的约束，和日常对话混在同一个窗口里

三层记忆缓存就是为了解决这些问题而设计的。

---

## 二、三层架构

```
┌─────────────────────────────────────────────────────────┐
│ L1 · 运行态消息窗口 (ChatMemoryManager)                   │
│ - 生命周期：单次 Agent 执行                                │
│ - 内容：原始 Message 列表（User/Assistant/ToolResponse）    │
│ - 作用：直接喂给 LLM 的上下文                               │
│ - 实现：MessageWindowMemoryImpl (基于 ConcurrentHashMap)   │
└─────────────────────────────────────────────────────────┘
                          ▲ 增量摘要
                          ▼
┌─────────────────────────────────────────────────────────┐
│ L2 · 结构化记忆快照 (MemoryCacheManager + Caffeine)       │
│ - 生命周期：会话级，TTL 30 分钟无访问自动淘汰               │
│ - 内容：MemorySnapshot { SUMMARY, FACT, CONSTRAINT,       │
│          TOOL_HINT, PROMPT_FRAGMENT }                    │
│ - 作用：快速恢复上下文、注入 think prompt、避免重复计算      │
│ - 实现：DefaultMemoryCacheManager + Caffeine Cache         │
└─────────────────────────────────────────────────────────┘
                          ▲ 异步刷盘
                          ▼
┌─────────────────────────────────────────────────────────┐
│ L3 · 持久化冷存储 (MemoryColdStorageGateway)              │
│ - 生命周期：永久（除非主动清理）                            │
│ - 内容：MemoryEntry 结构（含 TTL、confidence、version）     │
│ - 作用：重启恢复、跨会话迁移数据                            │
│ - 实现：DbMemoryColdStorageGateway / FileBased-           │
└─────────────────────────────────────────────────────────┘
```

## 三、记忆类型（MemoryType）

每种记忆有明确的语义和用途：

| 类型              | 含义           | 拼接优先级           | 每类型上限           |
| --------------- | ------------ | --------------- | --------------- |
| SUMMARY         | 对话摘要         | 注入 think prompt | 1 条             |
| FACT            | 已确认的事实       | 注入 think prompt | maxPerType(默认3) |
| CONSTRAINT      | 约束规则         | 注入 think prompt | maxPerType      |
| TOOL_HINT       | 工具调用结果的结构化记录 | 注入 think prompt | 1 条             |
| PROMPT_FRAGMENT | 预构建的提示片段     | 直接注入            | maxPerType      |

每种类型在 L2 中独立管理，注入时只取最新的一条（按 `updatedAt` 倒序）：

```java
private void appendMemorySection(StringBuilder builder, String title,
        List<MemoryEntry> entries) {
    // 只取最新的一条
    builder.append(title).append(": ")
        .append(ordered.get(0).getValue()).append('\n');
}
```

这样做是为了控制注入到 think prompt 的 token 量——不是把历史全部展开，而是每类只给最新的一条"结论"。

## 四、L1：消息窗口（MessageWindowMemoryImpl）

最贴近 LLM 的一层，存储原始 Message 对象。核心特性：

- **窗口截断**：超出 `maxMessages` 时丢弃最早的
- **系统提示词初始化**：Agent 的 systemPrompt 作为第一条 SystemMessage
- **键值分离**：`ConcurrentHashMap<String, List<Message>>` 按 sessionId 隔离

```java
// 初始化：按 sessionId 创建一个消息窗口
memoryManager.initialize(sessionId, restoredMessages, systemPrompt, maxMessages);
// 使用：AgentCore 随时存取
memoryManager.addMessage(sessionId, newMessage);
memoryManager.getMessages(sessionId);
memoryManager.replaceAll(sessionId, newHistory);
```

## 五、L2：结构化记忆快照

### 5.1 MemoryEntry 数据结构

```java
public class MemoryEntry {
    String key;          // "sessionId:MEMORY_TYPE:suffix"
    MemoryScope scope;   // SESSION / USER / AGENT / GLOBAL
    String entityId;     // 关联的实体 ID
    MemoryType memoryType;
    String value;        // 正文（摘要文本 / 事实描述等）
    long version;        // 版本号（时间戳），用于冲突解决
    long updatedAt;
    long expireAt;       // 过期时间
    String source;       // "rule" / "llm" / "manual"
    double confidence;   // 置信度 0-1
}
```

### 5.2 Caffeine 缓存配置

```java
Caffeine.newBuilder()
    .expireAfterAccess(Duration.ofMinutes(30))  // 30分钟无访问淘汰
    .maximumSize(256)                            // 最多 256 个快照
    .recordStats()                               // 开启统计（命中率、淘汰数）
    .build();
```

选择 Caffeine 而非 Guava Cache：
- Caffeine 使用 W-TinyLFU 淘汰策略，命中率优于 LRU
- 内置统计 API，可直接拿到 hitRate / missRate
- Spring Boot 官方推荐的本地缓存方案

### 5.3 快照生命周期

```
1. 冷启动 → refreshFromColdStorage(sessionId) → 从 DB 恢复 L2
2. 运行时 → checkpointSessionCache() → 增量摘要写入 L2
3. 结束时 → flushSessionCache() → L2 → 异步刷入 L3
4. 空闲 30 分钟 → Caffeine 自动淘汰 → 下次访问再从 L3 恢复
```

## 六、增量摘要器（IncrementalMemorySummarizer）

与全量摘要不同，增量摘要只处理**两轮 checkpoint 之间的新消息**：

```java
// AgentCore.checkpointSessionCache()
int safeStartIndex = resolveSafeStartIndex(messages);  // 上次 checkpoint 位置 + 1
List<Message> deltaMessages = messages.subList(safeStartIndex, messages.size());
List<MemoryEntry> deltaEntries = incrementalSummarizer.summarizeDelta(sessionId, deltaMessages);
```

四种摘要的生成规则：

| 类型 | 生成逻辑 |
|------|---------|
| SUMMARY | 取最近 8 条消息，每条截取 220 字符，总长度 ≤ 1200 字符 |
| FACT | 收集 UserMessage 的问题 + ToolResponse 的结果 + 包含"完成/结论/已"的 AssistantMessage，每条截取 160-180 字符 |
| CONSTRAINT | 收集 SystemMessage + 包含"必须/禁止/不要/仅当"关键词的消息 |
| TOOL_HINT | 收集所有工具调用的 `toolName=toolOutput` 键值对 |

所有摘要都带有置信度标记（0.60-0.75），用于后续合并不时排序淘汰。

### 为什么用规则而不用 LLM 生成摘要

这是有意为之的权衡：

| 方案 | 延迟 | 成本 | 质量 |
|------|------|------|------|
| 规则摘要 | ~0ms | 零 | 中等（模板化，缺乏语义理解） |
| LLM 摘要 | 1-3s | API 调用费 | 高（能理解语义和意图） |

在每轮对话都做 checkpoint 的场景下，如果用 LLM 生成摘要，延迟会累积到用户可感知的程度。规则摘要虽然不够"聪明"，但至少能稳定提供结构化的上下文线索。

## 七、MemoryMergeService 合并淘汰

增量摘要是追加的，不能无限增长。MemoryMergeService 负责：

### Step 1：按 key 去重

同一 key 的新版本覆盖旧版本（version 更大的胜出）。

### Step 2：相似度去重

```java
private boolean isSimilar(MemoryEntry left, MemoryEntry right) {
    return jaccardSimilarity(left.getValue(), right.getValue()) >= 0.75;
}
```

对 value 做词级 Jaccard 相似度判断，相似度 ≥ 75% 的视为同一内容，保留版本更新的。

### Step 3：排序淘汰

按 `confidence → updatedAt → version` 降序排列，再按类型上限截断：

```java
// SUMMARY 和 TOOL_HINT 只保留 1 条
if (type == SUMMARY || type == TOOL_HINT) return 1;
// 其他类型保留 maxPerType 条（默认 3）
return maxPerType;
```

## 八、异步 write-behind

缓存写入 L3 是异步的，不阻塞 Agent 主流程：

```java
// AgentCore.flushSessionCache()
asyncMemoryWriteService.submit(sessionId, entriesToPersist);

// AsyncMemoryWriteService 使用 @Async
@Async
public void submit(String sessionId, List<MemoryEntry> entries) {
    for (MemoryEntry entry : entries) {
        memoryColdStorageGateway.save(entry);  // INSERT ... ON CONFLICT DO UPDATE
    }
}
```

好处：
- Agent 对话主路径不被数据库 IO 阻塞
- 批量写入比逐条写入更高效
- 写失败不影响当前对话（下次查缓存时再从 L1 恢复）

代价：
- 极端情况下（进程被 kill）可能丢失最后一个 checkpoint 的新增摘要
- 可以通过缩短 checkpoint 间隔或使用同步 write-through 来缓解

## 九、面试问答

### Q: 你是怎么设计缓存体系的？

> 我用了三层。L1 是消息窗口，直接把 Message 对象存内存里，给 LLM 拼 prompt 用。L2 是结构化快照，用 Caffeine 做本地缓存，把会话压缩成 summary、facts、constraints、tool_hints 四种记忆类型，注入到 think prompt 里让 LLM 知道"对话进行到哪了"。L3 是冷存储，异步 write-behind 到 PostgreSQL，保证服务重启后能恢复。

> 三层之间不是孤立的——L1 里新消息累积到一定程度触发增量摘要写 L2，L2 结束时会异步刷到 L3。数据和热度从 L1 到 L3 逐步冷却，从 L3 到 L1 逐步恢复。

### Q: 为什么中间要加一个 L2，直接从 L1 到 L3 不行吗？

> L2 做的是"结构化压缩"。L1 的消息是原始 Message 对象——用户说了什么、模型答了什么、工具返回了什么——十几轮对话下来可能有几千字，没法直接注入到每轮的 think prompt 里。L2 把这几千字压缩成四五个关键信息点——当前话题是什么、确认了哪些事实、有什么约束——几十字就讲清楚了。没有 L2 的话，LLM 每轮看到的要么是冗余的原始消息，要么是空白的上下文。

### Q: 缓存一致性怎么保证？

> 主要靠 version 字段。每个 MemoryEntry 的 version 就是它的创建时间戳，合并时新版覆盖旧版。L2 的 checkpoint 是按"上次同步位置"做的增量——我记录了一个 checkpointedIndex，只对新增的消息做摘要，不会重复处理。

> 但说实话，当前的一致性保证是最终一致性，不是强一致。如果 Agent 正在跑的时候 L3 挂了，异步写入会静默失败。好在这个系统的记忆不是关键业务数据——丢了一条摘要最多是 LLM 回复质量下降一点，不会造成数据损坏。

### Q: Caffeine 的淘汰策略是什么？为什么不用 Redis？

> Caffeine 用的是 W-TinyLFU，这是一种结合了 LRU 和 LFU 优势的淘汰算法——既考虑访问频率也考虑访问时间。配置是 30 分钟无访问过期 + 最多 256 个快照。

> 至于为什么不用 Redis——我这个项目是没有分布式部署需求的，单实例跑就行。加一个 Redis 意味着多一个运维组件、多一个故障点。Caffeine 在单机场景下的性能比 Redis 更好（无网络开销），而且自带统计 API，命中率直接就能拿到。

### Q: 摘要为什么用规则做而不用 LLM？

> 这是成本和效果之间的权衡。规则摘要大概 0 毫秒延迟、零成本；LLM 摘要需要调 API，1-3 秒延迟，每次都有费用。在"每轮对话都要做 checkpoint"这个前提下，用 LLM 做摘要成本太高了。

> 我的判断是：规则摘要在"提供上下文线索"这个场景下够用了。它不需要深刻理解对话内容，只需要告诉 LLM"到目前为止用户问了天气、确认了明天有雨、还提到要发邮件"。这些简单的事实提取用正则和截断就能做。

### Q: 如果面试官问"为什么不做全量摘要而是增量"，你怎么答？

> 全量摘要是每轮都把所有历史消息重新跑一遍摘要，越到后面越贵——你第八轮对话时要重新处理前七轮的所有消息。增量摘要只处理新增的部分——第八轮只处理第八轮的消息，然后和前面的摘要合并。

> 代价是增量摘要会丢失一部分全局视角——第十轮对话时的约束可能在第一轮就设置了，但增量摘要只看最近几轮可能注意不到。我的做法是在 cold start（冷存储没有快照）时做一次全量摘要打底，后续只做增量。

### Q: 如果 Caffeine 缓存满了怎么办？

> 不会真的"满"，因为配置了 30 分钟访问过期和最大 256 个快照。如果会话数超过 256，W-TinyLFU 会淘汰最不活跃的。被淘汰的快照下次访问时，会触发 `refreshFromColdStorage` 从数据库重新恢复。

> 这是"缓存穿透"的标准解决方案——L2 被淘汰了不要紧，L3 还在。唯一的代价是恢复时有一次数据库查询，但这是一个冷路径，频率很低。

### Q: 你觉得这套缓存体系有什么不足？

> 有两个。一是摘要质量——当前的规则摘要在高度复杂的对话里可能会遗漏重要信息，理想情况下应该做一个混合策略：默认用规则，检测到话题重大变化时用 LLM 做一次深度摘要。二是多会话间的记忆复用——现在是按 sessionId 隔离的，同一个用户的不同会话之间无法共享记忆。如果用户在上一个会话里说过"我是 Python 开发者"，下一个会话应该记住这个偏好。这需要在 MemoryScope 层面扩展 USER 级别的记忆管理。

### Q: TTL 和置信度是怎么定的？

> 当前所有记忆条目都是 24 小时 TTL，这是比较保守的设置。置信度是写的死值——规则生成的摘要 0.60-0.75，因为我知道规则摘要的语义理解不如 LLM。如果以后引入 LLM 摘要，它的条目可以标 0.90+ 的置信度，合并时 LLM 摘要就不会被规则摘要覆盖。

> 更好的做法是让置信度动态变化——每次记忆被"验证"（比如 LLM 引用了某个事实并确认了），置信度就上升一点；长时间没被引用就下降。但这个机制需要更多的追踪基础设施。
