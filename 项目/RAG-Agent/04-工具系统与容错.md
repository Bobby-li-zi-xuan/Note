# 04 · 工具系统与容错

## 一、双层工具体系

工具系统采用**业务抽象 + 框架适配**的双层设计：

```
【业务层】                             【框架层】
Tool 接口                             Spring AI @Tool
  ├─ getName()                         └─ @Tool(name, description)
  ├─ getDescription()                  
  ├─ getType() → FIXED / OPTIONAL     
  └─ 业务方法                           
      ↓ MethodToolCallbackProvider     
      ↓                               
  ToolCallback[] → DefaultToolExecutor
```

### 为什么分两层

业务层（Tool 接口）负责"这个工具在我的系统里是什么角色"——固定工具还是可选工具，Agent 装配时按白名单过滤。框架层（Spring AI `@Tool`）负责"LLM 怎么理解这个工具"——函数签名、参数描述、返回格式。

两层之间通过 `MethodToolCallbackProvider` 桥接——把业务层的 Tool Bean 上的 `@Tool` 注解方法提取成 `ToolCallback`。

### 工具分类

| 类型 | 含义 | 示例 |
|------|------|------|
| FIXED | 始终可用，任何 Agent 都能调用 | KnowledgeTool |
| OPTIONAL | 需要在 Agent 配置里显式开启 | EmailTools, DataBaseTools, TerminalTools |

装配逻辑：

```java
// 固定工具全部加入
List<Tool> runtimeTools = new ArrayList<>(toolFacadeService.getFixedTools());

// 可选工具按白名单叠加
Map<String, Tool> optionalTools = toolFacadeService.getOptionalTools();
for (String toolName : agentConfig.getAllowedTools()) {
    Tool tool = optionalTools.get(toolName);
    if (tool != null) runtimeTools.add(tool);
}
```

这样做的原因是安全性——你不会希望随便哪个 Agent 都有执行终端命令或发邮件的权限。

## 二、工具注册与代理处理

工具对象可能被 Spring AOP 代理（比如加了 `@Transactional` 或其他切面），直接传给 `MethodToolCallbackProvider` 会拿不到原始注解：

```java
private Object resolveToolTarget(Tool tool) {
    return AopUtils.isAopProxy(tool)
        ? AopUtils.getTargetClass(tool)    // 取真实类
        : tool;                             // 否则直接用
}
```

## 三、ToolExecutor 接口设计

```java
public interface ToolExecutor {
    // 决策阶段：返回 true 表示 LLM 想调用工具
    boolean think(Prompt prompt, List<ToolCallback> tools, String thinkPrompt);

    // 执行阶段：返回新的完整对话历史
    List<Message> execute(Prompt prompt, ChatResponse lastResponse);

    // 查询与统计
    ChatResponse getLastResponse();
    long getLastTtftMs();       // 最近一次首 token 延迟（毫秒）
    int getTotalToolCalls();    // 累计工具调用次数
    int getFailedToolCalls();   // 累计失败次数

    // 回调：工具执行完成后通知上层
    void setOnToolCalled(Consumer<ToolResponseMessage> callback);
}
```

接口的职责边界非常清晰：
- `think` 只管 LLM 交互，不管工具执行
- `execute` 只做工具执行和失败恢复
- 统计接口让上层可以监控工具调用的健康状态
- 回调让 AgentCore 能在工具执行后立即持久化消息

## 四、三层工具失败恢复

这是项目的重点设计。工具调用可能因为各种原因失败——网络超时、参数错误、目标服务不可用。简单的 try-catch + throw 会让一次工具失败直接终结整轮对话。三层恢复的设计目标是：**尽最大可能让工具调用成功，失败时给出有意义的信息而不是崩溃。**

### 4.1 整体架构

```
executeWithRecovery(baseHistory, lastResponse, callingManager)
  │
  ├─ [Layer 1] 快速重试 (Fast Retry)
  │    次数预算: 3 次
  │    退避策略: 200ms → 400ms → 800ms (指数退避, 上限 2000ms)
  │    适用错误: 网络超时、连接中断（由 isRetryable() 判定）
  │    决策者: 代码逻辑
  │
  ├─ [Layer 2] 策略重试 (Policy Retry)
  │    次数预算: LLM 决定 (0-5, 默认 0 即跳过)
  │    退避策略: LLM 决定 (100-2000ms, 可带乘数)
  │    触发条件: 快速重试耗尽
  │    决策者: LLM (通过 ToolRecoveryDecision)
  │
  └─ [Layer 3] LLM 决策 (Model Consultation)
       次数预算: 2 次
       触发条件: 策略重试也失败
       决策者: LLM 分析失败上下文，返回 RETRY / DEGRADE / STOP
```

### 4.2 失败上下文

每次失败都构造结构化的 `ToolFailureContext`：

```java
record ToolFailureContext(
    String toolName,        // 哪个工具失败了
    String toolArguments,   // 传了什么参数
    String failureStage,    // 在哪个阶段失败的 (EXECUTE/RETRY/POLICY_RETRY)
    String exceptionClass,  // 什么异常
    String exceptionMessage,// 异常信息
    int retryCount,         // 已经重试了几次
    boolean retryable,      // 是否可重试
    long lastDelayMs,       // 上一次等待了多久
    int toolCallIndex       // 第几个工具调用
) {}
```

### 4.3 LLM 恢复决策

当代码层的重试耗尽后，将失败上下文提交给 LLM，获取恢复策略：

```java
// ChatClientToolRecoveryDecisionClient.decide()
String prompt = failureRecoveryService.buildRecoveryPrompt(context);
// LLM 返回 JSON:
// {
//   "action": "RETRY" | "RETRY_WITH_POLICY" | "DEGRADE" | "STOP",
//   "maxRetries": 3,
//   "initialBackoffMs": 500,
//   "backoffMultiplier": 1.5,
//   "allowModelConsultation": true,
//   "reason": "网络抖动，适当加长等待时间"
// }
```

四种动作的含义：

| 动作 | 含义 | 举例 |
|------|------|------|
| RETRY | 用相同参数再试 | "可能是临时网络抖动，重试就好" |
| RETRY_WITH_POLICY | 调整重试策略后再试 | "这个服务比较慢，加大超时和退避时间" |
| DEGRADE | 降级处理 | "目标数据源不可用，用缓存版本" |
| STOP | 停止 | "参数错误，重试多少次也没用" |

### 4.4 安全边界

每一层都有硬上限，不会无限循环：

```java
// 快速重试：最多 3 次
int fastRetryBudget = 3;

// 策略重试：LLM 决定但封顶 5 次
policyRetryBudget = Math.max(0, Math.min(decision.maxRetries(), 5));

// LLM 咨询：最多 2 轮
if (modelConsultationCount >= 2) {
    return returnFailure(baseHistory, context, activePolicy);
}

// 退避时间：100ms ~ 2000ms
currentDelayMs = clampBackoff(decision.initialBackoffMs(), 100L, 2_000L);
```

### 4.5 兜底消息

所有恢复都失败后，生成结构化的失败消息：

```java
ToolResponseMessage failureMessage = failureRecoveryService.buildFailureResponse(context, decision);
// 包含完整的失败上下文，LLM 可以看到并决定如何向用户解释
```

这个失败消息会被写回对话历史，LLM 下一轮 think 时就能看到"哦，刚才那个工具调用失败了，我需要告诉用户发生了什么"。

## 五、工具调用统计

DefaultToolExecutor 维护了工具调用的计数器：

- `totalToolCalls`: 累计次数（包括重试）
- `failedToolCalls`: 累计失败次数（包括成功恢复的）
- `lastTtftMs`: 最近一次 think 的首 token 延迟

这些统计对监控和调优很有帮助——如果某个工具的失败率突然上升，说明它的下游依赖可能有问题。

## 六、面试问答

### Q: 你们工具调用的失败处理是怎么设计的？

> 我设计了三层恢复机制。第一层是代码层的快速重试——超时和连接中断这类临时故障，直接重试，200ms 指数退避，最多 3 次。第二层是把失败上下文交给 LLM 决策——LLM 分析失败原因后可以要求调整策略重试（比如扩大退避时间）或降级处理。第三层是安全兜底——每层都有预算上限，LLM 最多咨询 2 轮，重试最多 5 次，退避时间封顶 2 秒。

> 为什么要把失败交给 LLM 决策？因为有些失败不是纯技术故障，而是策略问题。比如调某个 API 超时，可能是网络抖动（重试就行），也可能是目标服务太慢（需要加大超时），还可能是参数有问题（重试多少次都没用）。LLM 可以根据异常消息判断属于哪一类，比固定规则灵活。

### Q: 为什么不把所有错误都丢给 try-catch 处理？

> try-catch 只能处理"已知的已知"——你知道会抛什么异常、知道怎么处理。但实际上工具调用的失败模式很多样——参数错误、超时、权限不足、下游服务返回异常数据——很难穷举。三层恢复的优势在于：代码层处理确定性的可恢复错误（网络问题），LLM 层处理需要判断力的不确定性场景（策略调整），兜底层保证即使 LLM 也判断错了，系统也不会崩。

### Q: 如果 LLM 在恢复决策里给了不合理的建议怎么办？

> 有三层防护。一是 LLM 的输出被约束在固定的 JSON schema 里，action 必须是四种之一，参数有上下限。二是即使 LLM 说"重试"，最大次数和退避时间也被代码限制住了——不会出现"重试 100 次每次等 30 秒"这种离谱情况。三是 LLM 本身也可能失败——如果 recoveryDecisionClient 抛异常了，直接 STOP 兜底，给个明确的失败消息而不是继续死磕。

### Q: 工具注册为什么分为固定工具和可选工具？

> 主要是安全和控制。固定工具是系统级能力——比如知识检索，任何 Agent 都应该能用。可选工具是有风险或需要特定场景才开启的——比如终端命令执行、发邮件、数据库直连。Agent 创建时按 allowedTools 白名单过滤，管理员可以控制"这个 Agent 能做什么"。

> 另一种思路是按 RBAC 做更细粒度的权限控制，但当前阶段按类型分就够了。

### Q: MethodToolCallbackProvider 和 AOP 代理的冲突你是怎么解决的？

> 工具类如果被 Spring AOP 代理过（比如加了事务注解），拿到的是代理对象而不是原始类。MethodToolCallbackProvider 需要读取原始类上的 @Tool 注解，代理对象上读不到。所以我在 Factory 里做了判断——如果是 AOP 代理就取 targetClass，否则直接用。

### Q: 流式调用时工具失败和非流式有什么区别？

> 流式调用时我做了降级——某些模型（比如 DeepSeek）的流式 API 在带 tools 参数时偶尔会失败。失败后自动切非流式调用。但如果工具执行本身失败了，恢复流程是一样的——不管是流式还是非流式，都走同一套 executeWithRecovery 逻辑。

### Q: 工具调用的回调机制是怎么设计的？

> DefaultToolExecutor 在执行完成后回调 AgentCore 的 onToolCalled 方法。这个回调负责把工具结果持久化到数据库和同步到记忆。回调不是"可选的"——如果没有注册回调，工具结果只会存在内存里，一旦服务重启就丢了。当前实现是构造时强制注册。

### Q: 如果我想添加一个新的工具，需要改哪些地方？

> 三步。第一步：创建一个类实现 Tool 接口，决定它是 FIXED 还是 OPTIONAL。第二步：在方法上加 @Tool 注解，写清楚 name 和 description——LLM 就是靠这个理解工具的。第三步：如果是 FIXED 工具，ToolFacadeService 里注册一下；如果是 OPTIONAL，在 Agent 配置的 allowedTools 里加上。

> 不用改 AgentCore、不用改 ToolExecutor——它们在 Factory 阶段通过 MethodToolCallbackProvider 自动发现所有 @Tool 方法。

### Q: 你提到有可能工具失败恢复导致 LLM 产生幻觉，怎么理解？

> 如果工具返回了"我失败了，原因是连接超时"，LLM 理论上应该如实告诉用户。但如果 LLM 选择性地忽略了失败信息，或者把失败信息"润色"成了似是而非的结果——比如"数据库中不存在这条记录"被 LLM 理解成了"数据库返回空"——这就是恢复机制可能引入的幻觉风险。

> 目前的做法是失败消息的结构化程度很高，exceptionClass 和 exceptionMessage 都是精确字符串，不太容易被误解。但要完全消除这个风险，需要做更严格的输出校验。

### Q: 如果面试官问"你们这个三层恢复和 Kubernetes 的 restart/retry 有什么区别"？

> K8s 的重启是 Pod 级别的——整个进程挂了就重启。我的三层恢复是方法级别的——工具调用失败不意味 Agent 进程要重启，而是在同一个进程里做精细化的恢复。K8s 不会知道"这个工具超时了要等 500ms 再试"，它只会无脑重启。

> 两者是互补的——我的恢复机制处理应用层的故障，K8s 处理基础设施层的故障。如果整个 Pod 因为 OOM 被 kill 了，K8s 会重启，重启后 L3 冷存储能恢复之前的对话状态。
