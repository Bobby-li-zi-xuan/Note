# 05 · 技术选型与架构决策

## 一、决策全景

```
技术选型决策树

"做什么？" ── Agent 对话系统 ──→ Spring Boot + Java 23
"怎么调 LLM？"              ──→ Spring AI 1.1.0（统一多模型接口）
"怎么存向量？"              ──→ PostgreSQL + pgvector（零新组件）
"怎么查向量？"              ──→ MyBatis + PgVectorTypeHandler
"怎么做缓存？"              ──→ Caffeine（高性能本地缓存）
"怎么做 Embedding？"        ──→ Ollama + bge-m3（本地免费）
"怎么推送状态？"            ──→ SSE（单向实时流）
"怎么管理工具？"            ──→ 双层 Tool 体系 + @Tool 注解
```

## 二、关键决策详解

### 决策 1：为什么自己编排 Agent 循环

**背景**：Spring AI 提供了自动工具执行能力，`internalToolExecutionEnabled=true` 时一次调用完成 think + execute。

**方案对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| 使用 Spring AI 自动执行 | 代码少、框架保证正确性 | 中间插不进业务逻辑 |
| 自己编排 think/execute | 完全控制流程、可插入持久化/推送/容错 | 需要自己管理 Prompt 和工具回调 |

**决策**：自己编排。

**为什么**：Agent 不只是"调 LLM + 执行工具"。真正的生产系统需要在 LLM 决策和工具执行之间插入消息持久化、SSE 状态推送、缓存 checkpoint 和失败恢复。如果用自动执行，这些逻辑无处安放。

**后果**：
- 收益：完整的流程控制权，后续加的每一项能力（失败恢复、缓存、统计）都受益于这个决策
- 代价：多写了 ~200 行编排代码，需要正确管理 think/execute 之间的状态传递

### 决策 2：为什么用 pgvector 而不是专用向量数据库

**背景**：RAG 的核心是向量相似度检索，市面上有 Milvus、Pinecone、Weaviate 等专用方案。

**方案对比**：

| 方案 | 检索性能 | 运维复杂度 | 数据一致性 | 扩展性 |
|------|---------|-----------|-----------|--------|
| pgvector | 中等（十万级够用） | 零额外运维 | 天然事务一致 | 受限于 PostgreSQL |
| Milvus | 高（百万级以上） | 需独立部署和维护 | 需自己保证 | 水平扩展好 |
| Pinecone | 高 | 零运维（托管服务） | 需自己保证 | 无限扩展 |

**决策**：pgvector。

**为什么**：
1. 当前数据规模是千到万级，pgvector 完全够用
2. 不需要引入新组件——PostgreSQL 已经在用了，pgvector 只是一个扩展
3. 混合查询是天然优势——向量检索 + 元数据过滤可以写在一个 SQL 里
4. 如果未来规模增长到百万级，pgvector 的查询性能会显著下降，届时再迁移

**迁移路径**：MyBatis Mapper 层已经把 SQL 封装好了，换向量数据库只需改 Mapper 实现，不影响上层服务。

### 决策 3：为什么用 Caffeine 而不是 Redis

**背景**：需要一层会话级缓存来加速上下文恢复，同时需要 TTL 和淘汰策略。

**方案对比**：

| 方案 | 延迟 | 运维 | 淘汰策略 | 持久化 |
|------|------|------|---------|--------|
| Caffeine | <1μs（进程内） | 零 | W-TinyLFU | 无（需自己加） |
| Redis | ~1ms（网络 IO） | 需独立部署 | LRU/LFU | 内置 RDB/AOF |

**决策**：Caffeine。

**为什么**：
1. 单实例部署，不需要分布式缓存
2. Caffeine 的 W-TinyLFU 淘汰策略在单机场景优于 Redis 的 LRU
3. 零运维成本
4. 如果以后需要多实例共享缓存，可以在 Caffeine 外面加一层 Redis，不影响现有接口

### 决策 4：为什么用 Ollama 做本地 Embedding

**背景**：需要对中文文本做向量化，可选方案包括：OpenAI Embedding API、智谱 Embedding API、本地模型。

**方案对比**：

| 方案 | 成本 | 延迟 | 中文质量 | 可控性 |
|------|------|------|---------|--------|
| OpenAI text-embedding-3 | 按 token 计费 | ~100ms | 中等 | 低（依赖外部服务） |
| 智谱 Embedding | 按调用计费 | ~100ms | 高 | 低 |
| Ollama bge-m3 本地 | 免费 | ~200-500ms | 高 | 高 |

**决策**：Ollama + bge-m3。

**为什么**：
1. 中文 embedding 质量高，bge-m3 在中英文混合场景表现优秀
2. 零 API 费用——知识库有几万条 chunk 的话，嵌入费用也是可观的
3. 延迟可接受——单次 embedding 200-500ms，对查询场景来说不构成瓶颈

**代价**：需要本地 GPU 或内存跑 Ollama，部署时多一个服务依赖。

### 决策 5：为什么用 MyBatis 而不是 JPA

**背景**：数据访问层的选择。

**方案对比**：

| 方案 | SQL 控制 | 学习曲线 | 复杂查询 |
|------|---------|---------|---------|
| JPA/Hibernate | 自动生成，黑盒 | 中等 | JPQL 受限 |
| MyBatis | 手写 SQL，完全控制 | 低 | 任意复杂 |

**决策**：MyBatis。

**为什么**：
1. pgvector 的 `<->` 操作符需要手写 SQL，JPA 不支持
2. 向量类型 `float[]` 需要自定义 TypeHandler，MyBatis 的扩展机制更直观
3. 项目中有多表关联和聚合查询，XML Mapper 管理 SQL 更清晰

### 决策 6：为什么用 SSE 而不是 WebSocket

**背景**：Agent 执行过程中需要实时推送状态和流式文本到前端。

**方案对比**：

| 方案 | 方向 | 复杂度 | 适用场景 |
|------|------|--------|---------|
| SSE | 服务端 → 客户端单向 | 低 | 实时推送进度和结果 |
| WebSocket | 双向 | 中 | 实时聊天、协同编辑 |
| 轮询 | 客户端 → 服务端 | 低 | 低频状态查询 |

**决策**：SSE。

**为什么**：
1. Agent 执行是单向推送——服务端告诉前端当前状态，前端不需要主动向服务端发消息
2. SSE 比 WebSocket 更轻量——基于 HTTP，不需要升级协议，不需要心跳维护
3. 浏览器原生支持 EventSource API，前端代码简洁

### 决策 7：冷存储的 database vs file 双后端

**背景**：记忆和对话历史需要持久化，不同部署环境可能有不同偏好。

**设计**：

```java
// 策略模式：通过配置文件切换
ragagent.cold-storage.type: database  // 或 file

// 接口抽象
public interface MemoryColdStorageGateway {
    List<Message> loadConversationHistory(String sessionId, int limit);
    List<MemoryEntry> loadMemoryEntries(String sessionId);
    void save(MemoryEntry entry);
    void saveMessages(String sessionId, List<Message> messages);
}
```

- `database` → `DbMemoryColdStorageGateway`：存 PostgreSQL `memory_cache` 表
- `file` → `FileBasedMemoryColdStorageGateway`：存本地 JSON 文件

**为什么**：
1. 开发环境用 file 模式省去数据库配置
2. 生产环境用 database 模式保证可靠性和一致性
3. Spring 的条件注入 (`@ConditionalOnProperty`) 自动切换，代码零侵入

## 三、架构演进路线

当前架构的下一步演进方向：

### P1：LLM 辅助摘要
- 现状：规则摘要，成本零但质量中等
- 方案：默认规则，检测到话题重大变化时触发一次 LLM 摘要
- 预期：摘要质量提升，每轮额外延迟 0-3 秒

### P2：USER 级记忆共享
- 现状：记忆按 sessionId 隔离，跨会话不共享
- 方案：增加 USER 级别的 MemoryScope，同用户不同会话共享 preferences 和 facts
- 预期：Agent 能记住用户偏好，体验更连贯

### P3：向量检索优化
- 现状：pgvector L2 距离 + 固定 candidateLimit
- 方案：IVFFlat 索引 + 自适应 candidateLimit（根据查询复杂度动态调整）
- 预期：大数据量下检索性能提升 5-10x

### P4：工具执行并行化
- 现状：多个工具串行调用
- 方案：无依赖关系的工具调用并行执行
- 预期：多工具场景延迟降低 50%+

## 四、面试问答

### Q: 整个项目中，你觉得哪个技术决策最"正确"？

> 我觉得是关掉 Spring AI 自动工具执行，自己编排 think/execute 两阶段。这个决策当时看是多写了一些代码，但后续加的每一项能力——消息持久化、SSE 推送、缓存 checkpoint、失败恢复——都因为这个决策而变得自然。如果当初用了自动执行，后面每个需求都要想"怎么绕过去"，架构会越来越扭曲。

### Q: 哪个决策你现在觉得可能需要重新考虑？

> 用规则做增量摘要。当时选规则是因为快、免费，但现在回头看，摘要是记忆系统的核心——它决定了 LLM 在每轮对话中能看到什么。规则摘要的质量波动太大，如果对话比较复杂，可能会漏掉关键信息。

> 如果重来一次，我会做一个混合策略——默认用规则摘要，但让 LLM 定期（比如每 5 轮）做一次语义检查。如果 LLM 认为规则摘要遗漏了重要内容，就追加一条补充摘要。这样能把 LLM 调用的频率控制在可接受范围，同时保证摘要质量。

### Q: 为什么选 DeepSeek 和智谱这两个模型？

> 最初选型时考虑几个因素。一是 API 价格——这两个国产模型的 API 费用远低于 OpenAI。二是中文能力——它们在中文任务上表现不错。三是 Spring AI 的官方 starter——两个都有，集成成本很低。

> 选两个模型而不是一个，是为了做模型能力的分工——DeepSeek 推理强，适合复杂的决策和工具规划；智谱在中文理解和生成上更自然，适合用户对话。Agent 配置里可以按用途指定模型。

### Q: 如果面试官问"你会怎么评估这套系统的质量"，你怎么答？

> 我分四个维度来看。第一是检索质量——用 precision@K 和 recall@K 衡量 pgvector 返回的结果有多相关。第二是 Agent 对话质量——用 TTFT 和步骤数衡量响应速度和效率，用工具成功率衡量调用的可靠性。第三是缓存效果——用 Caffeine 的 hit/miss rate 衡量 L2 的价值。第四是记忆质量——用增量摘要和历史摘要的 Jaccard 相似度衡量摘要的一致性。

> 这四个维度的测试我都写了，在 metrics 测试套件里。

### Q: 项目架构中最大的取舍是什么？

> 最大的取舍是"简单性 vs 完备性"。举个例子——冷存储有两种后端（database 和 file），摘要有两种方式（全量和增量），工具有两种类型（FIXED 和 OPTIONAL）。加这些灵活性确实让架构更复杂了，但每个"灵活性"背后都有一个真实的需求场景。

> 我的原则是：只在有明确需求时才加灵活性，不做"以防万一"的设计。比如 database/file 双后端是因为我自己在开发环境下不想配数据库，而不是"万一将来有人不想用数据库"。有具体疼痛点才做设计决策。

### Q: 你提到了 pgvector 的混合查询优势，能举个具体例子吗？

> 比如这个查询："查知识库 A 中与 query 最相似的 chunk，但排除标题中含有'附录'的，最近一周创建的优先"。如果用 pgvector，一个 SQL 搞定——WHERE 条件里同时做向量距离过滤和元数据过滤。如果 Milvus，你需要先做向量检索拿到 ID 列表，再去数据库里做元数据过滤。多一次来回，延迟就上去了。

### Q: Caffeine 和 Redis 可以共存吗？你会怎么设计？

> 可以共存——Caffeine 做 L1 本地缓存，Redis 做 L2 分布式缓存，PostgreSQL 做 L3 冷存储。查询路径是 Caffeine → Redis → PostgreSQL。这样的好处是单实例时 Caffeine 够快，多实例时 Redis 保证一致性。

> 当前项目不需要这个复杂度——单实例部署就够了。但 MemoryCacheManager 接口已经定义好了，如果以后要加 Redis，实现一个新的 `RedisMemoryCacheManager` 就行，上游 AgentCore 不用改。

### Q: 如果面试官问"这个系统最大的瓶颈在哪"，你怎么答？

> 目前最大的瓶颈是 embedding 调用。Ollama 跑在本地的 bge-m3 是纯 CPU 推理，单次 embedding 200-500ms，如果并发查询多的话会排队。

> 解决方案有几个层次：一是换 GPU 推理，延迟能降到几十毫秒；二是加 embedding 结果缓存——常用查询的 embedding 可以复用；三是如果量真的很大，考虑换 API 服务（比如 OpenAI embedding），牺牲成本换延迟。

> 其次是 pgvector 的检索性能——十万级以内没问题，但如果 chunk 量上到百万级，IVFFlat 索引的查询速度会明显下降。不过这是好问题——意味着产品成功了，需要 scale 了。

### Q: 有什么是你想做但还没做的？

> 一是流式工具输出。当前 LLM 的回复是流式的，但工具调用结果是整个返回的。如果工具是一个长时间运行的任务，用户应该能看到中间进度。这需要在 ToolResponse 里加一个流式通道。二是多 Agent 协作。当前是一个 Agent 和一个用户对话，但更复杂的场景可能需要多个 Agent 分工——一个专门检索、一个专门分析、一个负责输出——类似于 MapReduce 的模式。

### Q: 你觉得做一个好的 RAG 系统，最关键的三件事是什么？

> 第一是 chunk 策略——怎么切决定了检索的天花板。切得太碎没有上下文，切得太大检索精度下降。第二是检索质量——不只是向量相似度，还要考虑去重、排序和预算控制，把最相关的找出来并且不要浪费 token。第三是评估体系——没有评估就没法优化。你需要知道你的检索命中率是多少、误召回率是多少，才能针对性地调参。
