## 一、项目总览

### Q1:介绍一下系统的整体架构，核心模块的职责划分是怎么样的，为什么选择SpringAI作为基础框架？

##### 整体架构
当前项目的架构主要有三层，最上层主要就是通过SSE与前端连接，进行消息推送。往下一层就是控制层，负责处理前端传来的请求，然后交给服务层来进行一些编写好的业务逻辑，服务层有三个**最核心的模块**分别是Agent引擎、RAG检索、和记忆缓存系统，然后最底层是数据层。

---

### Q2: 能详细说明一下Think-Executor循环机制的执行流程吗

##### Think-Executor循环
- **Think阶段**
>核心任务是让大模型判断当前用户问题是否需要调用工具，以及需要调用什么工具
1. 构建**决策命令提示词**：告诉大模型有哪些工具可以调用、当前可用的知识库列表以及对应描述，同时把会话缓存中保存的摘要、事实、约束等信息信息也传入
2. 系统会获取当前的完整对话历史（根据滑动窗口大小设置，当前为十条消息），构建一个Prompt对象，将对话历史一起发送给大模型
3. 大模型决策完后会返回一个消息对象，当模型认为不需要工具时，toolcalls列表为空，此时系统会把模型的回复直接推送给前端，同时把这条回复加入记忆。如果模型认为需要调用工具，toolCalls列表会包含具体的工具名称和参数，系统返回true来告诉上层需要进入执行阶段

> [!NOTE] 完整的对话历史包括哪些内容？
> 1. 系统提示词：包括基础规则和上下文约束
> 2. 冷储存恢复的历史消息
> 3. 滑动窗口内的近期消息
> 4. 工具调用相关的消息对；模型消息和工具调用响应消息必须成对出现，一个单个出现则丢弃另外一个，防止滑动窗口截断后导致大模型获取不到工具调用而报错

- **Executor阶段**
>执行工具调用，并把结果加入对话历史。
1. 系统先保存当前的对话历史快照，然后使用一个与think（）相同的对话历史构造Prompt对象，再把think()阶段的模型响应作为参数传入
2. execute()内部构建一个工具调用管理器，里面绑定了think()阶段识别到 所有可用工具。管理器会解析模型响应中的工具调用请求，根据对应工具名称找到对应的ToolCallback，然后在ToolCallback中执行工具逻辑，获取工具执行结果，最后构造包含结果的工具响应消息，并返回完整的对话历史
3. 工具执行过程中如果失败会进入失败回复机制
4. 执行完成后，系统返回完整的对话历史**整体替换**当前的对话记忆（不是简单追加，保证历史消息的一致性和完整性）。最后系统会检查这轮对话是否真的发生了变化，如果发送变化就标记缓存为脏状态，为后续的缓存更新做准备
- **执行结束后进行会话缓存管理**
1. 系统进行会话缓存的检查点更新，首先判断缓存是否被标记为脏，然后计算增量起始位置，增量指的是上次检查点之后的新消息范围。
2. 接下来使用增量摘要器对新增消息进行处理，提取出摘要、事实、约束、工具调用等，然后与已有的缓存进行合并，按类型和版本进行管理
3. 最后写回内存缓存管理器，更新检查点

> [!NOTE] 系统如何判断出这轮对话是否发送变化？
> 1. 通过消息类型和文本内容为每条消息构建指纹，通过对比指纹判断
> 2. think阶段大模型返回了非空文本内容
> 3. think阶段检测到有工具调用
> 4. 工具执行的回调中，工具响应产生



---

### Q3: 为什么不用 Spring AI 的自动工具执行？

A: 因为自动执行会把“是否调用工具”“怎么执行工具”“失败后怎么办”混在一起，不利于插入业务逻辑。当前实现关闭了 `internalToolExecutionEnabled`，改成自己管理 think / execute 两阶段，这样可以在中间插入：

- 会话持久化
- SSE 状态推送
- 失败恢复和重试
- 记忆刷新与冷存储刷盘
- 工具统计和审计日志

这也是当前项目中最重要的编排边界之一。

## 二、RAG 检索

### Q4: 文档是怎么切块和入库的？

A: 文档入库流程是：

```
Markdown 文档
  → MarkdownParserService.parseMarkdown()
  → MarkdownSection 列表
  → MarkdownChunkComposer.compose(title, body, maxTokensPerChunk)
  → 每个 chunk 调用 embedding
  → 写入 chunk 表
```

切块时优先保证语义完整：

1. fenced code block 和表格行视为原子块
2. 以段落边界切分
3. 段落太长再按句末标点切分
4. 仍超长时才退化为固定长度切分

当前默认 token 上限是 800 左右的 chunk 粒度，知识库检索默认最多召回 8 个候选块，再按上下文预算筛掉低相关内容。

---

### Q5: 检索流程和上下文裁剪是怎么做的？

A: 检索流程是：

```
query
  → embedding
  → pgvector 相似度检索
  → candidate limit 召回
  → token budget 裁剪
  → 返回 chunk 文本列表
```

当前实现的特点：

- 使用 pgvector 的距离操作符做相似度排序
- 默认候选数是 8
- 默认上下文预算是 1200 tokens
- 预算不足时会从后向前丢弃低优先级块

这比“直接把所有召回结果塞进 prompt”更稳，也更适合中文知识库场景。

---

### Q6: 为什么要按标题前缀保存 chunk？

A: 因为单独的正文切块会丢失上下文层级。当前 chunk 会携带章节标题前缀，模型在看到检索结果时更容易理解块与块之间的层级关系，也更容易在答案里引用正确的小节。

这个做法对面试可以这样说：**不是为了让文本更长，而是为了让检索出的每个局部片段保留结构语义。**

## 三、工具调用

### Q7: 工具是怎么接入 Agent 的？

A: 当前是“双层工具体系”：

| 层次 | 作用 |
|------|------|
| 业务层 Tool 接口 | 控制工具是 FIXED 还是 OPTIONAL，决定 Agent 装配时是否加载 |
| Spring AI `@Tool` | 把具体方法暴露成模型可调用的 ToolCallback |

`RAGAgentFactory.create(...)` 会根据 agent 配置、工具类型和允许列表组装最终的 `ToolCallback[]`，再交给 `DefaultToolExecutor`。

---

### Q8: 工具调用失败现在是怎么处理的？

A: 这是当前刚补齐的重点能力。工具失败不再是简单抛异常，而是一个“有限重试 + 大模型决策 + 安全兜底”的闭环。

#### 处理顺序

1. **快速重试**：先处理超时、连接中断等可恢复错误
2. **模型介入**：如果快速重试仍失败，构造结构化失败上下文，让模型决定下一步策略
3. **安全兜底**：如果模型也失败，或明确要求停止，则合成 `ToolResponseMessage` 返回给上层

#### 失败上下文包含什么

1. **toolName**
- 含义 : 被调用的工具名称
- 作用 : 标识是哪个工具失败了，用于日志和决策
2. **toolArguments**
- 含义 : 传递给工具的参数（JSON 格式字符串）
- 作用 : 记录失败时的入参，便于排查问题和重试
3. **failureStage**
- 含义 : 失败发生的阶段
- 取值 :
	- EXECUTE - 工具执行阶段失败
	- RETRY - 快速重试阶段失败
	- POLICY_RETRY - 策略重试阶段失败（budget > 0）
- 作用 : 区分失败发生的位置，帮助决定后续处理方式
4. **exceptionClass**
- 含义 : 异常的完整类名（root cause）
- 作用 : 判断异常类型，用于决定是否可重试
5. **exceptionMessage**
- 含义 : 异常的简短描述信息
- 作用 : 提供异常的具体原因，便于调试
6. **retryCount**
- 含义 : 当前已重试的次数
- 作用 : 结合 maxRetries 判断是否达到重试上限
7. **retryable**
- 含义 : 该异常是否可重试
- 作用 : 由 isRetryable(rootCause) 判断，某些异常（如网络超时）可重试，而参数错误等不可重试
8. **lastDelayMs**
- 含义 : 上次重试的延迟时间（毫秒）
- 作用 : 用于计算退避策略（如指数退避）
9. **toolCallIndex**
- 含义 : 工具调用的索引序号
- 作用 : 标识是哪一次工具调用，用于前端展示和结果对应

#### 模型可以返回什么

1. RETRY
含义 : 简单重试
- 使用快速重试机制，不咨询大模型
- 带有固定或指数退避（ backoffMultiplier ）
- 通常用于瞬时故障（如网络抖动）
2. RETRY_WITH_POLICY
含义 : 带策略的重试
- 由大模型决策后返回的重试方式
- 会重新设置 policyRetryBudget 、 initialBackoffMs 、 backoffMultiplier
- 模型会根据 failureStage 、 exceptionClass 等信息决定重试参数
3. DEGRADE
含义 : 降级处理
- 不再重试当前工具
- 可能返回降级结果（如兜底数据、降级响应）
- 让 Agent 继续工作，只是功能受限
4. STOP
含义 : 停止执行
- 完全放弃当前工具调用
- 返回失败信息给上层
- 不会再次重试

#### 关键约束

- 快速重试有上限
- 允许的模型咨询次数有上限
- 退避时间有下限和上限
- `RETRY_WITH_POLICY` 可以重置重试窗口，但不会无限循环
- 合成失败消息时会保留原始 `baseHistory`

#### 面试时怎么讲

你可以把它概括成一句话：**工具失败不是直接失败，而是先做技术层快速重试，再让模型做策略决策，最后才回落到带结构化错误信息的兜底消息。**

---

### Q9: 为什么要把失败信息反馈给大模型？

A: 因为很多失败不是纯技术故障，而是“策略不合适”或“参数不合适”。比如：

- 目标工具需要更小的重试窗口
- 某个工具当前不可用，可以切换到降级路径
- 同一类请求连续失败时，应停止重试，避免浪费配额

把失败上下文反馈给模型后，模型可以根据上下文决定是继续重试、换策略、降级，还是直接停止。这比固定规则更灵活，也更符合 Agent 的语义。

---

### Q10: 为什么要区分 `RETRY` 和 `RETRY_WITH_POLICY`？

A: 因为这两个动作语义不同：

- `RETRY`：只想再试几次，适合短暂网络抖动
- `RETRY_WITH_POLICY`：希望同时调整重试策略，比如扩大重试窗口、修改退避时间、改变模型咨询意愿

如果不区分，模型只能返回“重试”这种粗粒度指令，程序层就无法表达“继续试，但要改变节奏”的意图。

## 四、缓存与持久化

### Q11: 三层缓存分别做什么？

A: 当前是三层协同：

| 层级 | 组件 | 作用 |
|------|------|------|
| L1 | ChatMemory / MessageWindowMemoryImpl | 保存会话的原始消息窗口 |
| L2 | Caffeine Cache / MemoryCacheManager | 保存结构化记忆快照 |
| L3 | 数据库冷存储 | 保存长期持久化数据，负责恢复兜底 |
##### L1
>基于JVM堆内存存储，使用滑动窗口策略管理对话消息
- **设计目的**：保存窗口内的完整对话历史，供模型读取，默认窗口大小为10条
- **数据一致性策略**：初始化时从L3冷储存恢复历史消息。运行过程中不断追加新的消息。当工具执行完成后，会调用方法整体替换，确保L1与SpringAI内部维护的消息历史保持一致，保证消息完整性

##### L2
>基于JVM级别的内存缓存，使用Caffeine作为实现
- **设计目的**：在L1之外提供一层更加轻量的记忆抽象，储存的是对话内容的结构化摘要，包括：摘要、事实、约束、工具调用，在think()阶段被注入到提示词中，帮助模型做出决策，而无需传入完整历史，节省上下文
- **数据一致性**：更新采用增量检查点检查，当AgentCore检查到dirty标记时，会执行检查检查点操作：计算增量消息的起始位置，对增量消息进行摘要，然后与现有缓存进行合并，合并过程中采用jaccard去重。当L2起始为空时，会快速对已经恢复好的L1做一次完整摘要，作为初始快照写入L2.同时也支持从冷储存刷新之前的摘要记录

##### L3
>作为冷储存将缓存数据持久化到数据库中
- **设计目的**：实现记忆的持久化和跨会话共享
- **数据一致性**：采用异步写回策略，不会每次对话变化时写入。写回操作有一个服务类统一管理，该类会维护一个缓冲区，缓冲区达到一定规模时才将数据批量写入数据库，减少数据库压力

---

### Q12: Agent 执行失败时，为什么不会丢历史？

A: 因为 `AgentCore.run()` 的外层会在 `finally` 里刷写缓存和会话数据。也就是说，即使中间出现异常，前面已经产生的消息和缓存变更仍然会被保存，避免整个会话因为一次失败而丢失上下文。

这也是当前项目在工程上比较稳的一点。

## 五、前端与消息推送

### Q13: 前端是怎么实时看到 Agent 结果的？

A: 通过 SSE。后端在 Agent 状态变化时发送 `AI_PLANNING`、`AI_THINKING`、`AI_EXECUTING`、`AI_DONE` 等事件，前端建立长连接后可以实时接收状态和回复内容。

对用户来说，这意味着：

- 请求不会卡住在一个静默等待页
- 工具调用过程能看见
- 出错时可以尽早感知
- 流式输出和最终结果都能同步展示

---

### Q14: 工具失败时前端会看到什么？

A: 如果失败被恢复掉，前端通常只看到正常的工具结果或降级结果；如果最终进入兜底消息，则会收到结构化的失败内容。若是模型或系统层面不可恢复的异常，Agent 会进入 ERROR 状态，前端会收到错误状态通知。

关键区别是：**恢复成功时，用户感知到的是“功能继续工作”；恢复失败时，用户感知到的是“系统明确失败，而不是悄悄吞掉”。**

### Q16: 基于反射机制将SpringBean动态注册为AI可用算子，这个注册的具体实现逻辑是什么？怎么处理工具参数的类型校验、参数映射
##### 注册的实现逻辑
1. 当用户发起对话请求，系统会首先查询该用户关联的Agent配置，然后由工厂类完成Agent运行时的组装工作，此时会把业务层定义的各种工具转换为AI框架能够调用和识别的格式
2. 工具工厂类获取已经注册的工具实例，加载到工具列表中
3. 反射机制主要用于扫描工具类，可以遍历类的所有方法，识别到带有@Tool注解的方法，然后进一步读取方法的详细信息，系统据此生成工具定义告诉大模型该工具的作用、所需参数、参数类型等
4. 当模型决定调用某个工具时，系统根据工具名称在已经注册的工具列表中找到对应的方法对象，然后通过反射调用这个方法，调用过程中，反射负责将JSON格式的参数反序列化为JAVA对象参数传入方法，执行方法并获取到返回值

##### 完整流程分四个阶段
1. 注册（启动时）：每个工具类标注 @Component ，Spring Boot 启动时扫描到这些类后将类的实例自动注册为 Bean。当ToolRegistry的构造函数声明List<Tool>参数时，Spring会将所有工具Bean注入
2. 解析（Factory 构造时） ： Agent工厂在创建Agent时，合并固定工具和可选工具，再调用 buildToolCallbacks() 用 MethodToolCallbackProvider **反射**扫描每个 Tool 对象的 @Tool 方法，生成 ToolCallback[] 存入 AgentContext 上下文供大模型选择。ToolCallback 包装了一个 @Tool 方法，包含方法名、描述和参数 schema。传给 ChatClient.toolCallbacks() 后，LLM 会看到这些工具的说明，决定是否调用以及怎么构造参数。
3. 选择（Think 阶段） ：把 ToolCallback[] 传给 ChatClient ，LLM 根据对话上下文决定是否调用工具，返回带 toolCalls 的 AssistantMessage 。
4. 调用（Execute 阶段） ： ToolCallingManager 根据 toolCalls 中的方法名通过 StaticToolCallbackResolver 找到对应的 ToolCallback ，调用 MethodToolCallbackProvider 通过**反射**执行真实的 @Tool 方法，返回 ToolResponseMessage ，拼入对话历史。

##### 参数的类型校验
1. 当大模型看到工具定义时，会根据参数描述生成符合要求的JSON参数，Spring AI会将生成的参数字符串与Java方法的参数类型进行匹配，不匹配则会报错
2. 方法内部对参数进行严格校验

### Q18:SSE的全异步流式响应怎么实现的，多会话隔离和断线重连机制的实现逻辑。Agent状态实时透传如何实现，怎么处理长连接的稳定性问题
**SSE 全异步流式响应** ：我用 Spring 的 SseEmitter 实现，核心是一个 ConcurrentHashMap<chatSessionId, SseEmitter> 按会话隔离连接。流式输出通过分块发送实现——把 LLM 返回的内容按 12 个 Unicode 码点拆分，每块间隔 30ms，模拟打字机效果。

**多会话隔离** ：每个会话有独立的 SseEmitter 和 MessagePublisher ，通过 chatSessionId 作为 key 隔离。 AgentCore 每次构造时都会注入当前会话的 publisher，所以不同会话的消息不会串扰。

**断线重连** ：消息先持久化到数据库（ ChatMessageFacadeService ），断线后前端重新连接时，后端从数据库加载历史消息，通过 sendPendingMessages() 补发到前端。

**Agent 状态实时透传** ：在 think() 和 execute() 的每个阶段调用 publisher.sendStatus() ，发送 AI_PLANNING 、 AI_THINKING 、 AI_EXECUTING 、 AI_DONE 四种状态，前端根据这些状态显示不同的 UI。

**长连接稳定性** ：SSE 发送失败不会打断 Agent 主流程，用 try-catch 捕获后只打印 debug 日志。连接超时设置 30 分钟，并且有 onTimeout 、 onError 、 onCompletion 三个回调自动清理资源。
