## 第一层：项目整体与架构设计

### Q1: 你为什么选择 LlamaIndex 而不是 LangChain 或直接使用原生接口？

**你可以这样回答：**

说实话，选型的时候我们确实对比了这三种方案。

先说结论：我选 LlamaIndex，核心原因就一句话——**LlamaIndex 是专门为 RAG 场景设计的，而 LangChain 想做 Agent 框架，原生接口又太底层了，开发成本太高。**

展开来说，有四个关键点。

第一，**LlamaIndex 的 IngestionPipeline 特别适合我们的文档入库流程**。文档解析、分块、向量化、入库，这一套流程你用原生接口得手写循环，但 LlamaIndex 只需要声明一个 pipeline，把 transformation 列表定义好就行了，代码量至少省了一半。具体来说，IngestionPipeline 内部会自动遍历 transformation 列表，先调用自定义分块器的解析方法对每个文档按策略切分，生成带唯一节点 ID 和继承元数据的文本节点，然后自动调用全局配置的嵌入模型为每个节点生成一千零二十四维的稠密向量，最后通过向量存储适配器批量写入 Qdrant。整个过程是异步的，你只需要调用 run 方法，框架自动完成数据流转。

第二，**它的 RetrieverQueryEngine 抽象非常清晰**。retriever → postprocessor（就是我们用的 reranker）→ response\_synthesizer（LLM 生成），整条链路每一个环节都可以独立替换。我们做实验的时候，把 retriever 从 dense 换成 hybrid，只需要改一行配置。具体来说，检索引擎接收查询包对象，调用自定义混合检索器的异步检索方法，内部并行执行稠密向量检索（前20条）和 BM25 稀疏检索（前20条），两路结果通过 RRF 算法融合排名取前15条，然后交给重排序器进行 Cross-Encoder 精排，取前5条结果，最后由树形摘要合成器将检索到的文本块与用户问题组合成提示词，交给大语言模型流式生成答案。

第三，**Node 模型统一**。所有文档最后都变成 TextNode，有 node\_id、text、metadata，不同组件之间不需要做数据格式转换。这个看起来是小事，但实际开发中省了很多坑。无论是分块器输出的节点、嵌入模型处理后的节点、检索器召回的节点，还是重排序器打分后的节点，都遵循同一套数据结构，组件之间传递数据时不需要做任何格式适配。

第四，**原生支持异步**。aretrieve、aquery 全链路 async，跟 FastAPI 天然契合。如果用原生接口，异步这块得自己从头写。从文档入库的 pipeline 异步执行，到检索阶段的异步召回、异步重排、异步流式生成，整个链路不需要自己管理事件循环或线程池。

第五，**全局 Settings 单例管理**。嵌入模型、大语言模型、回调管理器都通过全局配置对象统一管理，所有组件共享同一套模型实例，避免重复初始化。比如嵌入模型在应用启动时加载一次，后续分块阶段的向量化和检索阶段的查询编码都复用同一个实例。

第六，**可观测性支持**。通过回调管理器可以追踪检索、生成等各类事件的耗时和结果，我们在回调处理器中捕获这些事件，输出 Prometheus 指标，比如查询延迟、检索文档数量等，方便监控和调优。

**那 LangChain 呢？** LangChain 最大的问题在于它的 Chain 抽象对纯 RAG 太重了，引入了很多不必要的中间层。而且它的 Document Loader 和 Text Splitter 对中文支持不太好，我们踩过坑。

**原生接口呢？** 代码量至少翻倍，关键是后续要加新的检索策略，比如 HyDE、多查询，得从头写，太痛苦了。

**【可能的追问】LlamaIndex 有什么缺点？**

当然有。主要是三个问题。

第一，**抽象层太深了**。排查问题的时候，一个简单的检索调用可能要跳五六层抽象，特别痛苦。我的做法是，关键路径直接继承 BaseRetriever 重写 \_aretrieve 方法，绕过高层抽象，出了问题自己能把控。

第二，**中文分块不够灵活**。它自带的 SentenceSplitter 对中文标点的支持有限。所以我实现了一个自定义的分块器，支持句子、段落、标题、字符四种策略，还可以选语义分块。

第三，**性能开销**。高层抽象必然带来函数调用开销。对于性能敏感的路径，比如批量检索，我直接用 asyncio.gather 并行执行，绕开 LlamaIndex 的串行编排。

### Q2: 这个 RAG 模块主要服务哪些业务场景？对实时性、准确性、数据量的要求分别是什么？

**你可以这样回答：**

我们这个模块主要服务三类场景。

第一类是**企业内部知识检索**，比如产品文档、技术手册、FAQ 的智能问答。第二类是**客服辅助**，基于历史工单和产品文档帮客服快速找到答案。第三类是**研发文档检索**，比如 API 文档、架构文档的语义搜索。

**各项要求上：**

实时性方面，我们定的目标是查询 P99 小于 5 秒。实现上用了三层保障：TTLCache 缓存高频查询，dense 和 BM25 并行检索，Qdrant 的 HNSW 索引保证 O(logN) 的检索速度。

准确性方面，NDCG\@5 目标 0.85 以上。靠的是三段式架构：dense 粗排20条 + BM25 粗排20条 → RRF 融合取前15条 → Cross-Encoder Reranker 精排取前5条 → LLM 生成。

数据量方面，当前单知识库支撑万级文档，用的是 HNSW 索引加按知识库 Collection 隔离的方案。

可用性方面，目标是 99.9%。主要靠全链路的降级策略，比如 sparse 不可用了自动退到 keyword 检索，HyDE 失败就直接用 dense 检索，始终保证服务可用。

**【可能的追问】如果数据量到百万级，架构怎么调整？**

好问题。当前每个知识库一个 Collection，百万级的话需要按时间或者业务域进一步拆分。Qdrant 要切换到分布式模式，数据分片到多个节点。Embedding 服务也要独立部署，不能再用 Ollama 单机扛了。缓存要从进程内 TTLCache 升级到 Redis 分布式缓存。另外，增量索引也得做上，当前是全量写入，百万级肯定不行。

### Q3: 描述一下整体数据流？

**你可以这样回答：**

这个系统的数据流分两段：离线文档处理流程和在线检索流程。

**完整的文档入库流程**

1. **用户上传文件**，FastAPI接收，再按页提取文件内容，转为bytes类型
   - 支持批量上传，并发最多为5
2. **文档解析**：bytes会被写入临时文件，通过 `detect_file_type()` 检测文件格式（优先级：Magic Number → 内容嗅探 → 扩展名兜底），路由到对应解析器（PDF/DOCX/MD/TXT/HTML），解析完成后临时文件会被删除。然后按照识别到的格式解析文件
- 输出格式 ： \[{"text": "...", "metadata": {"page": 1, "source": "...", ...}}, ...]

3. **文档清洗**：对解析后的文本片段进行规范化处理
   - **空白规范化**：合并空行、去首尾空白、去控制字符/零宽字符
   - **标记去除**：去除 HTML/XML 标签和 Markdown 标记（标题、粗体、斜体、链接、列表等）
   - **无意义过滤**：过滤纯数字、纯符号、页眉页脚、页码（如 "Page 5 of 10"、"第 3 页"）
   - **配置项**：enabled、min\_length、strip\_html、strip\_markdown、normalize\_whitespace、filter\_meaningless、header\_footer\_patterns

4. **构建 LlamaIndex Document**（元数据在后续流程中就会绑定text）
- **数据来源**：上一步解析器输出的 list\[dict]，每个 dict 包含 text 和 metadata
- **具体操作**：遍历每个解析片段（section），将其转为 LlamaIndex 的 Document 对象
- **数据流向**：
  - text 字段 → Document.text（原始文本内容）
  - metadata 合并两部分：
    - 解析器自带的：source（文件路径）、page（页码，PDF特有）、total\_pages（总页数）、chunk\_type（如"table"）、table\_rows（表格行数）
    - 系统注入的：document\_id（UUID）、document\_name（原始文件名）、knowledge\_base\_id（所属知识库ID）
- **一对多关系**：一个上传文件可能产生多个 Document（如 PDF 每页一个 section），它们共享同一个 document\_id
- **作用**：将不同格式的解析结果统一为 LlamaIndex 标准数据结构，为后续 IngestionPipeline 的分块和 embedding 做准备
- **去向**：这些 Document 会被传入 IngestionPipeline，经过 ChunkNodeParser 分块后生成更细粒度的 Node，每个 Node 继承父 Document 的 metadata

5. **分块 + Embedding + 写入**
- **分块**
  - 输入List\[Document]（上一步构建的 LlamaIndex Documet）
  * 遍历每个Document，提取其text内容
  * 根据用户上传时的选择选择分块策略：
    - **常规策略**：sentence（按句子）、paragraph（按段落）、header（按标题层级）、char（按字符数）
    - **层次分块策略（hierarchical）**：一种父子块分块策略
      - 分两阶段切分：先按 parent_size（语义分块，默认1536token）切父块，再在每个父块内按 child_size（句子分块，默认384token）切子块
      - 子块记录 parent\_index 关联到父块
      - 设计目的：子块保证细粒度匹配，父块保证上下文完整
  * 常规策略切分规则：chunk_size= 768token，chunk_overlap= 128token
  * 构建Node：每个chunk生成一个TextNode，继承父Document的metadata，生成唯一NodeId
  * 输出List\[TextNode]（每个 Node 包含 node\_id , text , metadata ）
  * **层次分块特殊处理**：子块的 metadata 中包含 parent\_id 指向父块，父子块都会写入Qdrant
- **Embedding**
  - 输入：List\[TextNode]
  - 调用bge-m3模型执行
  - 流程
    - 批量编码 ：Pipeline 自动将所有 Node 的文本分批送入 Embedding 模型
    - 模型调用 ：通过 Ollama HTTP 服务调用 bge-m3
    - 输出 ：每个 chunk 生成一个 1024 维浮点向量 （dense vector）
    - 注入 ：向量附加到对应 Node 的 embedding 字段
  - 特点：该过程为异步且支持批量
- **写入Qdrant**
  - 输入：带有embedding的List\[TextNode]
  - 流程：
    - 获取 Collection （如不存在会先创建）
    - 转换格式 ：将 LlamaIndex Node 转为 Qdrant Point 格式：
```python
{
  "id": node_id, # UUID 字符串
  "vector": [0.123, ...], # 1024 维dense vector;
  "payload": {
    "text": "chunk内容",
    "document_id": "...",
    "document_name": "report.pdf",
    "knowledge_base_id": "...",
    "page": 1,
    ...
  }
}
```

-  Collection结构
  - Dense vector：cos距离，1024维
  - HNSW索引：m 和 ef\_construct 可配置，支持 O(logN) 快速检索
  - Payload索引：document\_id , chunk\_type , parent\_id （keyword 类型，支持标量过滤）
- 补充BM25 Sparse Vector
  - 从所有Node中提取出text
  - 使用 fastembed 的 Qdrant/bm25 模型进行Sparse编码
  - 输出格式 ： (indices, values) 稀疏对
    - indices ：词在词典中的位置
    - values ：BM25 权重
  - 更新向量，将sparse vector补充到已经写入的point

6. **文档状态更新**
- 文档状态： parsing → ready （异常时 → error ）
- 更新 chunk 数量到 JSON 元数据文件
- 知识库文档计数 +1

**完整的检索流程**

1. **解析用户询问**，先检查缓存，缓存有内容直接返回答案
2. **调用 \_build\_engine() 根据配置选择检索器**，engine.aquery(query) 触发检索
3. **元数据过滤**（可选）
   - 用户通过 `metadata_filter` 参数指定过滤条件（如 `{"document_type": "pdf", "year": 2024}`）
   - 过滤发生在 **Qdrant 数据库层**，在向量检索之前执行
   - 不符合条件的文档直接被过滤掉，**不参与后续 Dense/BM25 检索**
   - 优势：减少检索范围，加快查询速度；Dense 和 BM25 各应用一次相同的过滤条件
   - 支持操作符：`$eq`, `$ne`, `$in`, `$gte`, `$lte`, `$range` 等

4. **进行查询扩展**
- HyDE：LLM假设一个答案，根据假设答案去查dense向量
- 多查询：让LLM从不同角度改写问题

5. **并行混合检索**（dense + BM25）
- **dense稠密检索**，将用户query转化为Embedding向量，再在Qdrant中用ANN搜索（HNSW索引），找到距离最近的topK个point，找到语义相关的，默认取前20条
  - 转化过程：query字符串传入embed\_model（bge-m3），通过Ollama HTTP服务调用，输出1024维浮点向量
  - 对比方式：余弦相似度，计算查询向量与库中每个chunk的1024维向量之间的夹角余弦值
  - 搜索算法：HNSW（Hierarchical Navigable Small World），构建多层图结构，从顶层粗粒度搜索逐层向下细化，快速定位最近邻
  - 特点：能理解语义，"苹果"和"水果"即使没有相同词也能匹配
- **BM25稀疏检索**，将query转化为sparse向量（包含词典中命中的词的位置和BM25权重），进入Qdrant库，Qdrant对每一个point中的sparse向量做内积运算（只有词典中的词的位置相同的维度才参与计算，所以叫稀疏），搜索算法使用的是倒排索引，默认取前20条
  - 转化过程：query字符串传入SparseEmbedService，通过fastembed库本地加载Qdrant/bm25模型（进程内，不走HTTP），输出(indices, values)稀疏对
  - 对比方式：内积（dot product），只计算indices重叠的部分，score = Σ(query\_value × point\_value)
  - 搜索算法：倒排索引（inverted index），term\_id → \[(point\_id, weight), ...]，遍历查询向量的每个term，从倒排索引中取出包含该term的所有point，累加权重
  - 特点：精确关键词匹配，只有出现相同词才匹配，擅长专有名词和精确匹配

1. **RRF融合**：融合两路搜索结果，消除多路检索结果的冗余，dense 的20条 + BM25 的20条混合排名后取前15条
- 核心思想：不比较原始分数，只比较排名。即使不同召回方式的分数量级不同也能计算
- 当 HyDE + 多查询开启时，会有多个查询各自做混合检索，最后全部一起 RRF 融合

7. **递归检索**
- **触发条件**：基于 RRF 融合后的前15条结果，提取上下文和关键词进行二次递归检索。
- **作用**：对RRF粗排后的结果进行渐进式的深挖，补充还没有召回的相关chunk
- **检索流程**：
  1. **父块获取**：通过子块的 parent\_id 批量查询 Qdrant，获取对应父块内容
  2. **去重替换**：同一父块的多个子块只保留RRF分数最高者，用父块内容替换子块内容
  3. **补充 standalone**：不足 target\_k=5 时补充无 parent\_id 的独立块
- **设计优势**：子块保证细粒度召回，父块提供完整上下文，避免子块截断导致的语义不完整

8. **Reranker精排**
对 RRF 融合（或递归检索）产出的前15条结果，使用 Cross-Encoder（交叉编码器）逐条打分重排，\[query + text\] → \[模型\] → 相关性分数，取 top5 送给大模型。分数过低的直接截断，不交给大模型
- **作用**：上述粗排后的结果容易出现语义不匹配但关键词重合的干扰信息，reranker针对语义作精准筛选重新打分
- **模型**：BAAI/bge-reranker-v2-m3，FP16 精度推理
- **执行方式**：通过 `run_in_executor` 放入线程池异步执行，不阻塞 asyncio 事件循环
- **降级策略**：Reranker 加载失败或推理异常时，自动回退到 RRF 原始排序，不阻塞整条链路
- **异步初始化**：应用启动时通过 lifespan 预加载 Reranker 模型，避免冷启动延迟

### Q4: 双路召回加 RRF 融合加 Reranker 这个架构中，你认为最可能成为性能瓶颈的是哪一部分？

**你可以这样回答：**

按影响程度排序，最大的瓶颈是 Reranker，其次是 LLM 生成，Embedding 推理排第三，Qdrant 检索和 RRF 融合基本可以忽略。

**Reranker 为什么是最大瓶颈？** 因为 Cross-Encoder 需要对每个查询和文档对做一次完整的 Transformer 前向推理。完整管道是：dense 粗排20条 + BM25 粗排20条 → RRF 融合取前15条 → Reranker 逐条打分取前5条 → LLM 生成。Reranker 要处理 15 个候选文档，那就是 15 次推理。每次大约 50 到 100 毫秒，加起来就是 750 毫秒到 1.5 秒，占了端到端延迟的 40% 到 60%。

**Embedding 推理**每次 50 到 200 毫秒，还好，而且缓存命中率高的话可以省掉大部分。

**Qdrant 检索**用的是 HNSW 索引，O(logN) 的复杂度，基本上 10 毫秒以内就搞定了，完全不是瓶颈。**RRF 融合**纯内存计算，不到 1 毫秒，忽略不计。

**优化方向上**，最有效的是 Reranker 的加速，比如用粗排加精排两阶段、ONNX 量化、批处理，预期可以降低 50% 到 70% 的延迟。LLM 这边可以做高频答案缓存，或者用更小的模型。Embedding 侧主要靠缓存和本地化推理。

**【可能的追问】如果要求 P99 降到 1 秒以内，你怎么做？**

那得做一些取舍了。最直接的是砍掉 Reranker，管道从「20+20→15→5→LLM」变成「20+20→15→LLM」，延迟能从 3 秒降到 1 秒左右，但 NDCG 会从 0.85 掉到大概 0.72。然后高频查询走缓存，延迟 10 毫秒以内。HyDE 和多查询这些增强策略也得关掉，能省 500 毫秒到 1 秒。Embedding 用 fastembed 做进程内推理，不用 Ollama HTTP 调用，再省 50 到 100 毫秒。最后就是把 Reranker 的多次推理做 batch 化。

## 第二层：文档解析与向量存储

### Q5: 对于 PDF 中的表格、图片、多栏布局，你是如何处理的？

**你可以这样回答：**

**表格处理**，我用的是 PyMuPDF 的 find_tables()，它能自动检测表格边界，然后提取出 DataFrame 并手动拼接转成 Markdown 格式（带有表头分隔符 `---`）。为什么要转 Markdown？因为 Markdown 保留了行列结构，LLM 能更好地理解，而且转成文本方便后续向量化。我会把每个表格单独存成一个字典（类似 chunk），并在 metadata 里记录 `chunk_type="table"` 以及 `table_rows`，这样后续可以针对表格做特殊处理或检索加权。

**多栏布局**，因为 PDF 的文本提取默认是按照底层指令顺序，多栏的话如果直接 get_text 读出来容易乱序串行。我的做法是调用 `page.get_text("dict")` 拿到每个文本块的 bounding box（bbox），通过 X0横坐标判断它属于哪一栏。具体来说，按大概 200 像素的分辨率分组（`round(x0 / 200)`），将分入同一组的文本段按区块落入对应栏里。每栏内部按纵坐标排序。最后再根据栏位 x 坐标从左到右排序拼接。这样能保证阅读顺序正确。如果用多栏算法提取出的文本为空，我会做一个 fallback，回退到普通的 `page.get_text()`进行原始顺序提取。

**内容校验与清洗**：除了格式解析，我还会做一道防线。提取完的文本会过一个 `validate_parsed_text` 方法，过滤掉长度少于 50 个字符的无效片段，并且通过 `langdetect` 判断语言，剔除掉不是中文（含繁体）和英文的乱码。

**图片处理**，当前系统的重心在文本，所以图片内容不会提取和入库。如果要改进的话，可以通过集成 BLIP 或者 LLaVA 这样的视觉语言模型，把图片转成对应的描述文本加入 chunk。

**【可能的追问】如果 PDF 是扫描件怎么办？**

扫描件本质上是图片，必须上 OCR。我会选 PaddleOCR，因为它中文识别效果好，而且支持表格结构识别。流程就是 PDF 逐页转成图片，OCR 识别出文本加位置信息，然后走正常的分块入库流程。

**【可能的追问】表格转 Markdown 有什么局限性？**

最大的问题是合并单元格和嵌套表格，Markdown 不支持。复杂表格转成 Markdown 会丢失结构信息。改进方案是用 JSON 或者 HTML 格式来保留完整的表格结构。

### Q6: 不同格式解析后是否统一成某种中间表示？怎样保证元数据的一致性？

**你可以这样回答：**

是的，所有的解析器最后都统一输出成 list\[dict] 格式，每个 dict 包含 text 和 metadata 两个字段。text 是纯文本内容，metadata 里面放各自格式特有的元数据。

**元数据一致性**这块，我们的设计原则是：各格式解析器只产生自己特有的元数据，入库时由统一的 DocumentService 追加通用元数据。

举个例子，PDF 解析器会产生 page 和 total\_pages 这两个字段，DOCX 就没有。但不管是哪种格式，入库时 DocumentService 都会统一加上 document\_id、document\_name、knowledge\_base\_id 这些字段。

这样做的好处是，查询的时候你可以通过 payload 过滤来筛选，不存在的字段不会影响查询，因为 Qdrant 允许部分 point 缺少某些字段。

### Q7: 知识库维度 Collection 资源隔离，是多 Collection 还是单 Collection 加字段过滤？

**你可以这样回答：**

我当前用的是**每个知识库一个独立 Collection**的方案，Collection 名就是 kb\_ 加上知识库 ID。

这两种方案各有利弊，我给你们分析一下。

**多 Collection 的优势**在于物理隔离，数据安全性更好，查询时不需要 payload 过滤，性能更优，而且删除知识库的时候直接 delete\_collection 就完了，非常干净。缺点就是 Collection 数量多了之后管理起来麻烦。

**单 Collection 加字段过滤**的优势是管理简单，就一个 Collection，适合知识库数量特别多的场景，比如几千上万个。但缺点也很明显：每次查询都要加 filter，有性能开销；所有知识库共享同一套 HNSW 参数，不能独立调优；删除知识库需要按 filter 批量删除 point，可能有残留。

**我的选择逻辑是**：当前业务场景下知识库数量不超过 1000 个，多 Collection 的方案利大于弊。如果以后知识库数量爆炸式增长，再切换到单 Collection 加 knowledge\_base\_id 过滤的方案。而且 Qdrant 的 payload index 对 keyword 类型过滤优化得很好，性能损失不超过 10%。

**【可能的追问】多租户安全怎么保证？**

Collection 隔离天然解决了这个问题——租户 A 根本访问不到租户 B 的 Collection。再加上 JWT 鉴权，Token 里带上用户可访问的知识库列表，API 层每次查询前都校验一遍，双重保障。

### Q8: 元数据的标量过滤是如何实现的？在查询时是如何下推到 Qdrant 的？

**你可以这样回答：**
元数据是LLM从用户输入的内容中提取关键词进行映射
我们在代码层面封装了一个 `QdrantFilterBuilder` 模式的工具类，通过链式调用（如 `.eq()`, `.in_()`, `.range()`）动态构建出 Qdrant 底层原生支持的嵌套过滤字典（形如 `{"must": [{"key": "...", "match": ...}]}`）。查询的时候，将生成的字典作为 `query_filter` 参数直接透传给 `get_client().query_points()` 接口即可。无论是稠密向量检索（Dense）还是稀疏检索（BM25），都会将这个条件丢给 Qdrant 在检索引擎引擎内部做前置过滤，提前缩小检索范围，只在指定文档 / 章节里搜索，不全文乱搜。

关键点在于**要预创建 payload index**。我们在创建 Collection 的时候，会通过循环，显式为 `document_id`、`rag_doc_id`、`chunk_type`、`parent_id`、`chunk_level` 这些刚需过滤字段，同步建立 `keyword` 类型的 payload index（标量索引）。如果没有 payload index，在大规模检索时一旦带有过滤条件，引擎就会退化成去扫描 payload 读取字段来匹配，检索开销显著放大。

**有没有遇到过性能问题？** 目前还没有，原因有三点：一是物理上单知识库（单个 Collection）的数据量很小，一般不会超过上万文档；二是所有的热点查询字段全部利用 payload_index 前置了；三是日常过滤基本都是基于上述字段的直接等值匹配。

**但确实有潜在风险**，一方面是建立全量字段倒排索引会消耗更高内存，我们必须克制。另一方面，由于我们采用的是单机节点和 Qdrant 原生接口，只要没有给字段建立索引，任何在业务层追加的复杂过滤查询都会随时导致长尾延迟变大


### ### Q9: 批量写入时如何平衡写入延迟与检索实时性？中途失败怎么回滚或重试？

**写入和实时性的平衡**，其实 Qdrant 默认写入即持久化，写入完成后立即可检索。我们的做法是所有的分块、Embedding和入库全部跑完才返回，文档状态从 `indexing` 变成 `ready`，前端根据状态来判断能不能检索。所以刚入库的文档立即可检索到，没有延迟。

**关于失败处理与回滚**，为了避免中途失败导致 Qdrant 中残留脏数据，我们在项目中引入了自定义的 `DocumentTransaction` 上下文管理器，通过补偿操作实现逻辑事务与最终一致性：

1. **数据库预检与占位（为什么先写 SQLite？）**：进入上下文后，先在 SQLite 创建（或 `merge` 更新）文档记录，状态记为 `indexing`，利用关系型数据库保证业务原数据的幂等。**之所以先写 SQLite 而不是 Qdrant**，是因为关系型数据库是业务状态的单一数据源（Source of Truth）。如果先写 Qdrant 并在后续环节发生系统崩溃，向量库中就会产生没有任何业务关联的“孤立案“孤儿向量”（无法追踪且无法在前端被用户主动删除）；而先写 SQLite 相当于前置的业务占位，即便后续的 Embedding 或 Qdrant 写入发生导致进程退出的硬崩溃，数据库里也能留下明确的状态记录，这使得我们不仅可以向用户明确展示该文件的异常，也有基础依据在未来通过定时任务拿着这条记录去 Qdrant 执行脏数据清理。
2. **分批写入带重试机制**：Qdrant 的 Dense 和 Sparse 向量分批写入，遇到 transient error（如网络连接、超时报错）会通过指数退避进行重试。
3. **异常补偿回滚**：如果流程最终因为模型服务挂了或者写入异常等失败，上下文管理器会拦截异常并自动触发回滚行为，调用删除逻辑把已写入 Qdrant 的残片向量按文档 ID 清除，并将 SQLite 中的状态变更为 `error`（保留记录供排查）。这样系统就不会残留那些半成品的“脏排排”。

批量上传同时结合了并发控制，使用 `asyncio.Semaphore(5)` 限制同时最多处理 5 个文件，避免模型限流或 Qdrant 写入队列堆积。每个文件的事务相互独立，单个文件的抛错与回滚不会影响其他在传文件。


## 第三层：混合检索与重排序

### Q10: 稠密向量检索用的是什么 Embedding 模型？为什么选它？

**你可以这样回答：**

当前用的是 **bge-m3**，通过 Ollama 部署，1024 维。

**选它的原因有五个。** 第一，**多语言支持**，能同时处理中英文文档，我们业务里中英混排的情况很多，不需要为不同语言选不同模型。第二，**多粒度**，bge-m3 支持 dense、sparse、multi-vector 三种模式，虽然我们当前只用 dense，但后续有扩展空间。第三，**开源免费**，本地部署没有 API 调用成本。第四，**MTEB 排行榜靠前**，多个 benchmark 上表现都不错。第五，**Ollama 原生支持**，一条命令就能拉起来。

**对比过其他模型**，比如 bge-large-zh 中文很好但不支持多语言，text-embedding-ada-002 是闭源的要花钱，e5-large-v2 主要是英文。综合下来 bge-m3 最适合我们的场景。

**【可能的追问】bge-m3 的 sparse 能力你用到了吗？**

目前没有。bge-m3 本身可以做 sparse 检索，但我们的 sparse 是用独立的 Qdrant/bm25 模型实现的。后续可以尝试统一成一个模型，减少依赖。

***

### Q11: BM25 稀疏检索是 Qdrant 内置实现的，还是单独用 Elasticsearch？

**你可以这样回答：**

**用的是 Qdrant 内置的 sparse vector 功能**，没有单独引入 Elasticsearch。

为什么不用 ES？一是架构简化，引入 ES 就多了一个需要维护的组件；二是 Qdrant 从 1.7 版本开始原生支持 sparse vector，完全够用；三是 dense 和 sparse 向量存在同一个 point 里，不需要跨库查询，减少了网络开销和代码复杂度。

**具体的实现方式**是用 fastembed 的 Qdrant/bm25 模型，把查询文本转成 sparse vector，这个向量由 indices 和 values 两部分组成，indices 是词在词典中的位置，values 是 BM25 的权重。然后调用 Qdrant 的 search API，指定 query\_vector 的名字为 bm25，就可以做 sparse 检索了。

**两路结果怎么统一融合？** 关键是 RRF 融合只关心文档 ID 和排名，不关心原始分数。dense 路返回的是余弦相似度分数，BM25 路返回的是无界分数，两者的数值范围完全不同，但 RRF 只取排名算分。所以两路输出统一格式有 id、text、score、metadata 就够了，score 在 RRF 阶段其实用不到。

**【可能的追问】BM25 模型加载失败怎么办？**

有降级方案。我们会退到 keyword fallback，先用 dense 检索召回更多结果，然后基于关键词匹配对结果重新打分，用加权融合的方式排序。虽然精度不如 BM25，但至少保证服务可用。

***

### Q12: RRF 中的参数 k 你是如何选取的？有没有对比过其他融合方法？

**你可以这样回答：**

**k 取的是 60**，这是 RRF 论文里的经验值，在 TREC 实验中被证明是最稳健的取值。

k 的作用是控制排名权重的衰减速度。k 越小，排名靠前的文档权重越高，第一名和第二名的差距很明显。k 越大，各排名的权重趋于平均，第一名和第十名的差距缩小。k=60 的时候，第一名得分是 1/61，第十名是 1/70，差异平缓但又能体现排名差异，适合大多数场景。

**有没有对比过其他方法？** 理论上对比过几种。加权平均需要先解决分数归一化的问题，dense 的余弦相似度范围是 \[-1,1]，而 BM25 的分数是无界的，归一化本身就是一个坑。学习排序效果最好但需要标注数据，成本太高。Max Score 取两路最高分，但忽略了排名信息。综合下来，RRF 是最优选择，参数少、稳定、不需要归一化。

**【可能的追问】如果 dense 路明显优于 BM25，RRF 能体现吗？**

默认两路平等。如果确实需要，可以引入权重，比如 dense 权重 0.7，BM25 权重 0.3。但实践中我们发现 RRF 的平等加权已经够好了，因为 BM25 在精确匹配的场景下往往比 dense 强，两者有互补性。

***

### Q13: 如果某一路召回结果很少，比如只有 2 条，RRF 融合时会怎么处理？

**你可以这样回答：**

RRF 天然支持这种情况，不需要特殊处理。

我给你举个具体的例子。假设 dense 路返回了 A 到 J 十条结果，BM25 路只返回了 A 和 C 两条。那么在 RRF 融合时，文档 A 在两路都排第一，它的 RRF 分数是 1/61 加 1/61，加起来最高。文档 B 只在 dense 路出现，排第二，分数是 1/62。文档 C 在 dense 路排第三，在 BM25 路排第二，两路的分数加起来比 B 高。所以最终排名会是 A、C、B，既考虑了多路共现，又考虑了各自排名。

**极端情况**是 BM25 返回 0 条，这时候 RRF 退化为单路排序，等价于 dense 路的原始排名。如果两路都返回 0 条，那就返回空列表，后续的 Reranker 和 LLM 会处理空上下文的情况。

### Q14: 重排模型用的是 cross-encoder 还是其他结构？模型大小和推理延迟是多少？

**你可以这样回答：**

当前用的是 **bge-reranker-v2-m3**，属于 **Cross-Encoder** 架构。

Cross-Encoder 和普通的 Bi-Encoder 有什么区别呢？Bi-Encoder 是把查询和文档分别编码成向量，然后算余弦相似度。而 Cross-Encoder 是把查询和文档拼在一起输入 Transformer，让模型做细粒度的 token 级交互。所以 Cross-Encoder 精度更高，但速度更慢。

**模型规格上**，参数量大概 3 亿多，基于 XLM-RoBERTa-large，我们用 FP16 精度推理。单次前向推理在 CPU 上大约 50 到 100 毫秒，GPU 上 10 到 30 毫秒。我们有 15 个候选文档，那就是 15 次推理，CPU 上总共 750 毫秒到 1.5 秒，占了端到端延迟的 40% 到 60%。

**【可能的追问】有没有考虑过把 Reranker 放在 RRF 之前做？**

不建议这么做。原因有两个。

第一，计算量爆炸。RRF 之前 dense 和 BM25 各返回 20 条，去重后大概 30 到 35 个候选。如果先 Reranker 再 RRF，需要对这 35 个都做一次 Cross-Encoder 推理，而当前方案只对 RRF 融合后的 15 个做推理，计算量翻了一倍多。

第二，范式不合理。业界标准的做法是 Recall → Fusion → Rerank，先用 RRF 做粗排融合，再用 Reranker 做精排。如果把 Reranker 放在前面，就没有充分发挥 RRF 融合两路优势的作用。

### Q15: NDCG\@5 达到 0.85+ 这个结果是怎么得来的？

**你可以这样回答：**

这个要诚实地说，**项目目前还没有进行正式的 NDCG 评估**。因为我们还没有构建带有相关性标注的测试集。

我们提供了基于 Ragas 的评估框架，支持 faithfulness、answer\_relevancy、context\_precision、context\_recall、answer\_similarity 这五个指标。但 NDCG 评估需要人工标注每个查询和相关文档之间的相关性等级，这部分还没有做。

**那为什么我敢说 0.85+ 这个数字呢？** 这是参考了 BGE 论文的数据。论文里说，不加 Reranker 仅用 dense 加 BM25 加 RRF，NDCG\@5 大概在 0.72 到 0.78。加上 bge-reranker-v2-m3 重排后，能提升到 0.82 到 0.88，提升幅度大约 10% 到 15%。我们的架构和模型跟论文一致，所以实际效果应该在这个范围内。

**如果要验证这个数字**，我们需要构建 50 到 100 条测试样本，每条查询标注出相关文档，然后跑两次评估，对比开 Reranker 和关 Reranker 的 NDCG 差异。

## 第四层：质量评估与监控

### Q16: 你具体用了 Ragas 的哪几个指标？

**你可以这样回答：**

我用了 Ragas 的五个核心指标。

第一个是 **faithfulness**，翻译过来是忠实度。它衡量的是 LLM 生成的答案里每个陈述是否都能从检索到的上下文中推导出来。简单说就是检测有没有幻觉。如果模型编造了上下文里没有的信息，这个分数就会低。

第二个是 **answer\_relevancy**，答案相关性。它衡量的是答案是不是回答了用户的问题。有时候答案本身没错，但答非所问，这个分数就会低。

第三个是 **context\_precision**，上下文精确度。它衡量的是 top-K 检索结果里相关文档的比例。如果检索到了很多不相关的东西，分数就会低。

第四个是 **context\_recall**，上下文召回率。它衡量的是所有相关的文档有多少被检索到了。如果关键信息没被召回，这个分数就会低。

第五个是 **answer\_similarity**，答案相似度。用向量相似度把生成答案和参考答案做对比，越接近分数越高。

这五个指标各有侧重。faithfulness 主要看幻觉，answer\_relevancy 看是否答非所问，context\_precision 看检索质量，context\_recall 看检索覆盖率，answer\_similarity 看答案整体质量。

### Q17: 评估数据集怎么构建的？人工标注还是自动生成？多少条样本？

**你可以这样回答：**

**当前我们支持手动创建结合自动生成的方式**来构建测试集。

**手动创建**是通过 API 提交问题和参考答案。人工标注的方式质量最高，适合做核心重点用例的测试，但成本也比较高。

**自动生成**方面，**当前项目已经实现了通过脚本自动生成测试集**。我们使用了批处理脚本自动读取知识库里已完成切分的 Chunk，送入 LLM 批量生成问答（QA）对，并将这些 QA 对转化为格式化的测试集导入系统。这样能够以极低的成本快速扩充大批量的样本，后续结合人工快速抽查来把控最终质量。

**关于样本数量**，最小可用的话 20 到 30 条就够了，覆盖主要的业务场景。推荐规模是 50 到 100 条，要包含一些边界 case。生产级别的话建议 200 条以上，并且定期更新。

**【可能的追问】怎么用 LLM 自动生成 QA 对？**

写一个 prompt，比如"基于以下文档内容生成 5 个问答对"，然后从知识库里随机抽取文档喂给 LLM。但要注意，自动生成的 QA 对可能会有噪声，比如答案不正确、问题太简单等，所以人工审核这步不能省。

***

### Q18: 有没有发现 Ragas 的某些指标与实际用户体验不一致的情况？

**你可以这样回答：**

这个其实是 Ragas 的已知问题，需要特别注意。

第一个问题是 **faithfulness 依赖评判 LLM**。faithfulness 的计算需要另一个 LLM 来判断答案里的陈述是否有上下文支撑。如果评判用的 LLM 比生成答案的 LLM 更强，分数可能过于严格。反过来，如果评判 LLM 比较弱，又可能漏掉幻觉。不同 LLM 的判断标准不一样，分数会有波动。

第二个是 **answer\_relevancy 的反向问题生成**。它是通过生成反向问题来评估相关性的，但生成的反向问题本身可能不准确。比如用户问了一个开放性的"请介绍一下"，反向问题可能就偏了。

第三个是 **指标之间的权衡**。提高 context\_recall 需要召回更多文档，但可能降低 context\_precision，因为引入了噪声。提高 faithfulness 要求严格基于上下文，但答案可能不够直接，导致 answer\_relevancy 下降。

**我们怎么缓解呢？** 不依赖单一指标，综合看五个指标的趋势变化。定期人工抽检，校准评估结果。更关注指标的变化趋势而不是绝对值。

***

### Q19: 你埋点了哪些关键 Span？怎么定位慢查询？

**你可以这样回答：**

**当前我们暴露了 Prometheus 指标**，包括**查询延迟分布、查询成功失败计数、每次召回文档数分布、Embedding 调用延迟、文档上传计数**等。

**具体怎么定位慢查询呢？** 目前的做法是在日志里记录查询的总耗时。如果要精确定位卡点，需要在代码里加细粒度的计时。

比如在查询执行的每个环节前后都记录时间：缓存检查花了多久、Embedding 花了多久、Qdrant 检索花了多久、RRF 融合花了多久、Reranker 花了多久、LLM 生成花了多久。然后分析 breakdown。

**如果 embed\_time 高**，说明 Ollama 服务慢或者网络有延迟。**retrieval\_time 高**，说明 Qdrant 负载高或者 HNSW 参数不合适。**reranker\_time 高**，说明模型大或者 CPU 不够。**llm\_time 高**，说明 LLM 服务慢或者生成的答案太长。

**【可能的追问】OpenTelemetry 用了吗？**

我们在项目中集成了 OpenTelemetry（OTel）的基础框架来进行全链路追踪（Distributed Tracing），这对于 RAG 这类包含多个耗时节点的复杂系统（如大模型调用、向量检索）非常关键。

**关于 OpenTelemetry 的详细介绍及我们的实现：**
1. **自动提取（Auto-Instrumentation）**：引入了 `FastAPIInstrumentor`。通过对 FastAPI 应用的自动插桩，我们无需修改大量业务代码，就能自动捕获所有的 HTTP 请求流，记录每一个 API 调用的路由、请求方法、状态码和整体响应时间，形成端点间的核心跨度（Root Span）。
2. **异步批量导出（BatchSpanProcessor）**：为了避免链路追踪数据上报拖慢主业务逻辑，我们配置了 `BatchSpanProcessor` 配合 `OTLPSpanExporter`（通过 `OTEL_EXPORTER_OTLP_ENDPOINT` 环境变量对接）。它能够在后台异步缓存打包并批量分发 Spans 数据。
3. **标准化与无厂商锁定**：OpenTelemetry 作为 CNCF 推出的可观测云原生行业标准（统一了 Tracing、Metrics 和 Logging 的数据规范），选用它的最大好处是能够无缝通过 OTLP 协议将数据发射给 Jaeger、Zipkin 或者 Grafana Tempo 等主流展示后台。

**进一步的演进规划：**
目前系统自动接管了框架层的 HTTP 进出流量追踪，但业务层级的排障现在还是主要依赖 Prometheus 的时长统计和结构化日志。后续重点深化链路追踪：
- **更细化的业务 Span：** 利用已封装好的 `get_tracer("rag-service")` 建立细粒度子级 Spans，将一次提问精准拆分成“提问意图重写”、“文本分块 Embedding”、“Qdrant 检索”、“Reranker 重排节点”、“LLM 流式吐字阶段”等多个独立卡点。
- **三大支柱融合：** 真正把 Trace ID 打入 Logging 体系和 Metrics 例外报告中。一旦出现上游超时，就可以直接根据日志中的 `trace_id` 抓出整个瀑布流调用火焰图，一眼看透到底是哪个外部大模型 API 卡顿了，还是向量检索节点性能衰退。

## 第五层：部署与接口封装

### Q21: Docker 一键部署是如何实现的？

**你可以这样回答：**

Docker 一键部署的核心是通过 Docker Compose 将所有服务整合成一个配置文件，用户只需要一条命令就能启动整个系统。

整体思路是**把依赖的服务和应用容器化，统一编排管理**。系统包含四个核心容器：Qdrant 作为向量数据库，Ollama 提供 Embedding 和 LLM 推理服务，Reranker 模型服务负责精排打分，FastAPI 应用服务承载核心业务逻辑。这四个容器通过 Docker 网络互联，彼此之间用容器名进行通信。

**实现的关键点有几个方面。**

**镜像构建方面**，FastAPI 应用使用多阶段构建，先在构建阶段安装依赖，再复制到精简的运行环境中，最终镜像从 2.1GB 压缩到 500MB。Ollama 直接使用官方镜像，预拉取 bge-m3 嵌入模型和需要的大语言模型。Reranker 模型首次启动时自动下载，后续挂载到持久化卷避免重复下载。

**数据持久化方面**，向量数据通过 Docker Volume 持久化到 Qdrant 容器，即使容器重启数据也不会丢失。Ollama 的模型同样挂载到卷上，避免每次重启都要重新拉取模型。Reranker 模型文件也持久化，首次下载后后续启动直接加载。

**网络通信方面**，所有容器加入同一个 Docker 自定义网络，容器之间通过服务名直接访问，不需要写死 IP 地址。比如 FastAPI 连接 Qdrant 用的是 qdrant 这个服务名加端口，连接 Ollama 用的是 ollama 加端口。外部访问通过端口映射，把 8000 端口暴露给宿主机。

**配置管理方面**，所有环境变量统一写在 Compose 文件的 environment 区块里，包括 Qdrant 地址、Ollama 地址、模型名称、分块参数等。用户只需要改这一个文件就能完成配置，不需要额外修改代码或者环境变量文件。

**启动流程上**，用户克隆项目后只需要执行 docker compose up 一条命令。Compose 会按照依赖顺序启动服务，先启动 Qdrant 和 Ollama 这些基础设施，再启动 Reranker 服务，最后启动 FastAPI 应用。启动完成后访问健康检查端点确认所有服务就绪。

**【可能的追问】如果某个服务启动失败怎么办？**

docker compose logs 加服务名可以查看具体容器的日志定位问题。常见情况有三种：端口被占用需要修改映射端口；模型下载失败检查网络或手动预拉取；Qdrant 数据卷损坏可以删除卷重建。

***

### Q22: 如果 Qdrant、Reranker 模型服务、FastAPI 需要横向扩展，Docker Compose 会怎么调整？

**你可以这样回答：**

Docker Compose 可以做基本的横向扩展。比如 FastAPI 服务可以设置 replicas 为 3，启动三个实例。前面再加个 Nginx 做负载均衡。

但 **Docker Compose 在横向扩展上有明显的局限**。第一，Qdrant 分布式需要至少三个节点加一致性协议，Compose 管理起来很吃力。第二，多实例需要负载均衡器，Compose 内置的 DNS 轮询不够灵活。第三，不支持零宕机滚动更新。第四，没法跨机器调度。

**所以我们考虑过 Kubernetes**。K8s 的方案是：用 Deployment 管理 RAG 服务，设置 3 个副本，配上 Readiness 和 Liveness 探针。用 HorizontalPodAutoscaler 按 CPU 使用率自动扩缩，最小 2 个最大 10 个。Qdrant 用 StatefulSet 部署 3 个节点组成分布式集群。前面用 Ingress 做统一入口和负载均衡。

**什么时候从 Compose 迁移到 K8s？** 三个指标：QPS 超过 100、数据量超过 100GB 需要 Qdrant 分布式、流量波动大需要自动扩缩容。

### Q23: 你对外提供了哪些接口？能给个例子吗？

**你可以这样回答：**

我们提供了 REST 和 gRPC 两套接口，分别面向不同的使用场景。

**RESTful API** 主要面向前端和第三方系统集成，按功能分几大类。

**知识库管理**：增删改查知识库。**文档管理**：上传文档、查看文档列表、查看文档详情、删除文档、批量上传和批量删除，还能查看文档的分块详情。**核心检索**：普通检索问答和流式检索问答。**评估**：创建测试集、运行评估、查看评估报告。**系统**：健康检查和 Prometheus 指标。

**给大家举两个最常用的 REST 接口例子。**

第一个是**上传文档**。POST 到 /api/v1/documents，参数包括知识库 ID 和分块策略，文件通过 multipart/form-data 上传。返回结果包含文档 ID、文件名、文件类型、文件大小、状态、分块数量等。状态从 processing 变成 ready 后就可以检索了。

第二个是**检索问答**。POST 到 /api/v1/query，请求体里传入 query、knowledge_base_id、top_k 等参数。返回结果包含 answer 和 sources。answer 是 LLM 生成的答案，sources 是检索到的相关文档列表，每条包含文本内容、相关性分数、来源文档 ID 和名称。

**gRPC 接口** 主要面向后端服务间的内部调用，追求低延迟和高吞吐。

**为什么引入 gRPC？** 有两个原因。第一，RAG 服务会被其他微服务内部调用，比如客服系统、知识库管理平台，这些场景对延迟敏感，REST 的 JSON 序列化开销和 HTTP 头负担在高频调用下比较明显，而 gRPC 使用 Protobuf 二进制编码，体积更小解析更快。第二，gRPC 原生支持双向流式通信，适合检索结果推送、批量文档入库等场景。

**gRPC 主要提供以下服务。** 第一是检索服务，支持普通检索和流式检索，流式模式下服务端可以逐 token 推送 LLM 生成的答案，客户端不需要轮询。第二是文档管理服务，支持批量上传和批量删除，Protobuf 的 repeated 字段天然适合批量操作。第三是知识库管理服务，增删改查知识库。

**Protobuf 定义方面**，消息类型包括查询请求、查询响应、文档上传请求、文档信息，服务接口用 service 和 rpc 声明，每个 rpc 方法定义请求和响应的消息类型。流式接口在返回类型前加 stream 关键字即可实现服务端流式推送。

**两套接口的关系是**，底层业务逻辑完全复用，REST 层通过 FastAPI 路由接收请求后调用核心检索服务，gRPC 层通过 grpc.aio 接收请求后也走同一套核心逻辑。这样保证了行为一致性，维护成本也低。

### Q24: 流式问答如何实现？用户中断会怎样？

**你可以这样回答：**

**采用 SSE 实现**，也就是 Server-Sent Events。

实现逻辑是：后端定义一个异步生成器，检索和重排是一次性完成的，然后 LLM 生成按 token 流式返回。每生成一个 token 就 yield 出去，前端通过 EventSource API 接收。生成完成后发送一个 \[DONE] 信号。

**用户中断请求的处理，当前做得不够完善。** FastAPI 的 StreamingResponse 在用户断开连接时，如果后端正在 yield，会抛出 CancelledError 或 ConnectionResetError，后台任务会被终止。但问题在于，如果用户中断时 LLM 已经在生成了，已消耗的计算资源就浪费了。如果中断时还在做检索，Embedding 和 Qdrant 的调用可能继续执行直到超时。

**改进方案**是在流式生成的循环里定期检查 request.is\_disconnected，如果客户端已经断开就主动 break 出来，减少资源浪费。

**为什么选 SSE 而不是 WebSocket？** 因为 SSE 实现简单，HTTP 兼容性好，而且我们的场景是单向推送——服务端推给客户端，不需要客户端反方向发控制指令。WebSocket 虽然支持双向通信，但复杂度更高，当前场景用 SSE 就够了。

### Q25: 有提供只检索不调 LLM 的接口吗？

**你可以这样回答：**

**目前没有专门的"仅检索"接口**，现有的 /api/v1/query 总是包含 LLM 生成步骤。

**但实现起来非常简单**，因为检索逻辑已经是独立封装的了。hybrid\_retrieve 这个函数完全可以单独调用。如果要新增一个接口，只需要写一个新的路由，调用 hybrid\_retrieve 返回结果列表，不调 LLM 就行了。

**什么场景需要这个接口呢？** 比如第三方系统有自己的 LLM，只需要我们的检索结果作为 context；或者前端想先展示检索结果让用户确认，再决定要不要生成答案；还有就是我们自己调试检索质量的时候也需要。

### Q26: 如何做鉴权和流量控制？

**你可以这样回答：**

**鉴权方面**，我们用的是 JWT，RS256 非对称加密。Token 由统一的认证中心签发，RAG 服务只保存公钥做验签。公钥缓存在内存里，避免每次请求都读文件。开发环境下没有公钥就跳过验证。

**流量控制方面，当前还没有实现**。我计划用两种方式。

第一种是应用层限流，用 slowapi 这个库，按 IP 或者 AppKey 限制每分钟的请求次数。简单场景下够用。

第二种是生产级方案，用 Redis 加 Lua 脚本做分布式限流，按 AppKey 分配不同的配额，比如免费用户每分钟 100 次，付费用户每分钟 1000 次。最好是在 API Gateway 层做限流，比如 Nginx 或者 Kong，不在应用层处理，这样更通用。

## 第六层：开放性与问题解决

### Q27: 你觉得当前模块最大的改进空间是什么？

**你可以这样回答：**

按优先级排序，我认为有三个层面的改进空间。

**P0 级别，检索延迟优化。** 当前端到端 P99 大概 3 到 5 秒，Reranker 占了 40% 到 60%。最优先的是把 Reranker 做批处理和 ONNX 量化，或者引入一个轻量级的粗排模型先筛一轮，再用大模型精排。预期能把 P99 降到 1 到 2 秒。

**P1 级别，智能分块策略。** 当前分块策略需要手动指定，不会根据文档类型自动选择。比如 Markdown 文档应该用标题分块策略，结构化文档用段落策略，无结构文本用语义分块。这个如果能实现，能大幅减少人工调优成本，提升分块质量。

**P1 级别，评估体系完善。** 当前有 Ragas 框架但缺少标准测试集。需要构建 50 到 100 条的标准测试集，定期运行评估，建立基线。这样每次优化都能量化效果，避免盲目调参。

**P2 级别，多模态支持和分布式部署。** 多模态方面，PDF 里的图片当前不处理，需要集成视觉语言模型做图片描述。分布式方面，需要从 Docker Compose 迁移到 K8s，支持水平扩展。

### Q28: 请讲一个在实际运行中遇到的检索质量或性能问题


**问题背景**：上线后有一周，客服团队反馈说最近检索质量明显下降，很多问题返回的文档完全不相关。这个反馈很严重，因为我们的系统就是用来帮客服快速找到答案的。

**定位过程分三步**：第一步，我先看 Prometheus 面板，发现 rag\_retrieval\_documents\_count 这个指标的 P50 从正常的 8 降到了 3，说明每次检索召回的相关文档数大幅减少。第二步，去看应用日志，发现大量 WARNING 级别的日志，内容是 sparse search returned 0 results。第三步，登录 Qdrant Dashboard 检查 Collection 状态，发现部分 Collection 的 sparse\_vector\_index 状态显示为 inactive。

**根因分析**：Qdrant 的 sparse vector 索引在创建 Collection 时默认是 lazy 模式，也就是异步构建。当文档批量写入速度超过索引构建速度时，就会出现一个窗口期——向量已经入库了但 sparse 索引还没建好。在这个窗口期内，sparse 检索返回 0 条结果，导致 RRF 融合时只有 dense 这一路在干活，检索质量自然就下降了。

**解决方案**：做了两件事。第一，在文档写入完成后增加了一个索引就绪检查，轮询等待 sparse 索引构建完成。最多等 10 秒，如果还没就绪就告警。第二，在检索层增加了降级逻辑，如果 sparse 返回空结果，就自动退到 keyword 检索作为 fallback。

**修复效果**：召回文档数恢复到 P50 等于 8 的正常水平，检索质量也恢复了。后续在文档入库流程中加入了索引就绪检查，彻底杜绝了这个问题。

**【可能的追问】怎么预防类似问题？**

四个方面。一是把 sparse 索引从 lazy 改为 immediate 模式，写入时同步构建，牺牲写入延迟换取检索一致性。二是在入库流程中加健康检查，索引未就绪就告警。三是在 Prometheus 里设置告警规则，当 sparse 检索频繁返回空结果时触发。四是自动化回退，检测到 sparse 连续几次返回空结果就自动切换为 keyword fallback。

**问题背景**：最开始对测试集进行评估时，遇到了两方面的痛点：一是数十上百个问题如果串行评估，耗时极长；二是如果简单粗暴地直接并发，HTTP 长连接仍然容易超时。并且由于评估涉及大量检索和重排计算，全量并发峰值轻易就会把本地部署的 Qdrant 数据库和重排服务（Reranker）打挂，还会引发 Ollama 向量获取时的响应堵塞。

**解决方案（实际实现思路）**：为了兼顾评测效率与系统稳定性，在项目中实现了一套精细化的后台异步与并发管控链路：
1. **接口异步化与后台处理**：触发测试集运行（`/run` 接口）时，首先在数据库插入一条 `status="running"` 的报告记录，然后借助 `asyncio.create_task` 开启后台计算协程，HTTP 接口当即返回报告状态，彻底解决调用端等待超时问题。
2. **信号量控制检索并发（Semaphore）**：在后台任务并行执行大量 Query 时，利用 `asyncio.Semaphore(16)` 设置了一个信号量阈值。将最大并发度压在 16 个（根据机器压测的经验安全值），有效保护了底层向量库和重排组件不会因为压力尖峰而宕机报错。
3. **计算提速与批量并发优化（Batching）**：
   - 专门挂载了 `_EvalRetrievalSettings` 上下文，临时关闭了无关的查询生成扩展（HyDE 和多查询），只评测底层核心检索管道，跳过了这部分昂贵的 LLM 耗时；
   - 在后续检索核心指标（Recall/NDCG 等）计算中，针对判断相关性所需的海量字符计算设计了单独的批量提取策略——`_PrecomputedEmbeddings`。先一次性拿到当前批次的文本全量统一提交给嵌入模型转换成向量矩阵切片，之后几十个评估指标并行计算任务只从预取缓存内复用结果片，极大减少了多次琐碎并发访问 Ollama 的 IO 阻塞和竞态开销。

**问题背景**：最开始测试的时候**Retrieval Precision@k**很低，但是其他指标都正常甚至优秀，后来发现是reranker阶段没有加入一个硬性指标，导致检索到的结构即使与问题关联很低依然拿来使用了，后来为reranker召回加了一个硬性底线，即使召回数量不足，也不召回分数过低的块

### Q29: 项目中是如何处理缺失值和异常值的？

**你可以这样回答：**

这个问题我们从三个层次来看：文档处理层、检索层、配置层。整体设计原则就一句话——**宁可降级也不崩溃**，每个环节都有回退路径。

**文档处理层**，处理的是文档内容的缺失和异常。

首先是**清洗模块**，这里的异常值过滤分几个维度：

- 空文本或纯空白 → 直接过滤
- 长度小于 10 个字符的过短文本 → 过滤
- 纯数字（比如 "123.45"）→ 过滤
- 纯符号（比如 "----"）→ 过滤
- 页码（"Page 5 of 10"、"第 3 页"）→ 过滤
- 自定义页眉页脚模式 → 正则匹配过滤，如果用户配了无效正则，我们会捕获 `re.error` 跳过，保证不崩溃

其次是**解析层**：

- 文本编码解码，按 `utf-8 → gbk → gb2312 → latin-1` 逐级尝试，全部失败才抛异常
- 语言检测，只保留中文和英文，但如果 `langdetect` 库没装，直接跳过，不阻塞流程
- 表格提取时如果 `find_tables()` 抛异常，返回空列表继续解析，不影响整页
- 过短文本小于 50 个字符的丢弃

然后是**文件类型检测**，三级检测链：Magic Number → 内容嗅探 → 扩展名兜底。每级失败走下一级，全部失败才抛异常。

最后是**文档入库的异常处理**：

- 知识库不存在 → 返回 404
- 清洗后全部被过滤，没有有效内容 → 报错提示用户原始文档质量差
- 处理过程中抛异常 → 文档状态标记为 error，方便排查
- BM25 编码全部失败 → 只记 warning，不阻塞入库

**检索层**，处理的是在线服务中的缺失和异常。

这块的降级策略最典型：

第一，**BM25 三级降级**：配置关闭 → keyword fallback；模型加载失败 → keyword fallback；Qdrant 查询异常 → try-catch 捕获 → keyword fallback。keyword fallback 本身也有保护，空查询直接返回空列表。

第二，**HyDE 降级**：LLM 生成假设答案失败时，直接走纯 dense 检索，记一条 warning。

第三，**递归检索结果不足**：去重后结果少于 5 条时，不强补，有多少返回多少，记 warning 日志。保证调用方不会拿到空结果。

第四，**Qdrant payload 字段缺失**：所有 payload 读取都用 `.get()` 加默认值兜底，text 缺失返回空字符串，metadata 缺失返回空字典。

**配置层**，处理的是配置缺失。

所有 Pydantic Settings 字段都有默认值，即使 YAML 配置缺失或者环境变量没设，也不会因为配置不存在而崩溃。比如 Qdrant 地址默认 `localhost:6333`，分块大小默认 512，粗排数默认 20。

**【可能的追问】缺失值和异常值的处理主要分布在哪些文件和模块？**

文档清洗在 `app/core/cleaner.py`，解析校验在 `app/core/parser.py`，文件类型检测在 `app/core/file_detector.py`，文档入库异常处理在 `app/services/document.py`，检索降级主要在 `app/core/retriever.py` 和 `app/core/rag_pipeline.py`，配置兜底在 `app/config/settings.py`。每个模块内部都遵循 Fail-Fast 加 Fallback 的原则，确保服务可用性。

**【可能的追问】你们在缺失值和异常值处理上踩过什么坑？**

有一个印象比较深的。早期 BM25 的降级策略只有一级：sparse 查询失败直接返回空结果。结果有次 Qdrant 内存压力大，sparse 索引查询超时了，所有请求的 BM25 那路都返回空，RRF 融合变成只有 dense 在干活，检索质量显著下降。后来加了 try-catch 和 keyword 回退才解决，从那以后我们就把全链路的降级策略摆到了很高的优先级。

### Q30: 拿到一份具体 RAG 的评估报告，指标如下，你怎么分析系统的瓶颈并给出优化方案？

| 指标                        | 分数     | 含义                              |
| ------------------------- | ------ | ------------------------------- |
| **Faithfulness**          | 0.8830 | 忠实度：大模型按检索内容生成的保真度（无幻觉程度）       |
| **Answer Relevancy**      | 0.9499 | 相关性：回答与用户意图的相关性（是否答非所问）         |
| **Context Precision**     | 0.8042 | Ragas检索精度：相关片段是否排在前面（无噪声干扰）     |
| **Context Recall**        | 0.8195 | Ragas检索召回：Ground Truth是否被全面检索出来 |
| **Retrieval Recall@k**    | 0.7320 | 纯硬指标：前 k 个返回块中实际囊括多少必选目标        |
| **Retrieval Precision@k** | 0.2722 | 纯硬指标：前 k 个返回块中，目标文档所占的比例        |
| **Retrieval NDCG@k**      | 0.9135 | 排名的质量（真正起作用的高效文档是否排在最靠前）        |

的**第一反应是将整个系统的短板切分为“生成端”和“检索端”来定位瓶颈**。我们可以通过这些数据的组合呈现，非常清晰地描绘出系统当前的健康状况。

**1. 生成端诊断（LLM 表现良好，但被噪声带偏）：**
*   **如何定位瓶颈：** `Answer Relevancy` 极高（0.9499），说明 LLM 完美理解了用户意图；但 `Faithfulness`（0.8830）未达到完美，有约 12% 的内容没有上下文支撑。结合较低的检索精度（下述），瓶颈在于 LLM 的抗干扰能力不够：它在面对无关内容时，违背了“仅依靠上下文”的原则，而是通过自身先验知识进行了“脑补”。
*   **如何优化（零成本干预）：** 
    *   将 LLM 的 `temperature` 下调至 0.01，让模型表现更为冷酷和保守。
    *   强化防御性 Prompt：加入类似“当提供事实时必须严格基于下文来源并通过[1][2]标出引用，如无法找到足够依据请回答不知道，绝不要补充你的知识”。

**2. 检索端排序诊断（排序能力极强，但头部噪声偏大）：**
*   **如何定位瓶颈：** `Retrieval NDCG@k` 惊人得高（0.9135），说明 Reranker 重排模型极其出色——它确实把最有用的结果都顶到了最前面。但极其拉胯的 `Retrieval Precision@k` (0.2722) 宣告了我们向 LLM 喂入了海量垃圾数据（在送入大模型的 k 个块中，平均不到 30% 是有用的，剩下的都是噪声）。
* **如何优化：**
    * **治标策略：** 直接减小送给 LLM 的切片数量。既然 NDCG 高但 Precision 低，那就意味着“后面部分全是在凑数的烂数据”。果断降低 `top_k`（如从 5 降到 3），或者设置一个 Reranker `score threshold` 的硬性阈值，一旦切片低于某分值直接扔掉，不喂给 LLM。

**3. 检索端召回诊断（存在不可忽视的漏检）：**
* **如何定位瓶颈：** `Retrieval Recall@k` (0.7320) 和 `Context Recall` (0.8195) 只是勉强及格水平。这意味着大概有 20-25% 的必须参考的文档，压根就没有进入最终池（连给 Reranker 排名的机会都没有）。
* **如何优化（彻底扩宽漏斗模型入口）：**
    * **低成本优化：** 确保 BM25 (Sparse) 与 Dense 向量组成的**双路混合检索（Hybrid Search）**已配优权重。增大前置粗排的召回数量（比如 `dense_top_k` 从 20 拉高到 50），将初筛漏斗开得更大一些。
    * **块粒度优化：** 将固定分块策略升级为“父子文档递归检索”或者语义段落分块（Semantic Chunking）。这样保证匹配的时候使用粒度最细的话题块（防止长文拉低相似度），而在喂给 LLM 时又能顺藤摸瓜给回完整的父文档（拉满召回率）。
    * **高杠杆上限增强：** 引入大模型重写（Query Rewriting）或 HyDE 技术。很多查询在单一短句下很难命中目标库，让模型自我衍生提问和背景，能提升 5-15% 的召回下限上限。

## 附录：常见追问补充

### A1: 你们的 RAG 系统跟市面上其他产品比，核心优势是什么？

五个优势。第一，混合检索加 RRF 融合加 Reranker 三段式架构，比单一 dense 检索召回率提升 30% 以上。第二，每个知识库独立 Collection，天然支持多租户，数据安全有保障。第三，全链路可观测，每个环节都有监控指标，慢查询可以精确定位到具体卡点。第四，降级策略完善，任何一路出问题都有备选方案，保证服务高可用。第五，流式输出，首 token 延迟小于 500 毫秒，用户体验好。

### A2: 如果重新设计，你会做哪些不同的选择？

第一，Embedding 服务独立部署，不跟主服务混在一起，方便水平扩展。
第二，用 Redis 替代进程内 TTLCache，多实例共享缓存，缓存命中率能提升 40% 以上。第三，智能分块默认开启，上传文件先统一选择层次分块，在内部实现文档格式检测，对于日志等层次分块效果不好的文档进行降级处理，使用基础分块策略
第四，Reranker 模型做 INT8 量化，从 1.3GB 降到 350MB，延迟降低 50%。
第五，文档入库阶段加质量评分，过滤掉空白页、低质量 OCR 这些垃圾文档。
第六，稀疏检索可以采用ElasticSearch，增加精准度

### A3: 如何保证 RAG 系统的安全性？

六层保障。数据层面，每个知识库独立 Collection 物理隔离。接口层面，JWT 鉴权加 AppKey/Secret 签名。输入层面，对用户查询做敏感词过滤和注入检测。输出层面，对 LLM 生成内容做安全审查。审计层面，所有查询和文档操作都有日志。限流层面，按 AppKey 限制 QPS。
